# 并行开发协作规范

**适用**：多会话（多个 AI 会话 / 多人）在同一仓库并行开发的所有场景。本规范由 transformation-plan S6 试点确立并经试点复盘升版（v2，2026-09-07）。**第八节（账本时效纪律）同样适用于单会话串行工作**——账本滞后不是并行特有问题，其根因（完成实现 ≠ 完成登记 + 合并后无人回头销账）在任何工作模式下都存在。

## 一、核心铁律：一会话=一分支=一能力域

1. **一会话=一分支=一能力域**：每个并行会话在独立分支上工作，只负责一个能力域（如 admin 认证、脚本契约、审核拆分）；跨能力域的需求拆成独立任务排到合并之后，不在并行分支上顺手实现。
2. **分支创建/切换/合并/推送一律由用户手动执行**（见 [git-safety.md](git-safety.md)）；会话只在当前分支的工作区内编辑文件。
3. 任务启动时**必须**在 [docs/process/CURRENT.md](../../docs/process/CURRENT.md) In-flight 区登记（见第三节），未登记不得开工；任务完成合并后由执行会话（或下一会话）销账。

## 二、文件路径互斥

1. **任务启动时声明触碰文件清单**（In-flight 区登记项之一），清单外的文件原则上不改；确需扩面时先更新登记再动手。
2. **两份登记清单不得存在交集**：新任务启动前先读 In-flight 区，与现有任务触碰面重叠即停，改选任务或等对方销账。
3. 高风险共享文件（任何任务都可能顺手改的文件）默认冻结，只有登记在案的 owner 会话可改：
   - `AGENTS.md`、`CLAUDE.md`、`docs/process/CURRENT.md`（登记/销账操作除外，见第三节）
   - `pyproject.toml`、`uv.lock`、根配置文件
   - `migrations/`（Alembic 迁移号互斥，见第四节）
   - `.github/workflows/`
4. 并行期间对共享文档（specs/、product/、domain/）的修改，仅限本任务能力域直接相关的条目；大面积文档重构禁止并行，串行安排。

## 三、CURRENT.md In-flight 区使用流程

In-flight 区是并行协调的唯一登记处，登记动作本身不视为触碰 CURRENT.md。

1. **登记（任务启动时）**：在 In-flight 表新增一行——任务名、分支名、触碰文件清单、状态（`进行中`）。
2. **状态更新（任务过程中）**：状态变化（如「实现完成待合并」）时更新本行。
3. **销账（合并完成后）**：合并入 dev/main 后，将该行状态改为 `已合并（<合并提交短哈希>）` 或直接删除该行（保留在 status-archive 有据可查的前提下）。
4. CURRENT.md 保持在 ≤150 行；In-flight 区不承载任务细节，细节看各自任务文档或 transformation-plan。

## 四、Alembic 迁移号与共享本地库互斥

1. **迁移号互斥**：并行期间 Alembic 迁移文件（`migrations/versions/`）串行产出——要么**迁移冻结**（并行窗口内不接受新迁移），要么**单会话负责**（In-flight 区指定唯一 owner，其他会话不得新建迁移文件）。
2. **`.local/*.db` 共享库互斥**：SQLite 本地库（research.db 等）是共享可变状态，并行期间由 In-flight 区指定唯一 owner 会话执行写入操作；其他会话对 `.local/` 只读。
3. 违反互斥导致迁移号撞车或库状态污染时，停止实现并报告，由用户裁决恢复方式（对齐 git-safety 的异常处理纪律）。

## 五、合并队列纪律

1. 合并顺序按 In-flight 区登记顺序或用户指定顺序**串行**执行；每次合并前 rebase 到最新 dev，CI 全绿后合并，再处理下一个。
2. 合并操作由用户手动执行；会话的义务是：合并前提供**改动文件清单 + 建议 commit message + 冲突风险评估**。
3. 合并后发现冲突：优先回退该分支由 owner 会话重做 rebase，禁止在合并现场由非 owner 会话代解。
4. 每次合并后，其余在队分支合并前须再次 rebase 并重跑各自全量回归（防止前序合并引入的语义漂移）。

## 六、基线口径与验证纪律（试点沉淀）

1. **全量回归的基线口径以「最近一次合并入 dev 的绿基线 + 各在队分支新增测试」动态计算**：并行期工作区可能同时包含其他会话的未合并改动（如 S5 的 `tests/scripts/`），跑出的总数高于账本基线不代表回退；判回退标准=失败数 > 0 或既有用例由绿转红。
2. **工具门禁范围以 CI 为准**：如 ruff 的 CI 范围是 `src/ scripts/ tests/`，仓库根全量跑出的 spike/、migrations/ 存量违规不算回退；报告基线时注明口径。
3. **运行环境锁定**：全量回归用项目 `.venv`（或 `uv run`）执行，不用裸系统 python（缺依赖会产生假失败）。
4. 每个分支合并前的本地验证清单：pytest 全量 + ruff（CI 范围）+ 相关前端三件套（Vitest + tsc + build）+ golden（求解器相关时）+ check_docs + check_layering。

## 七、试点复盘记录（v1 → v2 演进）

- **v1（2026-09-07，S6-1 建立）**：确立一会话=一分支=一能力域、触碰清单互斥、In-flight 登记流程、迁移/共享库互斥、合并队列纪律五条主干。
- **v2（2026-09-07，S6-5 复盘升版）**：S6 试点（任务 C admin 会话持久化 × 另一会话 S5 脚本契约）实战沉淀——
  1. **冲突点实测为零**：S5 触碰 `scripts/` + `tests/scripts/` + `script-contract.md`，S6 触碰 `admin-web/src/auth` + 文档治理文件，清单零交集，合并预期零解冲突。唯一共享触碰是 `CURRENT.md` 与 `transformation-plan.md` 的登记/状态表更新，靠「只改自己那一行/格」约定避免（已隐含在 v1 第三节，本条显式化）。
  2. **机制缺口 ①：In-flight 区双会话并发写 CURRENT.md**：两会话可能同时更新登记表造成文本冲突。缓解：登记行内不改他人内容；若发生冲突由后提交方 rebase 时手工并排保留两行。此为当前最大机制缺口，未来可考虑登记文件拆分或加锁。
  3. **机制缺口 ②：测试基线漂移**：并行期工作区混入他人未合并测试导致总数变动（本次 465→479），验证时必须按第六节第 1 条口径动态判定，不能机械对比账本数字。
  4. **机制缺口 ③：本地环境不一致**：裸 python 无 alembic/httpx 造成 49 个假收集错误；全量回归必须用项目锁定环境。
  5. **任务选择纪律有效**：排除 A（S7 前置未满足且与 S7-1 重叠）、排除 B（S3 P0-1 已完成大半）、选 C（触碰面最小、与 S5 天然正交）——「先读 In-flight 区再选任务」流程可复制。

## 八、账本时效纪律（v2.1，2026-09-07 增补）

**问题**：账本滞后（状态表/里程碑与仓库实际不一致）反复出现——不仅限于并行期，**单会话串行工作同样会发生**（本日实例：S6 会话合并入 dev 后，其状态表停在「进行中/待合并」直到下一轮才被发现）。根因：账本更新的触发时机挂在「会话自觉」上，完成实现 ≠ 完成登记，而合并动作由用户执行，合并后的销账最容易被漏。**这是流程结构问题，不是某个会话的疏忽**，所以解法必须机械化，不能靠「下次注意」。

**规则**：

1. **谁执行，谁登记**：每个会话在任务实现完成时立即更新 transformation-plan 状态表 + CURRENT.md（实现完成 ≠ 已合并，状态写「实现完成待合并」），不等合并、不等对方。
2. **合并后销账由后跑的会话负责**：任何会话开工前读 CURRENT.md 时，若发现 In-flight 区或状态表与 git log 不一致（如显示「待合并」但提交已存在），**顺手收口**——更新状态、跑 sync + check_docs。这把销账从「owner 会话的义务」变成「下一个读到的人的自动动作」，不依赖漏登记的那个会话自己回头补。
3. **收口属于登记动作**：按第三节，更新账本不视为触碰冻结文件，与「清单零交集」原则不冲突。
4. **check_docs 是下限不是上限**：它只校验节点声明一致性与行数预算，校验不了「状态表说进行中但代码已合并」这类语义漂移——语义一致性靠本节第 1、2 条纪律保证。

**单会话场景的机械化兜底（v2.1 增补）**：

5. **任务收尾固定收口脚本化**：会话每完成一个 transformation-plan 任务（或一轮实质性工作），收尾固定执行三件事——①更新账本（状态表 + CURRENT.md）→ ②`python scripts/sync_agents_docs.py` → ③`python scripts/check_docs.py`。把「跑门禁」作为收尾的机械动作而非自觉行为。
6. **建议的最低成本机器化（按需采纳）**：`check_docs.py` 新增一个轻量 warning 级检测项——用正则从 transformation-plan 状态表提取形如「待合并」「进行中（2026-xx-xx）」的条目，对照 `git log --oneline` 近期提交 message，发现「任务名已出现在提交历史但状态非已完成」时输出提示。这是提示不是门禁（warning 不算失败），专治单会话「合完了忘收口」；若误报率高再回退。此项尚未实现，登记为候选改进，采纳时先写契约测试。
