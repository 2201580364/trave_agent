# 需求规格化技能

把「功能」转成「可验证的规格」，是工作流 G2 阶段的核心动作。

## 输入

- 产品文档中的功能清单（[docs/product/](../../../docs/product/)）
- 假设登记册（[docs/assumptions.md](../../../docs/assumptions.md)）

## 步骤

1. **选功能**：按优先级（核心假设承载者优先，如「一键生成分日行程」承载 H3）。
2. **写头标**：关联假设 `H-x`、关联指标、优先级。
3. **拆验收标准**：用 Given/When/Then，每条标准必须回答「测谁、怎么测、对应哪个假设」。
4. **覆盖路径**：至少包含正常、边界、异常和降级场景，明确未排入原因和不可静默丢弃规则。
5. **把主观词客观化**：拆成硬约束违反数、交通耗时、开放时间命中率、未排入原因覆盖率、Golden Case 接近度、体力均衡度等；体力不得写成硬预算通过率。
6. **写追溯**：在规格末尾列出「假设 ↔ 验收标准 ↔ C-x/S-x ↔ 指标」映射表。
7. **落盘**：写入 `docs/specs/<功能名>.md`，标明状态、版本和设计依据。

## 质量自检（退出准则）

- [ ] 每条验收标准可测、有量化阈值
- [ ] 正常、边界、异常和降级路径齐全
- [ ] 核心假设的验收标准已客观化（不依赖纯主观评分）
- [ ] 追溯表完整，且没有把软约束误写成硬约束
