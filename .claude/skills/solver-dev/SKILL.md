# 求解器开发技能

以 [trip-solver.md](../../../docs/specs/trip-solver.md)、ADR-0002/0003/0004 和 [Gate 规范](../../../docs/process/gates.md) 为准。`spike/` 只提供历史证据，不作为生产代码模板。

## 开始协议

实现前声明任务关联的 H-x、验收标准、C-x/S-x、ADR、包含/排除范围和验证命令。发现权威来源冲突时停止实现并报告。

## P1 最终约束

- 硬约束：C1 多天闭馆与例外、C2 入园时间窗、C4 首末日锚点、C5 极端天气、C6 OD 交通衔接。
- 软约束：S1 默认 60% 游览时长阈值与提示、S2 体力均衡与节奏提示。
- 体力不得作为拒绝合法行程的条件；不得恢复 3/5/8 星硬上限。
- 当前目标函数为 `min Σ travel`。体力均衡只在分天启发式中体现，不进入目标函数。

## P1 分层流程

```text
Step 1 可用性感知分天
  K-Means 空间初分
  → 闭馆/天气不可用时移到最近可用日
  → 时间容量均衡
  → 高体力景点软均衡
Step 2 天内 OR-Tools TSP-TW
  硬时间窗 + 首末日锚点 + OD transit + AddDisjunction
  缓冲折入 transit，禁止后处理破坏已满足的窗口
Step 3 日间/晚间分段
  晚间-only 景点独立求解，不插回日间路线
Step 4 全量校验与输出
  C1/C2/C4/C5/C6 违反数为 0 才输出
  返回未排入景点及结构化原因、实际可玩时长与节奏提示
```

## 约束 TDD 顺序

1. 先写一个会失败的约束测试，再写最小实现。
2. 优先按 C1 → C2 → C4 → C5 → C6 实现；随后实现分天、路由、S1、S2 和输出。
3. 每个硬约束至少覆盖正常、边界、异常和降级路径。
4. S2 必须测试“有条件时倾向分散”和“无法分散时仍输出且提示偏紧”，不得测试硬拦。
5. 运行对应单测、全量测试、Golden Case、ruff 与 mypy。
6. 记录随机种子、求解器参数、数据版本和 OD 来源，保证结果可复现。

## 不变量

- 不静默丢弃景点；所有未排入项必须有 reason code。
- LLM 不参与景点分配、排序、时间或硬事实决策，只可解释确定性结果。
- 近似 OD 仅可作为明确标注的降级实现，并通过同一接口替换为真实路网 OD。
- 改变目标函数、恢复体力硬约束或引入新求解路线必须先写 ADR。
