# 技术 Spike 技能

> 核心原则：**风险前置**。最不确定的（求解器、数据质量）最先验证，不按自然实现顺序排。

## 何时用

- 要验证一个「可能走不通」的技术方案
- 团队对某技术无经验（如无 OR 背景的求解器）
- 要在投入大量实现前降低不确定性

## Spike 模板

1. **验证问题**：一句话说清要回答什么（如「K-Means 聚类分天是否会产生严重不均衡分组」）。
2. **成功/失败判据**：实验前量化定义（如「10 景点/3 天无 1/9 极端失衡，高体力景点在可行时得到分散，硬约束违反数为 0」）。
3. **时间盒**：明确限时（无 OR 背景时放宽）。
4. **可丢弃**：代码只求结论，不要求进入主代码库。
5. **结论输出**：保存环境、输入、随机种子、原始结果、局限、结论与下一步。

## 本项目两个必做 Spike（G3）

1. **Solver Spike**：验证「分层求解（K-Means 聚类 → TSP-TW 天内排序 → 约束校验）」在真实数据上可行、典型规模 < 30s 收敛。参考 [spike/solver_spike/](../../../spike/solver_spike/)。
2. **Data Quality Spike**：20 个景点端到端「爬取 → LLM 结构化 → 人工校准」，量化 LLM 抽取开放时间/闭馆日的准确率，据此定抽检比例。

## 输出

Spike 报告保存实验事实；只有形成长期架构/产品决策时才写 ADR，并记录「何时推翻重议」。Spike 代码和 README 必须标注为历史验证资产，不得覆盖 Accepted ADR 或当前规格。
