# Gate 7 专家评审与用户验证方案

- 文档版本：V1.1
- 日期：2026-08-29
- 产品里程碑：M1 — 行程骨架验证
- 当前状态：R0.1 环境锁机制和 R0.2-01 地点/投影 ADR 已完成；R0.2-02～07 杭州研究数据、R0.3 服务器 H5 和 R0.4 内部 dry run 待执行；尚未招募、尚未收集真实用户证据
- 关联假设：H1、H2、H3、H6、H7、H11
- 技术输入：Gate 6 已通过；A6 首个浏览器可操作纵向切片已收口

## 1. 目标和证据边界

Gate 7 的目标不是再证明“代码能运行”，而是判断 M1 的核心产品假设是否得到足够的人类证据支持，并把失败归因到数据、算法、交互、预期管理或基础设施。

以下证据必须分开保存和解释：

| 证据层 | 能证明什么 | 不能证明什么 |
|---|---|---|
| Spike/自动化 | 技术可行、硬约束、回归稳定、性能 | 用户是否认可、是否愿意使用或分享 |
| 真实 Chrome 验收 | 页面可操作、响应式、错误恢复 | 目标用户独立完成率和真实满意度 |
| 领域专家评审 | 行程结构、路线、时段和解释是否专业可接受 | 普通用户是否易用、是否愿意采用 |
| 形成性用户测试 | 发现交互摩擦、理解偏差和信任问题 | 以小样本确认 H3/H11 已证实 |
| 确认性用户测试 | 按预注册指标判断 H3/H6/H7 | 实际出行疲劳、线上分享转化 |
| 受控出行/线上试运行 | H2 实际疲劳、H11 分享漏斗 | 更大范围的长期留存或商业可行性 |

自动化、团队成员、AI 生成评价和公开攻略综合接近度不得计入目标用户样本量。未满足可观测前提的假设必须标记为 `not_evaluable`，不能用“暂无负面反馈”判定通过。

## 2. Gate 7 分段

```text
G7-R0.1 protocol/证据/环境锁定机制
→ G7-R0.2 杭州研究数据与地点类型建设
→ G7-R0.3 受控服务器 H5 研究环境
→ G7-R0.4 内部 dry run
→ G7-R1 形成性专家/用户测试
→ 修复 blocker/major 并回归
→ G7-R2 确认性 H3/H6/H7 测试
→ G7-R3 真实出行与分享漏斗试运行
→ 假设复盘和 M1 决策
```

### 2.1 G7-R0 准备门禁

开始接触参与者前必须满足：

- 本方案、专家表、用户脚本和证据 Schema 已版本化；
- protocol 在首个有效样本产生前锁定，按键排序和无空白 JSON canonicalization 生成跨平台 SHA-256；
- 使用稳定部署环境，不在访谈中临时修改代码或数据；
- 每个 session 固定应用版本、数据快照、求解器/约束/参数版本；
- 有知情说明、退出机制和最小化记录方案；
- 原始录音、联系方式、精确出行信息只保存在受控研究空间，不进入 Git；
- 仓库只保存匿名化聚合报告和不可逆 participant pseudonym；
- 团队成员和直接参与开发者只能做 dry run，不能计入用户结论；
- blocker/major 的定义和停止规则已明确。

R0 不以“文档存在”为完成。外部参与者开始前必须依次通过：

- R0.1：protocol、证据 Schema、研究环境 manifest 和隐私门禁；
- R0.2：先按 [`ADR-0018`](../decisions/ADR-0018-place-catalog-and-solver-projection.md) 建设通用 Place、访问点与求解投影，再形成足以支持真实选择的杭州 published research snapshot；当前 7 个路线点只保留为技术回归基线；候选来源由 AI 自主检索、获取、登记和交叉核验，未经合规与人工审核不得发布；
- R0.3：参与者可从自有手机访问的受控服务器 H5，或有书面理由限定为主持人设备的现场研究环境；edge/H5、FastAPI、迁移任务、MySQL、Redis 必须由一个逻辑 Docker Compose 项目统一管理；
- R0.4：团队内部 dry run，开放 blocker 和影响核心任务的 major 均为 0。

详细数据、渠道和部署门禁见 [`gate7-data-deployment-readiness-plan.md`](gate7-data-deployment-readiness-plan.md)。微信小程序正式上线不是 G7-R1 前置条件；移动端 H5 + HTTPS 是当前推荐研究入口，小程序体验版可在形成性问题关闭后补充验证。

### 2.2 G7-R1 形成性测试

目标是发现问题，不做“假设已证实”结论。

- 领域专家：3 人，每人独立评审至少 6 个场景；
- 目标用户：8–12 人；
- 采用 think-aloud 和主持人观察；
- 每 3–4 人形成一个修复批次；
- 出现 blocker 时暂停后续招募，修复并完成技术回归后继续；
- 同一参与者在修复前后的两次结果不能作为两个独立样本。

### 2.3 G7-R2 确认性测试

确认性样本必须在 protocol 锁定后一次性按同一口径收集：

- 目标用户有效样本 `n >= 21`；
- 参与者不是项目成员、开发者或测试数据提供者；
- 每个家庭/同行组最多计一个独立 H3 样本；
- 首次使用旅行助手，不能先接受功能教学；
- 只有主持人按脚本提供的标准提示可记录为 assistance；
- 结果必须同时记录成功样本、失败样本和退出样本；
- 不得为了达到阈值排除“不喜欢结果”的参与者；
- 确认性收集期间不得调整阈值、问题措辞或统计口径。

### 2.4 G7-R3 受控试运行

H2 和 H11 需要真实行为证据，不能由室内可用性测试替代：

- H2：参与者实际完成 2–4 天旅行后回访疲劳度、节奏提示匹配度和是否需要硬上限；
- H11：使用可公开访问的安全分享对象、独立接收者和明确转化事件；
- 测试环境必须具备必要的隐私说明、事件去重和机器人/团队流量排除；
- 受控试运行不是稳定生产发布，仍限制城市、样本和邀请范围。

## 3. M1 假设验证矩阵

| 假设 | 当前可观测性 | 主要研究 | 有效样本与判定 | 当前前置缺口 |
|---|---|---|---|---|
| H1 体力体系可理解 | 部分不可观测 | 形成性理解测试 | 只测试用户真实可见的体力/节奏文案；调整率 `>40%` 触发需调整 | 当前 UI 主要暴露“节奏”，未完整暴露 1–5 星体系；不得向用户解释隐藏模型后再计为理解 |
| H2 体力软约束可接受 | 室内不可确认 | G7-R3 实际出行回访 | 至少 12 名完成 2–4 天真实行程的参与者；记录实际疲劳偏差和要求硬上限比例 | 需要真实出行、行后回访和疲劳量表 |
| H3 比手动排更合理 | 可验证 | 专家评审 + G7-R2 | 目标用户 `n>=21`；认可率 `>=70%` 为支持，`<50%` 为推翻，`50%–69%` 为需调整；同时不得存在未关闭 blocker | 需要外部参与者和稳定研究环境 |
| H6 愿意填写到离锚点 | 可验证 | G7-R1/R2 任务行为 | 记录独立完成率、放弃率和 assistance；放弃/跳过率 `>50%` 推翻；其余结合定性证据判定 | 需要统一事件/观察口径 |
| H7 锚点提升合理性 | 需对照变体 | 反事实行程盲评 | 同一输入生成有锚点与无锚点版本，顺序随机；不得让用户知道哪个是产品版本 | 需要离线 ablation 生成器或固定对照样本，当前 UI 不提供“无锚点生成” |
| H11 分享成为获客钩子 | 当前不可确认 | G7-R3 分享漏斗 | 分享率目标 `>=30%`；独立接收者打开后参考复制/注册转化 `<5%` 触发需调整 | 当前只有安全链接和 HTML/CSS 卡片，缺图片/二维码/原生分享、正式转化埋点和公开试运行环境；未补齐前标记 `not_evaluable` |

H1、H2、H6、H7 的最终成功阈值若超出 `assumptions.md` 已登记内容，必须在首个有效样本前通过假设修订明确，不得在看到数据后补定。H3 的 `n>20 / >=70% / <50%` 和 H11 的 `>=30% / <5%` 沿用现有登记册。

H3 还要求数据供给不成为明显混淆因素：参与者必须有足够的杭州地点选择、区域和类型覆盖，替换候选不能因目录过小而失效。若数据覆盖不足，问题归因为 `data`，对应样本只能进入形成性观察，不能被解释为算法价值已验证或已推翻。

## 4. 样本分层与招募

### 4.1 领域专家

至少覆盖三类独立视角，每类至少 1 人：

- 杭州本地导游、定制旅行规划师或目的地运营人员；
- 熟悉城市公共交通、步行衔接或旅游路线的人；
- 有旅行产品、行程编辑或内容策展经验的人。

排除直接参与本项目求解器、Golden Case 或 UI 设计的人。专家可以获得场景事实和数据来源，但盲评阶段不能看到算法目标函数、历史评分或其他专家意见。

### 4.2 目标用户

确认性样本建议按以下维度预先分层，最终报告必须公开各层有效数：

| 维度 | 分层建议 |
|---|---|
| 攻略经验 | 经常手排 / 偶尔参考攻略 / 基本不做攻略，各不少于 6 人 |
| 同行类型 | 独自或情侣 / 朋友 / 亲子或长辈同行 |
| 节奏偏好 | 悠闲 / 适中 / 紧凑 |
| 行程长度 | 2 天 / 3 天 / 4 天 |
| 到离场景 | 首日早到 / 午后到达 / 末日提前离开 |

参与者应有真实或可回忆的杭州出行需求。纯粹为了完成测试而随机勾选景点的样本只能进入形成性观察，不能计入 H3 确认性分母。

## 5. 固定用户任务

| Task | 用户目标 | 可观察结果 | 关联假设 |
|---|---|---|---|
| T01 | 从首页开始新建杭州行程 | 能理解产品定位并进入规划 | H3 |
| T02 | 输入自己的日期、到达和离开事实 | 是否独立完成、是否跳过/误解锚点 | H6/H7 |
| T03 | 选择 5–10 个真实想去景点 | 选择是否符合本人需求，是否需要反复返回 | H3 |
| T04 | 生成并解释每日行程 | 能否找到午晚餐、交通、固定场次、未排入和依据 | H3/H7 |
| T05 | 判断计划是否愿意直接采用或作为主要底稿 | 二元认可 + 1–5 合理性 + 原因 | H3 |
| T06 | 替换一个不满意的景点 | 能否理解会生成新 Revision | H3 |
| T07 | 查看历史版本并返回当前版本 | 是否误以为历史会覆盖当前行程 | H3 |
| T08 | 对一个节点和整体行程提交反馈 | 能否区分安排反馈与景点评分 | H3 |
| T09 | 创建安全分享并说明接收者看到什么 | 隐私边界是否理解 | H11 准备证据，不计转化 |
| T10 | 接收他人分享并参考新建自己的行程 | 能否理解只复制景点、需重填日期交通 | H11 准备证据 |

主持人不得提示按钮位置、解释“正确答案”或替参与者选择景点。只有参与者停滞超过 60 秒或明确请求帮助时，才能按用户脚本提供一级提示；仍无法继续时提供二级提示，并分别记录。

## 6. 专家评审维度

每个场景独立评分 1–5，并要求引用具体 Revision/node：

1. 硬事实可信度：开放、闭馆、最晚入园、固定场次、天气和到离边界；
2. 空间合理性：同日区域、真实 OD、交通方式和往返折腾；
3. 时间合理性：上午/下午/晚上分布、午晚餐、建议时长和空白；
4. 节奏与体力：单日负载、连续高强度、休息和提示；
5. 可执行性：普通游客能否按计划实际行动；
6. 解释充分性：用户能否理解安排和降级原因；
7. 总体可接受性：是否愿意把它交付给真实游客。

任何硬约束错误、虚构真实 OD/天气、无法解释的景点丢失或可能导致误车/闭馆扑空的问题直接登记为 blocker，平均分不能补偿。

## 7. 观察和问卷指标

### 7.1 行为指标

- `task_completed_without_assistance`；
- 一级/二级 assistance 次数；
- 任务耗时；
- 返回、误点、重复提交和放弃；
- 到离锚点填写完成/跳过；
- 是否查看交通、餐食、未排入和解释；
- 是否完成替换、历史回看、反馈和分享理解任务。

### 7.2 H3 主指标

在主持人解释算法或展示专家意见前询问：

> 如果这是你的真实杭州行程，你是否愿意用这份计划替代自己从零手排，或把它作为主要行程底稿？

只接受 `yes/no` 作为主指标 `plan_preferred_over_manual`。随后记录 1–5 合理性评分、信心和原因作为解释性指标，不得用平均星级替代二元认可率。

### 7.3 反例和退出

以下样本仍必须保留在报告中：

- 生成失败或参与者中途退出；
- 参与者认为计划明显不合理；
- 参与者依靠二级提示才能完成；
- 实际需求超出杭州单城或当前产品范围；
- 数据错误导致结果不可评价。

只有不满足预注册招募条件、重复参与、无知情同意或证据损坏的样本可以排除，并必须记录排除原因。

## 8. 问题严重度与归因

严重度不能使用产品实现优先级 P0/P1/P2，避免概念混淆：

| 严重度 | 定义 | 处理 |
|---|---|---|
| blocker | 硬约束/安全/隐私错误，或多数用户无法完成核心任务 | 立即暂停对应研究批次，修复并全量回归 |
| major | 用户需帮助才能完成、计划质量显著受损或产生明显不信任 | 进入 M1 补修队列；关闭前不得进行确认性结论 |
| minor | 不阻断完成，但增加操作或理解成本 | 排序后修复，可进入下一批并持续观察 |
| observation | 偏好、建议或尚无足够证据的问题 | 保留，不自动转成需求 |

归因必须从以下枚举中选择一个主因，可附一个次因：

```text
data
algorithm
interaction
expectation_management
infrastructure
research_protocol
out_of_scope
```

## 9. 隐私和证据保存

- `participant_id` 使用研究系统生成的随机假名，不包含姓名、手机号、微信号或邮箱；
- Git 中不得保存录音、视频、原始聊天、精确票号/班次、家庭住址或联系方式；
- 原始材料保存在受控目录，报告只引用不可逆 `source_ref`；
- `.local/gate7/` 可用于本机临时材料，已被 `.local/` 总规则忽略；
- 真实证据 JSON 不提交时，仓库至少提交匿名聚合报告、protocol hash、样本区间、排除数、限制和反例；
- 任何公开报告中，单个自由文本引语必须人工去标识，并避免可组合识别信息；
- 参与者撤回后，原始材料按研究流程删除，聚合统计根据知情说明决定是否重算。

## 10. Gate 7 决策规则

### 10.1 允许进入确认性测试

- 形成性测试无开放 blocker；
- major 已修复，或有书面理由证明不影响主指标；
- 所有修复通过全量自动化和 Chrome 核心回放；
- protocol、应用版本和数据版本重新锁定；
- 确认性主持人脚本不再改变。

### 10.2 H3 结论

| 条件 | 结论 |
|---|---|
| 有效目标用户 `<21` | `insufficient_evidence` |
| `n>=21` 且认可率 `>=70%`，无开放 blocker | `supported` |
| `n>=21` 且认可率 `<50%` | `refuted` |
| `n>=21` 且认可率 `50%–69%` | `needs_adjustment` |

专家评分用于解释和发现风险，不替代 H3 用户分母。专家出现硬约束 blocker 时，即使用户认可率达到 70%，H3 也不能判定为 supported。

### 10.3 M1 路径

| 结果 | 后续 |
|---|---|
| H3 supported，关键 guardrail 可接受 | 准备受控 M1 试运行；H2/H11 继续按真实行为验证 |
| H3 needs_adjustment | 按 data/algorithm/interaction/expectation 归因补修，生成新 Revision 证据后重测 |
| H3 refuted | 停止扩大范围，重议核心价值主张和 M1 方案，不进入 M2 功能堆叠 |
| 证据不足 | 继续招募或修复研究设计，不能把“不足”解释为通过 |

## 11. 机器证据和执行命令

protocol：

```text
docs/test/gate7-protocol-v1.json
```

真实原始证据建议保存为：

```text
.local/gate7/<study_id>/evidence.json
```

校验并生成匿名聚合报告：

```powershell
python scripts/run_gate7_report.py `
  --protocol docs/test/gate7-protocol-v1.json `
  --environment-manifest .local/gate7/<study_environment_id>/environment.json `
  --evidence .local/gate7/<study_id>/evidence.json `
  --output docs/test/reports/gate7-<study_id>-aggregate.json
```

真实证据收集前必须先按 [`gate7-research-environment.md`](gate7-research-environment.md) 生成状态为 `locked` 的 manifest。Evidence 必须引用同一环境 ID 和 manifest canonical SHA-256；真实 evidence 引用 `candidate/invalid` 环境、环境版本漂移或 manifest 晚于收集开始时间时，汇总器必须拒绝。

没有真实外部参与者证据时不得生成或提交名为 `gate7-latest-passed.json` 的报告。测试 fixture 必须显式标记 `synthetic_fixture=true`，汇总器不得把它判为正式 Gate 7 通过。
