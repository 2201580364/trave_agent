# G7-R0.2-05-02 Revision 发布闭环 Chrome 验收

- 日期：2026-08-30
- 环境：本地 FastAPI `127.0.0.1:8000`、独立 `admin-web` `127.0.0.1:10086`、Google Chrome
- 数据：仅本地 SQLite 验收夹具 `browser-e2e-*`，未写入服务器 MySQL/Redis
- 凭证：使用本地长期管理员会话，密码未写入报告或日志

## 路径判定

产品支持两条合法的发布路径，二者都必须保留：

```text
路径 A：已有 human_verified Revision
  -> publication check
  -> 发布新的 Projection 快照

路径 B：已有基线 Revision
  -> 新建 candidate Revision
  -> 修改 candidate Revision
  -> 重新送审
  -> 审核通过进入 human_verified
  -> publication check
  -> 发布新的 Projection 快照
```

本报告分别保留了两类证据：Revision 2 曾验证了 API 准备夹具后由 Chrome 完成的后半段发布流程；本次 Revision 3 从已核验基线的 Revision 详情页点击“新建修订”开始，完整覆盖了路径 B 的浏览器操作，不再把创建步骤排除在 Chrome E2E 之外。

## 验收路径

```text
基线 Revision 1 browser-e2e-base
  -> Chrome 审核历史打开 Revision 详情
  -> Chrome 点击“新建修订”
  -> Revision 3 进入 candidate
  -> Chrome 编辑名称、地址、建议时长
  -> Chrome 点击“送审”
  -> Chrome 在审核队列点击“通过”
  -> Revision 3 = human_verified
  -> 为 Revision 3 准备独立 human-verified 几何、访问点、开放时间和 Projection 依赖
  -> Chrome 打开 Revision 3 详情并点击“发布新快照”
  -> publication check 通过，Projection 新快照发布
```

## 夹具说明

新 Revision 默认不会隐式复制几何、访问点、时间规则或 Projection。本次验收在 Revision 3 审核完成后单独准备了独立的 human-verified 几何、到达/离开访问点、开放时间规则和 Projection，并将 Projection 时长与编辑后的 Revision 对齐。夹具使用 `status=candidate` 和按 ORM JSON 对象计算的 Projection hash，确保 publication check 与正式数据模型一致。这是受控测试数据准备，不代表生产环境可以绕过 O04-O07 证据审核。

## 范围边界

本次验证的是 Projection 级发布闭环，不等同于 R0.2-07 的独立 research snapshot、城市当前快照指针、批次发布、旧快照退役或快照级回滚能力。新 Revision 的证据自动复制策略也仍需后续产品/数据治理决策。

## 清理

验收完成后应停止本地 API 与管理端进程。验收夹具保留在被 Git 忽略的本地 SQLite 中，不会进入 Git，也未修改 72 条正式 candidate 数据的生命周期状态。
