## 1. 结论

原 Gate 6 快照适合作为离线算法 fixture，但不能直接视为已校准的生产游客入口。7 个点中：

- 雷峰塔当前坐标距高德售票处约 67m，风险较低；
- 灵隐寺与飞来峰当前坐标分别距候选入口约 96m、174m，但二者属于共享景区和多门结构，仍需人工确认游客动线；
- 河坊街当前坐标距步行街代表点约 214m，属于街区代表点差异；
- 西湖湖滨偏移约 652m，原点不能继续无说明地作为湖滨公园代表点；
- 浙江省博物馆偏移约 636m，且必须明确是孤山馆区及具体入口；
- 湖滨晚间表演偏移约 755m，原点会明显扭曲与湖滨公园、省博等节点的真实衔接。

因此生成新的真实 OD 时应使用本报告候选点，但在正式生产发布前，仍须人工核对省博入口、灵隐/飞来峰联合游览入口和湖滨区域代表点。

## 3. 真实调用观察

连续无间隔文本检索期间，省博和雷峰塔两次返回：

```text
infocode=10021
```

按约 1.2 秒间隔重试后全部返回 `10000`。这进一步证明快照构建任务必须做请求节流，不能在普通 API 请求中无间隔批量调用。

高德文本检索“西湖音乐喷泉”时，普通 POI 搜索优先返回周边酒店和餐厅；使用 Input Tips 后才精确命中：

```text
B023B08WZ7
西湖音乐喷泉表演
120.160970,30.253778
```

因此发布审核不能简单采用“文本搜索第一条”，必须保存 POI ID、点位类型和人工审核状态。

## 4. 建模影响

单一 `lat/lng` 无法充分表达以下场景：

- 大型景区存在多个门；
- 灵隐寺/飞来峰共享外部入口，但内部游览节点不同；
- 湖滨、河坊街属于开放街区，没有唯一入口；
- 博物馆具有多个馆区和多个门；
- 固定表演地点与泛化街区点不是同一坐标。

后续发布数据至少需要保留：

```text
gaode_poi_id
routing_point_kind
coordinate_source
coordinate_fetched_at
coordinate_review_status
```

M1 求解仍可消费一个经过审核的 routing coordinate；M2 若支持景区内部游览、酒店出发和具体餐厅重排，应评估 arrival/departure 双点或景区内部接驳模型。

## 5. 发布门禁

候选坐标只有同时满足以下条件才能进入正式快照：

1. 高德 POI ID、名称、地址和城市一致；
2. 点位类型与实际游客到达语义一致；
3. 省博、灵隐/飞来峰等多门节点完成人工复核；
4. 使用候选点重新构建 42 条有向真实 OD；
5. 新快照 0 missing，任何 fallback 均显式标记；
6. 求解后景点守恒、C1/C2/C4/C5/C6 零违反；
7. 路线质量不出现跨区往返或因错误点位造成的虚假近邻；
8. 新快照使用新版本号，历史快照和历史 TripRevision 不覆盖、不重算。
