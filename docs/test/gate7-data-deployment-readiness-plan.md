# Gate 7 杭州数据与受控部署准备计划

- 文档版本：V1.3
- 日期：2026-08-29
- 产品里程碑：M1 — 行程骨架验证
- 所属阶段：G7-R0.2～G7-R0.4
- 当前状态：R0.2-01～04 已完成；72 个 candidate 和覆盖矩阵已锁定但尚未 human_verified。当前进入 R0.2-05-01 OM1 管理身份/API/审计底座；随后实现地点审核工作台，再执行批量事实采集与人工审核。尚未开始服务器应用部署或真实参与者招募
- 前置输入：Gate 6 已通过；A6 技术纵向切片已完成；G7-R0.1 研究环境锁定机制已完成

## 1. 决策摘要

G7-R1 正式人工测评前，必须先补齐足够的杭州研究数据和稳定、可追溯的受控测试入口。执行顺序固定为：

```text
G7-R0.1 研究环境锁定机制
→ G7-R0.2 杭州研究数据集与地点类型建设
→ G7-R0.3 受控服务器 H5 研究环境
→ G7-R0.4 内部 dry run
→ G7-R1 3 名独立专家 + 8–12 名目标用户形成性测试
```

渠道结论：

| 事项 | G7-R1 前置性 | 结论 |
|---|---|---|
| 服务器受控研究环境 | P0 | 远程或参与者自有手机测试前必须具备；优先采用移动端 H5 + HTTPS + 邀请访问 |
| Docker 部署与 Compose 管理 | P0 | edge、H5、FastAPI、迁移任务、MySQL、Redis 全部容器化，统一属于一个 Compose 项目；宿主机不直接运行应用服务 |
| 微信小程序正式上线 | 非前置 | 不阻塞 G7-R1；正式审核、备案和公开发布晚于形成性问题关闭 |
| 微信小程序体验版 | P1 | 可在 G7-R1 后半段或 G7-R2 前验证微信内渠道差异，不计为正式上线 |
| 杭州地点数据扩充 | P0 | 当前 7 个路线点只够技术验证，不能支撑真实选择、替换和专家路线评审 |
| 网红区域/街区数据 | P0 | 可以进入 M1 研究数据，但必须先定义区域、入口、内部游览和求解投影语义 |
| OM1 地点审核管理端 | P0 | 候选清单可先使用机器资产；50–75 个地点批量 human_verified 前必须具备独立管理身份、RBAC、审核工作台、发布门和结构化业务审计 |
| 社交平台大规模爬虫 | 不授权为默认方案 | 未完成来源条款、版权、隐私和反爬评审前，不采集评论正文、账号、图片或个人信息 |

本计划不修改 `gate7-protocol-v1.json`，因此 reviewed canonical SHA-256 保持不变。若后续数据或渠道变化影响研究问题、任务措辞、样本或指标，必须单独升级 protocol，而不能静默修改当前锁。

## 2. 当前基线与缺口

### 2.1 已有能力

- 7 个杭州路线点已经完成入口坐标人工复核；
- 7 点完整有向 OD 为 42/42，全部来自高德真实路网；
- 三日和风天气、开放时间、固定晚间表演、午晚餐留白和日内分布已经完成真实 Chrome 回放；
- `candidate → human_verified → published`、内容哈希、不可变快照和数据回放门禁已有技术基础；
- 用户可以选择、生成、替换、查看 Revision、分享和提交结构化反馈；
- 研究环境 manifest 可以固定 Git、数据、solver、数据库和前端 artifact。

### 2.2 为什么当前数据不能直接进入 G7-R1

G7 用户任务要求参与者选择 5–10 个真实想去的地点。总量只有 7 个时：

- 用户没有充分选择空间，结果被种子数据预设；
- 亲子、长辈、情侣、博物馆、城市漫步、夜间等偏好无法形成有意义差异；
- 替换景点缺少候选，不能观察修订体验；
- 多名参与者的结果会高度同质，无法评价系统是否理解真实需求；
- 专家无法充分检验跨区域组织、交通折返、雨天和小众需求；
- H3“比手动安排更合理”的人类证据会受到数据供给不足的严重混淆。

当前 7 点和对应天气只能作为不可变技术回归基线，不作为 G7-R1 的充分研究数据集。2026-08-27 起的历史天气也不能冒充未来参与者旅行日期的天气事实。

## 3. G7-R0.2：杭州研究数据集与地点类型建设

### 3.1 目标

形成一个来源合规、结构完整、人工审核、可被当前或升级后的求解器消费的杭州 M1 研究数据版本。研究数据的目标是覆盖典型旅行决策，不是追求杭州所有 POI 的全量抓取。

### 3.2 地点实体模型前置决策

现有 `attractions` 及求解器 `Attraction` 偏向单坐标、单停留时长的点状景点。“西湖湖滨、北山街、小河直街、九溪十八涧、龙井村、武林夜市”等对象不能在未定义语义时直接伪装为普通点状景点。

R0.2-01 已通过 [`ADR-0018`](../decisions/ADR-0018-place-catalog-and-solver-projection.md) 完成评审，确定以下封闭枚举和投影边界：

| 维度 | 初始枚举 | 用途 |
|---|---|---|
| `place_kind` | `attraction`、`scenic_area`、`neighborhood`、`walking_route`、`market`、`show`、`experience` | 表达用户实际选择的地点/体验性质 |
| `geometry_kind` | `point`、`area`、`route` | 决定坐标、入口和内部游览表示 |
| `category` | 自然、文化、博物馆、宗教、城市漫步、亲子、夜间、购物生活方式等 | 用于筛选、覆盖和推荐，不替代 place kind |
| `access_point_kind` | `visitor_entrance`、`visitor_exit`、`route_start`、`route_end`、`performance_location`、`meeting_point`、`area_representative` | 作为真实 OD 端点并支持多入口区域 |

已接受方案是新增通用 `places` 目录、访问点、几何、来源、revision、地点关系与 `solver_place_projections`，再将已发布地点投影为求解器可消费的 `Attraction`。M1 每个用户可选 Place 最多生成一个 solver 节点；真实 OD 使用 `origin.departure_access_point → destination.arrival_access_point`。R0.2-03 已完成 `place_catalog` 物理模型和 Alembic `0006_place_catalog`，没有把区域语义继续堆入单一 `attractions` 表。R0.2-04 只建立候选清单和覆盖矩阵；R0.2-05 才采集、归一并人工审核地点事实。

区域型地点进入 M1 求解时至少需要：

- 一个审核后的默认到达点；
- 可选的离开点或“同入口返回”规则；
- 建议时长范围，而非伪精确分钟；
- 内部步行预算；
- 适合时段和开放语义；
- 关联子地点或推荐游览段；
- 对用户明确展示“街区/景区/路线/市集/表演”，不能假装为精确单点。

### 3.3 数据来源与合规边界

数据来源由 AI 协作开发方自行检索、筛选、获取、登记和交叉验证，用户不需要提供景点清单、网红区域清单或攻略链接。只有当某个必要来源必须付费购买、签署授权、登录账号或扩大到受限制数据时，才向用户报告并请求新的授权。

来源优先级：

1. 政府、杭州文旅及区县文旅公开信息；
2. 景区、博物馆、场馆和预约平台的官方公开信息；
3. 高德 Web 服务允许使用的 POI、地理编码和路线数据；
4. 有明确许可的开放数据或授权数据源；
5. 多个公开攻略的人工综合与独立领域专家审核。

在单独完成服务条款、版权、用途和速率评审前，不默认执行针对小红书、抖音、大众点评、携程、马蜂窝或微信公众号的批量页面爬取。任何采集器均不得保存：

- 用户昵称、账号、联系方式或可组合识别信息；
- 评论全文、聊天内容或用户画像；
- 未授权图片、视频或整篇文章；
- 登录 Cookie、访问 token、验证码或绕过反爬的凭证；
- 无法说明来源和采集时间的“网红指数”。

社交趋势只作为随时间衰减的软信号，建议结构化为：

```text
trend_score
trend_source_count
trend_observed_at
trend_window
trend_reason_codes
```

它不是开放时间、坐标或闭馆日等硬事实，也不能直接决定一定排入行程。

### 3.4 数据流水线

```text
source registry
→ raw/staging record
→ 实体归一与去重
→ candidate place
→ OM1 审核工作台：坐标/入口审核
→ OM1 审核工作台：开放时间、闭馆日、例外日期审核
→ OM1 审核工作台：时长范围、体力、室内外、适合时段和类型补全
→ OM1 审核工作台：来源冲突与重叠关系裁决
→ ReviewDecision + human_verified
→ OM1 发布中心：数据门禁
→ immutable published research snapshot + AuditEvent
```

Raw/staging、candidate 和 published 必须物理或逻辑隔离。未经审核的数据不能因为数量足够就进入求解器。硬事实变更必须产生 revision；历史行程继续引用原快照。

R0.2-04 候选发现可以使用版本化 JSON/CSV/CLI，不要求先完成可视化管理端；进入 R0.2-05 的批量编辑和人工审核后，不允许通过直接 SQL 修改 `review_status` 或 `published` 状态。管理端只调用应用用例，不能复制或绕过 `place_catalog` 发布门禁。

### 3.5 G7-R1 初始数据就绪门槛

以下数量是 M1 形成性研究的初始工程门槛，不是永久产品真理；R1 之后可按证据调整：

| 维度 | 初始门槛 |
|---|---:|
| human_verified 点状景点 | 40–60 |
| human_verified 区域/路线/市集/表演等非普通点实体 | 10–15 |
| 地理旅行区域 | 至少 8 个 |
| 用户可感知类别 | 至少 8 类 |
| 夜间或固定时段体验 | 至少 8 个 |
| 室内/雨天代表地点 | 至少 5 个 |
| 未裁决重复或来源冲突 | 0 |
| 发布实体必填字段完整率 | 100% |
| 发布实体坐标/入口 human_verified | 100% |
| 时间规则适用实体的可解析率 | 100% |

地理覆盖至少包括：西湖湖滨/北山、灵隐/天竺、西溪、南宋御街/河坊街/吴山、运河/拱宸桥、武林/湖滨商圈、钱江新城、良渚，并尽量纳入湘湖、之江/宋城、龙井/梅家坞/九溪等差异化区域。

场景覆盖至少包括：首次来杭、去过西湖后的差异化需求、亲子、长辈、情侣/朋友、雨天、2/3/4 天、早到/午后到达/末日早离和悠闲/适中/紧凑节奏。

### 3.6 OD 扩容架构门禁

当前 7 点完整有向 OD 只有 `7×6=42` 条；100 点完整有向 OD 会增长为 `100×99=9,900` 条，叠加步行、公交和驾车模式后不能继续无条件采用全城 N² 预计算。

R0.2 在发布扩大后的研究数据前，必须完成 OD 扩容 ADR 和技术验证，目标流程为：

```text
published place facts
→ 按用户输入、时间窗和区域做候选过滤
→ 使用坐标/区域近似成本做候选初筛
→ 对用户实际选择、必要替换候选及到离锚点获取真实高德有向 OD
→ Redis/持久化缓存与配额治理
→ 固化本次求解使用的 OD 子图、来源、版本和 hash
→ 生成可回放 Revision
```

要求：

- 求解关键连接必须使用真实有向路网或明确降级；
- 缺边不得填 0，近似不得冒充高德真实结果；
- 同一 Revision 使用的 OD 子图必须可回放；
- 不为未进入候选集的大量地点浪费外部请求；
- 构建和在线请求都受每日预算、限流、熔断和缓存约束；
- 扩容方案完成前，不将大规模地点目录直接接入现有“完整矩阵必填”的 published Provider。

### 3.7 天气研究口径

G7-R1 先采用固定的未来标准场景日期，生成并锁定相应和风天气快照，以支持专家和参与者之间的可比性。参与者真实日期需求可作为补充形成性场景，但必须使用独立数据快照/环境 manifest，不能把不同天气事实混入同一锁定环境。

R0.2 输出：

- ADR-0018 地点类型、访问点与求解投影决策；
- 数据来源与合规登记；
- 数据模型和发布 Schema 修订；
- 首批候选清单与覆盖矩阵；
- 数据采集/导入/校验工具；
- 数据质量报告；
- OD 按需子图 ADR 与实现；
- 杭州 G7-R1 immutable published research snapshot。

数据获取执行不等待用户逐项确认来源。每批采集必须提交非敏感 source registry、失败/排除清单、采集时间、字段覆盖、冲突和人工审核结果；API Key 仍只从 `.env` 或服务器权限受限环境读取，不进入数据文件、日志和报告。

## 4. G7-R0.3：受控服务器 H5 研究环境

### 4.1 渠道选择

G7-R1 的推荐入口是受邀可访问的移动端 H5，而不是微信小程序正式发布。理由：

- 可以让参与者使用自己的手机；
- 可以验证移动网络、刷新恢复、身份隔离和真实持久化；
- 版本、数据和前端 artifact 可以锁定；
- 不把小程序备案、平台审核、原生分享和内容治理工作混入核心价值形成性测试；
- blocker/major 修复后可以快速生成新批次，而不必重复公开审核。

微信小程序仍是 M1 目标上线形态。体验版可在形成性问题基本关闭后验证微信容器、授权、分享和设备差异；正式上线不是 G7-R1 前置条件，也不能替代目标用户证据。

### 4.2 服务器门禁

在现有授权服务器上完成，禁止在本机安装或启动 MySQL/Redis。全部组件使用 Docker 镜像，并统一由 Docker Compose 管理；完整拓扑和发布门禁见 [`../ops/gate7-controlled-h5-docker-deployment.md`](../ops/gate7-controlled-h5-docker-deployment.md)：

1. 提交并固定应用 commit；
2. 备份服务器 MySQL/Redis；
3. 将数据库从 `0002_anonymous_identity` 按顺序迁移至当前应用及新数据目录要求的 revision；
4. 重新验证 readiness、Planning、Revision、分享、反馈、数据发布和恢复；
5. 构建 API 镜像和包含 H5 production artifact 的 edge 镜像；
6. 配置受控访问域名、HTTPS、反向代理、安全响应头和最小暴露端口；
7. 将 edge、api、migrate、MySQL、Redis 纳入一个逻辑 Compose 项目，不开放公网 8000/3306/6379；
8. 配置邀请范围、研究隐私说明、日志脱敏和原始证据目录；
9. 真实 Google Chrome 完成移动端/桌面回放；
10. 生成状态为 `locked` 的 G7-R1 formative manifest。

如果尚无域名/TLS，只能进行主持人设备上的受控 dry run；不把裸公网 IP 环境直接交给外部参与者长期使用。域名、证书和访问控制方案需要在 R0.3 实施前单独确认。

### 4.3 不等同于正式生产发布

受控研究环境可以限制为杭州、受邀样本和固定研究期。它不代表：

- 微信小程序已通过正式审核；
- 已具备大规模公网流量能力；
- H11 分享获客已可评价；
- 多城市、登录、支付或 UGC 已上线；
- 集中监控、跨故障域备份和长期 SLO 已全部完成。

R0.3 输出：

- 受控 H5 地址和访问规则；
- 服务器迁移、部署、备份与恢复报告；
- published 数据版本和 artifact hash；
- Chrome 研究路径回放报告；
- 首个 `locked` formative environment manifest。

## 5. G7-R0.4：内部 dry run

参与者只能是团队成员、开发协作者或专门的内部测试人员，必须标记 `role=internal` 或 `synthetic_fixture=true`，不得进入 H3/H6/H7 目标用户分母。

至少验证：

- T01–T10 任务从受控地址可以完整执行；
- 40–75 个地点下选择、替换、生成和未排入解释仍可理解；
- 区域/路线类地点在 UI、OD 和时间线上没有伪精确或类型混淆；
- 固定标准场景和天气快照一致；
- 多个匿名参与者数据相互隔离；
- manifest、evidence、aggregate report 可端到端生成；
- blocker 会暂停批次，major 有明确修复队列；
- 页面和报告不泄露 token、联系方式、原始评论或完整连接串；
- 375×812 和至少一个常见 Android 尺寸可用；
- 完整刷新、弱网和受控后端失败有稳定恢复路径。

R0.4 退出条件：

- 开放 blocker 为 0；
- 影响核心任务的已知 major 为 0；
- 数据发布门禁和完整回放通过；
- 研究主持脚本不再变化；
- `locked` manifest 在首名外部参与者开始前生成；
- 招募名单、知情说明和退出机制准备完成。

## 6. 实现优先级

P0/P1/P2 只表示当前 M1/G7 前置实现优先级，不表示产品里程碑，也不表示研究问题严重度。

| 优先级 | 工作 |
|---|---|
| P0 | 地点类型 ADR、来源合规边界、通用地点目录/求解投影设计、OM1 管理身份/API/审计和审核工作台、40–60 点状地点 + 10–15 区域类实体、人工审核、published 数据门禁、OD 按需子图、服务器迁移与 user-H5/admin-web/HTTPS 部署、locked manifest、内部 dry run |
| P1 | 趋势软信号、多入口优化、审核任务分配/质量看板/双人复核、小程序体验版、弱网/多设备扩展 |
| P2 | 自动化趋势刷新、更大杭州长尾目录、多渠道趋势融合、公开小程序发布后的规模化运营能力 |

研究问题严重度继续使用 `blocker/major/minor/observation`，不得用 P0/P1/P2 记录专家或用户问题。

## 7. 执行任务顺序

