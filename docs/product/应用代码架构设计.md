# M1 用户端与 OM1 管理端应用代码架构设计

- 文档版本：V1.4
- 日期：2026-08-29
- 产品里程碑：M1
- 管理侧里程碑：OM1（身份/API/RBAC/审计后端底座已实现；管理 Web 与地点审核仍待实现）
- 设计阶段：A4
- 上游输入：功能模块设计 V3.5、管理端功能模块设计 V1.0、信息架构与 UI V1.4、交互流程与状态机 V1.4、ADR-0005、ADR-0009、ADR-0018、ADR-0019、M1 求解器契约
- 目标：让阶段性完成的求解器形成稳定用户闭环，并让地点审核/发布通过独立管理产品面调用同一领域门禁；保留 Execution、Journal、Sharing、Community 的正确扩展边界

## 1. 架构结论

M1 采用：

```text
Taro + React 前端
        ↓ HTTP/JSON
FastAPI 模块化单体
        ↓ 应用端口
SQLAlchemy / 数据快照 / 求解器适配器 / 日志审计
        ↓
MySQL（生产）/ 测试数据库 + 版本化杭州快照
```

核心决策：

1. 后端采用模块化单体，不按功能域提前拆微服务；
2. 领域和应用层不依赖 FastAPI、SQLAlchemy、Celery、Redis 或具体 Provider；
3. 当前 `travel_agent.solver` 保持纯求解内核，由应用适配器调用；
4. 首个纵向切片允许进程内同步执行，通过 `GenerationExecutor` 端口保留异步替换能力；
5. M1 已实现 Planning、Catalog/PlaceCatalog、Identity、Sharing、Feedback、Observability 的必要部分；OM1 将追加 Governance 管理身份/审核/审计边界，Execution、Journal、Community 仍只保留后续边界，不创建空服务和空表；
6. 行程生成必须以 `generation_intent_id`、输入快照和版本化结果实现幂等，不使用含义模糊的 `regenerate`；
7. 求解结果、应用实体、HTTP DTO 和 ORM 模型四者分离，禁止相互泄漏；
8. 运行日志、求解决策审计和业务数据分开保存，遵守 ADR-0005；
9. M1 不把 LLM 放在生成成功的硬依赖路径；解释文案可模板化，未来经端口增强；
10. 架构只预留真实需求证据支持的扩展点，不提前引入微服务、Kafka、事件溯源或通用规则引擎。

> **Gate 7 增量边界**：R0.2-03 已完成 ADR-0018 的通用 PlaceCatalog、12 张 SQLAlchemy 表、Alembic 0006 和 staging/published 发布门禁；按需 OD 子图仍属于 R0.2-06。ADR-0019 新增的 Governance、admin HTTP、审核任务、发布批次和管理审计目前只有设计，须由 R0.2-05 后续迁移追加，不能描述为已实现。

## 2. 架构目标与非目标

### 2.1 目标

- 支撑匿名用户三步创建、生成、查看、保存和恢复行程；
- 稳定适配当前 `solver-p1-v2 / trip-result-v2`，并保留 `solver-p1-v1 / trip-result-v1` 历史 Revision 回放；应用层不依赖求解器内部实现细节；
- 支持完整成功、部分成功、软降级、无解、无效输入和内部错误分流；
- 保存 Trip、TripRevision、GenerationIntent、SolverRun 的可追溯关系；
- 保证双击、网络重试和刷新恢复不会重复生成或改变结果；
- 允许未来把进程内执行替换成 Celery worker，而不改变用例或 API 状态语义；
- 允许 A5 继续定义 API、数据库实体、错误码和迁移；
- 允许 A6 按单个纵向切片实现，而不先建设全部后台能力。

### 2.2 非目标

- 不在 A4 实现 FastAPI、SQLAlchemy、Taro 页面或数据库迁移；
- 不重新设计求解算法；
- 不实现 M2 小记、M3 社区或 M4 自动游记；
- 不把未来功能提前拆成独立部署服务；
- 不承诺 Celery、Redis、微信登录、真实在线 Provider 进入首个切片；
- 不在应用层复制 C1–C6 或重新排序求解结果；
- 不使用 LLM 生成开放时间、交通耗时、计划时间或未排入机器码。

## 4. 后端架构

### 4.1 分层与依赖方向

```text
interfaces/http
       ↓
application
       ↓
domain
       ↑
infrastructure
```

具体含义：

| 层 | 职责 | 可以依赖 | 禁止依赖 |
|---|---|---|---|
| `domain` | 业务实体、值对象、状态转换、仓储/端口协议 | Python 标准库、领域内部 | FastAPI、Pydantic HTTP DTO、SQLAlchemy、Celery、Redis、solver 具体模型 |
| `application` | 用例编排、权限、事务、幂等、端口调用、错误映射 | domain、应用端口 | ORM Session 细节、FastAPI Request、直接文件写入 |
| `interfaces` | HTTP DTO、认证上下文、路由、状态码和响应映射 | application、接口 DTO | 直接查询 ORM、直接调用 solver、实现业务事务 |
| `infrastructure` | ORM、仓储、Provider、solver adapter、日志、审计、任务执行 | domain/application 端口、外部库 | 反向让 domain 导入 infrastructure |

依赖通过组合根装配，不在模块 import 时创建数据库连接、日志文件或网络客户端。

## 5. 核心领域对象

### 5.1 M1 聚合与身份

| 对象 | 类型 | 职责和不变量 |
|---|---|---|
| `TripDraft` | 聚合根 | 保存用户当前输入、选择和确认状态；每次有效编辑增加 `draft_version` |
| `Trip` | 聚合根 | 表示用户可访问的一次旅行计划容器；不直接承载全部可变输入 |
| `TripRevision` | 实体/不可变快照 | 保存一次提交生成的输入快照和结构化结果引用；新修改产生新 revision |
| `GenerationIntent` | 聚合根或事务实体 | 以 `generation_intent_id` 表示一次用户生成意图，管理幂等和执行状态 |
| `SolverRun` | 审计记录 | 保存求解版本、输入哈希、数据版本、结果计数和决策证据；不作为用户编辑对象 |
| `AnonymousPrincipal` | 身份值对象 | 标识匿名访问主体，不把原始 token 写日志或业务审计 |
| `PlanShare` | 聚合根/不可变公开快照 | 绑定原作者、Trip 和 Revision；保存 token 摘要、`plan-share-v1` 脱敏快照与内容哈希；不承载实际旅程回顾 |

### 5.2 关系

```text
TripDraft ── submit snapshot ──→ GenerationIntent
                                      │
                                      ├── creates/uses → Trip
                                      ├── creates      → TripRevision
                                      └── invokes      → SolverRun

Trip 1 ─── * TripRevision
TripRevision 1 ─── 1 GenerationIntent
TripRevision 1 ─── 1 structured result snapshot
```

### 5.3 关键不变量

- 一个 `generation_intent_id` 只能对应一个规范化输入快照哈希；
- 相同 intent 重试不得绑定不同输入；若输入已改变，必须生成新 intent；
- TripRevision 创建后不可原地覆盖；
- 查看历史 revision 不触发重新求解；
- 当前 revision 只是 Trip 的指针，切换指针不能删除历史；
- 只有质量门通过的结果可以成为可展示成功 revision；
- 部分成功和软降级仍可成为成功 revision，但必须保留未排入和降级；
- 硬门失败、无效输入或内部错误不能伪装成空行程；
- SolverRun 审计必须引用 contract/constraint/parameter/data 版本。

### 6.3 `SubmitGeneration` 与 `ExecuteGeneration` 分离

```text
HTTP SubmitGeneration
1. 校验身份和 draft_version
2. 规范化输入并计算 snapshot_hash
3. 按 generation_intent_id 查重
4. 新 intent：保存 queued + input snapshot
5. 提交 executor
6. 返回可查询状态

Executor ExecuteGeneration
1. 原子领取 queued intent → running
2. 在短事务外加载/构造不可变求解输入
3. 调用 SolverGateway
4. 计算质量、降级和审计
5. 开启短事务保存 SolverRun + TripRevision + completed
6. 异常映射为结构化 failed；允许同 intent 稳定重试
```

求解期间禁止持有数据库事务或行锁。否则 OR-Tools 时间和未来 Provider 延迟会扩大锁范围。

## 7. 求解器适配边界

### 7.1 端口

应用层只依赖：

```text
SolverGateway.solve(SolverRequest) -> SolverOutcome
```

`SolverRequest` 和 `SolverOutcome` 是应用 DTO，不是 HTTP Schema，也不是 `travel_agent.solver.models`。

### 7.2 适配器职责

```text
Application SolverRequest
→ 校验数据快照一致性
→ Catalog/Provider 数据装配
→ data_verified 门禁
→ 合并时段偏好 user > curated > public_guide_synthesis
→ 转换为 SolverInputBatch / Step1Plan / provider
→ 调用 assign_days / route_itinerary / quality / degradation
→ build_solver_run_audit（纯转换）
→ 映射为 Application SolverOutcome
```

适配器必须：

- 固定使用并返回 `DEFAULT_SOLVER_P1_CONTRACT` 三个版本；
- 将 Python 异常映射成内部技术错误，不把异常文本作为用户文案；
- 保留搜索状态、拒绝码、未排入、数据拒绝、降级和质量报告；
- 保证景点守恒和硬质量门在保存成功结果前再次确认；
- 不在求解器内部写数据库或文件日志；
- 不让 HTTP/ORM 对象进入纯内核；
- 不让前端重新计算时间、交通或约束。

### 7.3 兼容性保护

- 适配器契约测试引用 `solver-p1-contract.json`；
- 求解器版本变化由 adapter 显式支持，不覆盖历史结果；
- 历史 TripRevision 保存其使用的契约版本；
- 新增兼容输出字段可以通过应用 DTO 版本追加；
- 破坏性变化按 ADR-0009 升级版本并运行 Gate 6。

## 8. 持久化与事务架构

### 8.1 A5 最低实体集合

A5 应至少设计：

```text
anonymous_principals / users（可分阶段）
trip_drafts
trip_draft_attractions 或版本化 selection snapshot
trips
trip_revisions
generation_intents
solver_runs
feedbacks（P1）
attractions / time rules / published data versions
```

不建议继续只用：

```text
trips.itinerary JSON + status
```

原因是它无法可靠表达草稿版本、重复生成意图、多个 revision、当前 revision、失败执行和回放关系。

求解器完整结果可以在 M1 保存为不可变 JSON snapshot，以降低关系化成本；但 Trip、Revision、Intent、状态、版本和查询索引应结构化存储。节点级查询进入实际需求后再评估拆表，不为理论纯度提前过度规范化。

### 8.2 Unit of Work

应用用例通过 `UnitOfWork` 协调仓储：

```text
with uow:
    aggregate = repository.get(...)
    aggregate.transition(...)
    repository.save(aggregate)
    uow.commit()
```

规则：

- HTTP 层不能直接 commit；
- 仓储不能自行决定跨聚合事务；
- 外部网络和 OR-Tools 调用不放在长事务内；
- 提交执行前事务只保存 intent；执行完成事务保存 run、revision 和 intent 完成状态；
- 审计与业务结果必须同一完成事务成功，或采用可恢复 outbox；M1 单库优先同事务，不先引入消息系统。

### 8.3 并发控制

- `TripDraft` 使用 `draft_version` 乐观锁；旧版本更新返回 `draft_version_conflict`；
- `GenerationIntent` 对 `generation_intent_id` 建唯一约束；
- intent 同时记录 `input_snapshot_hash`，相同 ID 不同哈希返回幂等冲突；
- 执行领取使用条件更新 `queued/retryable_failed → running`，避免两个 worker 同时求解；
- TripRevision 使用 `(trip_id, revision_no)` 唯一约束；
- 反馈、分享等后续写用例分别定义自己的幂等键，不复用 generation intent。

## 9. 生成状态与错误架构

### 9.1 应用生成状态

应用层状态不能直接等同于 solver 搜索状态：

```text
draft
queued
running
completed
failed_retryable
failed_terminal
```

完成结果使用两个正交维度：

```text
completion_kind = complete_success | partial_success
has_soft_degradation = true | false
```

因此“部分成功且晚餐缩短”可以同时准确表达，不需要增加组合枚举。

solver 搜索状态继续保存为证据：

```text
empty / completed / best_so_far /
time_limit_no_solution / no_solution / invalid
```

### 9.2 错误分层

| 层级 | 示例 | HTTP/页面处理 |
|---|---|---|
| 字段错误 | 日期格式、缺少交通确认 | 400/422，就地定位字段 |
| 业务冲突 | draft version 过期、intent 哈希冲突 | 409，恢复最新状态或创建新 intent |
| 数据门禁 | 景点未验证、OD 缺失、版本不一致 | 结构化不可生成，回到景点/数据说明 |
| 业务无解 | C1/C2/C4/C5/C6 下无方案 | 返回可操作原因，不当系统异常 |
| 软降级 | 时长、体力、晚餐、时段偏好 | 成功结果中的 notice |
| 外部暂时失败 | Provider 超时、worker 暂时失败 | 可稳定重试，沿用 intent 和 seed |
| 内部错误 | 未预期异常 | 通用错误 + request ID，详细信息只进 error 日志 |

机器错误码与用户文案分离；接口不返回堆栈、数据库错误或 Python 异常文本。

## 11. 日志、审计与安全

### 11.1 运行日志

应用入口显式初始化：

```text

logs/api/info/YYYY-MM-DD.log
logs/api/error/YYYY-MM-DD.log
```

worker 启用后使用 `worker` 模块；不按实例/PID 拆目录。每月按 ADR-0005 压缩归档。

HTTP 中间件生成/透传 `request_id`；生成链路同时关联：

```text

generation_intent_id
trip_id
revision_id
solve_run_id
```

### 11.2 审计

| 审计 | 保存内容 | 保存位置 |
|---|---|---|
| 生成审计 | 版本、输入哈希、计数、状态、决策事件 | `solver_runs` 及必要子结构 |
| 草稿/修订审计 | 谁在何时基于哪个版本提交 | 业务表版本字段/审计记录 |
| 数据发布审计 | 来源、验证、冲突裁决和发布版本 | 数据 revision/publish 表 |
| 管理操作审计 | actor/role/action/target、前后 digest、理由和结果 | 追加式 `admin_audit_events`；不随文件日志清理 |
| 访问日志 | 路径、状态码、耗时、关联 ID | 文件日志，不保存 token/自由文本 |

### 11.3 安全边界

- 匿名访问 token 只保存不可逆摘要，原值只返回客户端一次；
- token、Cookie、openid 原值、私人交通细节和自由文本不进日志；
- 分享 token 与匿名所有权 token 分离；
- 所有 Trip/Draft/Intent 查询先做主体权限校验；
- 数据删除和审计匿名化边界在 A5 明确；
- 用户端仍不需要复杂 RBAC；OM1 管理端必须有最小服务端 RBAC，运营数据发布和普通用户接口使用不同认证上下文。

## 17. 技术难点与解决方案

| 难点 | 风险 | M1 方案 | 升级触发条件 |
|---|---|---|---|
| 求解耗时与请求超时 | HTTP 阻塞、重复提交 | intent 幂等 + Executor 端口；首切片 inline 受控，页面查询状态 | P95 或并发证据表明 inline 不足时启用 Celery |
| 结果可回放 | 数据/参数变化导致历史漂移 | 不可变 input/result snapshot + 完整版本键 | 存储体积或查询需求明显增长时拆事件/节点表 |
| 数据版本一致性 | 景点、OD、天气混用版本 | PublishedDataSnapshot 一次装配并保存版本 | 在线 Provider 上线时增加快照发布流程 |
| 双击与网络重发 | 重复 Trip/求解成本 | intent 唯一键 + snapshot hash + 原子领取 | 多 worker 时保持相同数据库约束 |
| 跨端草稿恢复 | H5/小程序退出导致丢数据 | 服务端 draft + 本地缓存 + version 冲突恢复 | 登录同步上线时增加主体合并策略 |
| ORM 与领域耦合 | 后续修改困难 | 显式 mapper/repository，不使用 Active Record | 若映射成本明显超过收益再评审简化 |
| M2–M4 扩展 | 把实际状态/内容塞入 Trip JSON | 现在分清 Planning 与未来模块边界，不建空表 | 进入相应里程碑时详细建模 |
| 日志多进程归档 | 文件交错或归档误删 | 复用 ADR-0005 实现和锁 | 多机部署或锁等待显著时接集中日志 |

## 17.1 ADR-0010 架构增量

新增或明确以下端口和边界：

```text
GaodeTravelTimeMatrixProvider
  → 多模式真实有向 OD
  → POI ID、路线点语义、入口坐标、道路距离、耗时、travel_mode、basis、version、fetched_at

JsonPublishedSolverDataProvider
  → published-solver-data-v1 不可变 JSON
  → SHA-256、candidate/published、human_verified、真实天气来源、完整有向 OD 门禁
  → 正式 MySQL Provider 上线前的离线发布适配器

ApproximateTravelTimeProvider
  → 仅 local fixture / transparent fallback

MealPlaceCatalog
  → 餐厅候选、营业规则、排队/预约依据

Planning application
  → AddMealPlaceToDraft
  → SubmitMealReplan
  → 新 GenerationIntent / 新 TripRevision
```

求解器内部职责：

- `routing.py` 继续负责硬可行顺序和 C2/C4/C6；
- `schedule_refinement.py` 负责不改变顺序的建议时长扩展、午餐空档和 DAY_SPREAD；
- `segments.py` 负责日间/晚间合并及晚餐软块；
- 餐厅节点进入求解模型后与景点共享时间窗和 OD 校验，但使用独立节点类型和业务字段；
- Provider 结果先形成版本化 PublishedDataSnapshot，再进入求解；求解器不直接发高德 HTTP 请求。

高德 Provider 必须实现缓存键、超时、请求节流、限流分类、熔断和结构化降级。缓存键至少包括起终入口、交通模式、策略、Provider 版本和时间桶。调用失败不得将 0 或直线距离静默写成真实 OD。Provider HTTP 只发生在 OD 快照构建阶段；求解阶段读取 `InMemoryTravelTimeProvider` 或等价持久化快照。当前结果契约由 ADR-0011 升级到 `solver-p1-v2 / trip-result-v2`，新增真实交通模式、道路距离和透明降级原因；ADR-0012 引入 OD 感知聚类和晚间终端成本；ADR-0013 将软目标升级为 `constraints-p1-v4 / parameters-p1-2026-08-26`，在保护强近邻的同时平衡每日景点数量和建议游览负载；ADR-0015 进一步将单日间节点与固定晚间段的下午展开版本化为 `constraints-p1-v5`，参数版本保持不变。

路线坐标不能以裸 `lat/lng` 发布。正式数据至少保存高德 POI ID、`routing_point_kind`、来源、抓取时间和审核状态；大型/多门景区与开放街区必须保留点位语义。JSON Provider 默认拒绝 candidate，正式 published 强制 `human_verified`，并校验内容哈希、版本、ID 唯一性、天气来源和完整 `N×(N−1)` 有向 OD。正式天气至少保存 `basis/severity/condition/condition_code/source_ref/fetched_at`；审计 fixture 不得进入 published。和风三日 forecast 只在发布前构建阶段联网，求解过程不访问第三方天气；三日之外必须使用正式 climate 基线或拒绝覆盖，不补造晴天。正式 MySQL PublishedDataProvider 后续复用同一门禁语义；V1/V2/V3 历史 Revision 仅用于不可变回放，不原地重算。

生产 HTTP 组合根使用 `ProductionHttpSettings` 显式绑定数据库、快照根目录、M1 城市和发布版本。`build_production_http_app()` 在创建 FastAPI 应用时先加载指定 JSON 快照并核对城市，任何 candidate、未审核坐标、审计天气、缺少天气来源或内容错误均 fail-fast；生产入口不暴露 `allow_candidates`。`build_local_dev_app()` 继续使用明确标注的本地 fixture，两类入口物理分离，避免开发近似数据误进入生产。正式 MySQL 发布表上线后替换 Provider 实现，不改变应用层 `PublishedSolverDataProvider` 端口、GenerationIntent 或历史 Revision 语义。

餐厅重排事务继续沿用 GenerationIntent：外部 Provider 调用和求解不放在数据库长事务中；完成事务原子写入 SolverRun、新 TripRevision 和 Intent 完成状态。历史 Revision 及其版本键不变。

## 17.2 A6-9.3 Sharing 实现增量

当前 Sharing 纵向切片使用独立边界：

```text
domain/sharing
  → PlanShare、PlanShareRepository
application/sharing
  → CreatePlanShare、GetPublishedPlanShare、CopyPlanShareToDraft
infrastructure/sharing
  → HmacPlanShareTokenCodec
infrastructure/database/sharing
  → SQLAlchemy plan_shares 仓储
interfaces/http
  → 作者创建、公开读取、访客复制三个端点
frontend/features/plan-share + pages/plan-share-*
  → simple 模板、作者预览、公开落地页和参考复制
```

安全与可靠性规则：

- `PlanShare` 保存创建时生成的 `plan-share-v1/planned_itinerary` 快照，不在公开 GET 时回查并动态重算 Revision；
- 公开 token 采用 `ps1.<plan_share_id>.<HMAC-SHA256>`，数据库只保存 SHA-256 摘要；生产组合根要求独立的 `TRAVEL_AGENT_PLAN_SHARE_TOKEN_SECRET`，少于 32 字节 fail-fast；
- 分享 intent 负责作者创建幂等；同一 intent 的 Trip/Revision/模板不一致时抛出 `plan_share_intent_conflict`；
- 公开 DTO 是白名单投影，不暴露 access token、主体、Trip/Revision、内部 node/attraction ID、坐标、OD、私人交通或笔记；
- 访客复制由服务端重新创建归属于访客的 `TripDraft`；景点集合读取该 Revision 对应 GenerationIntent 的不可变 `input_snapshot`，不得读取可能继续编辑的源草稿当前值，只复用城市和景点集合；
- `SqlAlchemyUnitOfWork` 和 `InMemoryPlanningStore` 都暴露 `plan_shares` 仓储，应用处理器不依赖 ORM；
- Alembic head 已升级为 `0004_plan_shares`，readiness 同步检查该版本；服务器真实 MySQL 仍需在下次发布前从 0002 依次升级 0003、0004；
- 当前不引入图片 renderer、对象存储、二维码库或平台 SDK；产生真实需求和转化证据后在 A6-9.3.1 增加，不改变 `PlanShare` 与 M2 回顾资源的隔离边界。

## 17.3 A6-9.4 Feedback 实现增量

结构化反馈使用独立领域边界，不写回 TripRevision，也不复用 M3 Community 景点评分/评论：

```text
domain/feedback
  → Feedback、载荷规则、FeedbackRepository
application/feedback
  → SubmitTripFeedback、SubmitNodeFeedback、归属/节点校验和去重
infrastructure/memory + infrastructure/database/feedback
  → 内存与 SQLAlchemy 仓储
interfaces/http
  → Revision 整体反馈、Revision 节点反馈两个端点
frontend/features/feedback
  → TripFeedbackPanel、NodeFeedbackControl
```

可靠性与边界规则：

- `Feedback` 只表达 `trip | node` 两种安排质量反馈；原因枚举、合理评价不能携带问题、like/dislike 原因方向和 500 字限制由领域规则统一校验；
- 应用层在查询已有目标前先执行同一领域载荷校验，避免非法直接调用被目标去重分支吞掉；
- `feedback_intent_id` 唯一约束保证同一网络意图幂等；同 intent 不同载荷稳定返回 `feedback_intent_conflict`；
- `(principal_id, revision_id, target_key)` 唯一约束保证同一主体/Revision/整体或节点目标只保留首份；首版没有编辑反馈用例；
- 节点归属从该 Revision 的不可变 `result_snapshot` 校验，不能从当前 Revision 或可变草稿推断；
- `SqlAlchemyUnitOfWork` 和 `InMemoryPlanningStore` 都暴露 `feedbacks` 仓储，处理器不依赖 ORM；
- Alembic head/readiness 已升级为 `0007_admin_identity_audit`；服务器真实 MySQL 仍在 0002，正式应用发布前按 0003→0004→0005→0006→0007 顺序迁移；
- 前端同一规范化 payload 的失败重试沿用 intent；成功和目标去重都转为只读成功态。首版只在当前 Revision 展示入口，历史 Revision API 能力保留但 UI 不开放；
- 反馈不触发自动重求解，不成为公开评论，也不混入未来小记、旅程回顾或自动游记资源。
