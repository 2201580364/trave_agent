# 产品功能完整性审查与追踪矩阵

- 文档版本：V1.0
- 审查日期：2026-08-24
- 审查范围：产品全景、功能模块、信息架构/UI、交互流程、技术选型、假设登记、当前 Accepted ADR 与规格
- 审查原因：发现景点讨论区、节点旅行小记和行后回顾分享未被当前功能树完整建模
- 结论：M1 主闭环覆盖较完整；原 V2.2 功能树是 M1 中心化设计，对 M2–M4 仅做路线登记，不能作为全产品功能架构。功能模块设计 V3.0 已补齐跨里程碑骨架。

## 1. 判定规则

| 状态 | 含义 |
|---|---|
| 完整建模 | 已进入一级/二级/三级功能树，并有边界或验收口径 |
| 部分建模 | 有相近功能或路线登记，但粒度、状态、权限或内容生命周期不完整 |
| 原先遗漏 | 仅存在于产品全景文档，没有可追踪功能点 |
| 本次细化 | 用户本次明确了比旧文档更具体、应作为后续设计依据的业务语义 |
| 规格冲突 | 历史产品描述与 Accepted ADR、当前规格或路线表不一致，不能直接进入实现 |

权威顺序：最新 Accepted ADR → 当前 Accepted 规格 → 领域/数据模型 → assumptions → 历史产品文档。历史路线描述不得覆盖已接受的约束语义。

## 2. 用户本次提出的两项缺口

### 2.1 景点评论区

旧产品文档明确将“景点评分系统 + 景点讨论区”放在 M3，但功能模块 V2.2 只在 `2.3.4 查看深度信息卡` 中概括了“评论、评分”，没有讨论发布、排序、点赞、举报、审核、反垃圾和内容状态，因此属于**原先遗漏**，不是被取消。

V3.0 已新增一级功能域 12：

```text
景点评分、讨论与内容治理
├── 景点评分与上下文评分
├── Tips / 时效信息 / 避坑讨论
├── 最新 / 最有用排序、点赞与置顶
└── 举报、人工审核、自动审核与反垃圾
```

产品用词建议采用“景点讨论区”，因为原定位是高信息密度的轻量留言板，而不是长篇消费评价流；“评论”可作为用户口语和内容实体的通用称呼。

### 2.2 节点旅行小记和整体回顾分享

旧产品文档将旅行小记放在 M2，但只定义“按日期绑定”。用户本次明确：行程开始后，应能在所生成行程的具体景点/活动卡片下保存照片和文字；行程结束后，可选择部分节点小记形成整体行程分享。

该需求被正式细化为：

```text
Trip
└── Trip Revision（开始行程时依据的计划版本）
    └── Trip Day
        └── Itinerary Node / Visit（优先绑定）
            └── Travel Note
                └── Note Media

无法绑定节点的记录 → 回退绑定 Trip Day
```

同时分离三个内容对象：

| 内容对象 | 里程碑 | 事实语义 | 默认隐私 |
|---|---|---|---|
| 计划分享 | M1 | 分享“准备怎么走” | 由用户主动生成 |
| 旅程回顾分享 | M2 | 分享“实际上怎么走、看到了什么”以及选中的小记 | 草稿私密，发布前逐项确认 |
| 自动图文游记 | M4 | 在授权素材范围内由系统辅助编排完整故事 | 生成稿私密，用户编辑确认后发布 |

V3.0 已新增一级功能域 10、11、13，补齐行程开始/结束、节点状态、小记媒体、隐私授权、回顾生成和自动游记边界。

## 4. 跨功能能力缺口

这些能力不一定在全景表中占一列，但缺失会使上述功能无法安全实现：

| 能力 | 原问题 | 处理 |
|---|---|---|
| 计划状态与实际状态分离 | 生成结果无法表达用户是否真的到访 | 10.1–10.2 |
| 内容可见范围 | 小记“默认私密”没有可执行状态 | 11.3、13.4 |
| 内容复用授权 | 小记分享到讨论区/游记可能越权公开 | 11.3、13.4.3 |
| 内容删除与派生关系 | 删除小记后讨论区、回顾、游记如何处理未定义 | 11.1.3、13.4 |
| 媒体生命周期 | 只有“最多 9 张”，没有上传失败、压缩、顺序和隐私 | 11.2 |
| 分享隐私脱敏 | 计划分享可能泄露私人交通或位置 | 13.4.1，并继续适用 9.5 |
| 社区治理 | 讨论区只有人工审核一句话 | 12.4 |
| 节点级反馈 | 产品要求每项 👍/👎，功能树只做整体反馈 | 应在 6.3 补充节点反馈，与评分系统分开 |
| 实际轨迹授权 | 行程回放需要真实数据，但权限边界缺失 | 10.5；默认手动确认，自动采集另行授权 |

## 5. 文档内部冲突与处理建议

| 冲突 | 当前判定 |
|---|---|
| 旧“3/5/8 星日体力预算”与 ADR-0004 冲突 | 以 ADR-0004 为准：体力是分天均衡和节奏提示的软约束；旧表仅为历史假设，后续应改写 |
| 产品附录部分假设里程碑与路线图不一致 | 以当前路线图和 assumptions 为准，不把 H8–H12 误算成 M1 已完成范围 |
| 产品文档仍出现 Phase、旧 P1/P2 阶段用语 | 后续术语清理；产品路线只用 M1–M4，P0–P2 只表示实现优先级 |
| M1“室内替代建议”与当前实现能力不一致 | M1 只能提供如实标注的策展候选/换景点入口；自动验证并连锁重排的 Plan B 归 M3 |
| “行程分享卡片”同时可能指计划和回顾 | 已分为计划分享、旅程回顾分享、自动图文游记三类 |

## 6. 对当前推进流程的影响

- A4 应用代码架构暂缓一轮是必要的，因为新增的 `TripExecution/Visit/TravelNote/Media/ContentGrant` 边界会直接影响领域模型和数据库设计；
- 本次审查不把 M2–M4 塞入 M1 首个纵向切片，M1 范围保持稳定；
- A2/A3 的 M1 页面和流程仍有效，但需要登记 M2–M4 页面与流程扩展入口；
- 恢复 A4 时，应先把“计划行程”和“实际旅程内容”分成不同聚合边界，避免以后用 `trip_node` 一张表同时承载计划、签到、小记、评论和分享。

## 7. 审查结论

1. 用户指出的两项缺口成立；它们是功能架构遗漏，不是产品范围取消。
2. V3.0 已将全产品从 9 个 M1 中心功能域扩展为 14 个跨里程碑功能域。
3. 旅行小记采用“节点优先、日期回退”，计划修订与实际记录分离。
4. 计划分享、旅程回顾分享、自动游记是三个独立内容对象和权限流程。
5. 景点讨论区必须与评分、互动、举报、审核和反垃圾一起设计，不能只增加一个评论列表页面。
6. A2/A3 的后续页面、行程三模式、IF-13–IF-24 和核心状态边界已同步完成；下一步进入 A4 应用代码架构设计。
