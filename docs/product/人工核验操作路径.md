# 人工核验操作路径

- 文档版本：V1.0
- 日期：2026-09-01
- 适用范围：OM1 地点数据治理、Revision 审核与研究快照发布
- 当前节点：G7-R0.2-07 真实研究目录准备（单条人工核验发布已验证，待数据隔离与批量审核）
- 关联文档：[管理端功能模块设计](管理端功能模块设计.md)、[交互流程与状态机设计](交互流程与状态机设计.md)、[API 契约](../specs/api-contract.md)

## 1. 这条流程解决什么问题

人工核验的目标是把一个有来源但可能不完整、可能冲突的 candidate Revision，转化为能够被求解器安全使用、并最终进入研究快照的地点数据。流程必须可追溯、可重做、可审计，不能通过直接改数据库状态跳过审核。

本手册描述的是管理端的实际操作顺序，不是理想化的“点击一次即可发布”流程。`送审`、`逐项证据核验`、`Revision 级通过`、`准备求解投影` 和 `发布检查` 是五个不同动作，任何一个动作成功都不代表后续动作已经完成。

### 几何证据填写规则（面向业务审核员）

几何证据不要求审核员直接编写 JSON。新增或编辑几何时，先选择几何类型，再按页面字段填写：点状地点填写一组经度和纬度；区域填写边界坐标点（每行“经度, 纬度”，至少 3 个点，系统自动闭合）；路线填写轨迹坐标点（每行“经度, 纬度”，至少 2 个点，按行进顺序）。系统会根据这些字段自动生成标准 GeoJSON，并校验经纬度范围、坐标数量和坐标顺序。几何证据列表用点位坐标、边界点数或轨迹点数等中文摘要展示，避免审核员阅读技术对象。

编辑已有几何时，系统会自动把可识别的点、区域或路线坐标拆解回表单；原始图形数据仅在“查看原始图形数据（仅供追溯）”折叠区中只读展示，不作为人工录入入口。来源记录仍通过当前地点有效来源下拉选择，审核员不需要填写内部来源编号。

## 2. 角色边界

| 角色 | 可以做什么 | 明确不能做什么 |
|---|---|---|
| `data_editor` 数据编辑者 | 创建候选、从基线创建新 Revision、编辑 candidate 事实和证据、处理来源冲突与关系裁决、送审 | 审核证据、通过 Revision、准备/发布 Projection |
| `data_reviewer` 数据审核人 | 查看审核队列、查看基线差异、逐项通过/驳回证据、Revision 级通过或退回修改 | 编辑候选事实、绕过来源/关系/证据门禁、发布 |
| `data_publisher` 数据发布人 | 查看发布门禁、准备 candidate Projection、预览和执行发布批次、生成研究快照、退役 | 编辑或审核事实；不得把未通过审核的 Revision 直接发布 |
| `research_viewer` 研究查看者 | 查看候选覆盖、审核结果、发布批次和研究快照 | 修改、审核、发布 |

团队只有一个人时，也必须按动作权限和系统门禁执行；不能因为同一个人兼任角色而减少步骤。所有写入均由服务端 RBAC、版本号和审计约束。

## 3. 两套状态必须分开看

### 3.1 Revision 生命周期

```text
candidate → human_verified → published → retired
```

`candidate` 表示可编辑但不能作为已核验数据使用；`human_verified` 表示 Revision 级审核已经通过；`published` 表示其 Projection 已通过发布门并进入当前或历史快照。

### 3.2 审核任务状态

```text
draft
  → ready_for_review
  → in_review
      ├── request_changes → changes_requested
      │                         └── 编辑后重新送审 → ready_for_review
      ├── approve → approved → closed
      └── cancel  → closed
```

审核任务状态不写入 Revision 生命周期。任务处于 `in_review` 不等于 Revision 已进入 `human_verified`；只有 reviewer 的 Revision 级 `approve` 事务成功后，二者才分别变为 `approved/closed` 和 `human_verified`。

## 4. 一条完整可执行路径

### 4.1 登录并定位候选

1. 进入管理端并使用管理员会话登录。
2. 打开“候选清单与覆盖矩阵”，按城市、区域、地点类型、Revision 生命周期和待核验项筛选。
3. 打开候选详情，确认当前 Revision 编号、Revision 版本、创建时间、来源数量和已有审核任务。
4. 先确认当前操作对象是 candidate。`human_verified` 或 `published` 不允许原地编辑。

### 4.2 创建或确定 candidate Revision

以下两种入口最终都必须得到一个新的 candidate Revision：

- 对尚未审核的候选：直接打开当前 candidate。
- 对已人工核验或已发布地点：在地点详情点击“新建修订”，以指定基线复制出新 Revision，再进入编辑页。

编辑基础事实时检查：规范名称、别名、地点类型、分类、所属区域、地址、几何类型、建议游玩时长、室内外、适用时段、雨天适配和适合人群。时长未采集的 `1/1/1` 占位可先填写建议时长，系统会建立合法区间；已有真实区间时，建议时长必须位于最短和最长值之间。

新建 Revision 会复制基线 Revision 当前仍然有效的地点事实证据（Geometry、AccessPoint、TimeRule、Closure、DateException），并为每条子证据生成新的编号。复制后的证据统一回到“待核验”状态，`reviewed_at` 清空；已停用的历史证据不会重新生效。这样新 Revision 可以在已有事实基础上只修改变化项，同时仍然必须由 reviewer 重新核验，旧 Revision 和旧审核记录保持不可变。

如果页面是在修复前创建的旧 Revision 上打开，旧版本不会被后台自动补写证据。请从最新基线重新点击“新建修订”，或在当前 candidate 中通过“新增”补录缺失证据。

保存后系统会递增 `revision_version`，重置 `solver_eligible=false`、`conflicts_resolved=false` 和 `reviewed_at=null`，并使既有证据审核结果不再代表新内容。页面应显示“已保存，需要重新送审”。

### 4.3 核验地图、几何和访问点（O04）

在“地图、几何与访问点”逐条处理 active 证据：

1. Geometry：确认点位代表地点本体，而不是把游客入口误当作地点几何；确认 `point/area/route` 与地点类型匹配；检查坐标来源、观察时间和版本。
2. AccessPoint：确认游客入口、游客出口、路线起终点、演出地点或区域代表点的语义和方向；到达和离开端点必须能解释后续路网计算。
3. 错误证据应编辑为正确值或停用，不能仅在备注中掩盖错误。
4. 每次保存都会使该证据回到待核验状态，并要求重新送审。

reviewer 在开放审核任务中对每条 active Geometry 和 AccessPoint 点击“通过”或“驳回”。驳回必须有稳定理由码；被驳回项回到编辑者修订路径。

#### 面向非开发人员的填写口径

| 页面字段 | 实际含义 | 获取与核验方式 |
|---|---|---|
| 几何类型 | 地点本体在地图上的形状：点、区域或路线 | 点状景点通常选“点”；景区/街区核对边界后选“区域”；步行路线按起终点或轨迹选“路线” |
| 图形数据（GeoJSON） | 机器可读的地图形状，不是普通文字地址 | 从已登记地图来源导出或由数据编辑者按来源录入；点的 `coordinates` 顺序必须是“经度、纬度” |
| 访问点用途 | 游客真正进入、离开或集合的位置 | 根据地图入口、现场指引和官方说明选择游客入口/出口、路线起终点、演出地点等 |
| 坐标 | 访问点的纬度和经度 | 使用已登记地图 Provider 的点位，结合现场/地图页面确认；纬度范围 -90～90，经度范围 -180～180 |
| 来源记录 | 证明该条事实的采集记录，包含来源、URL、观察时间、采集方式和许可状态 | 只能从当前地点已有的有效来源中选择；来源记录 ID 不是高德 POI ID，也不是内部地点编号 |
| 求解投影端点 | 发布后求解器实际使用的到达/离开访问点绑定 | 不是审核人手工填写；由发布者在 `human_verified` 后准备 Projection，系统依据已核验访问点生成并显示 |

坐标不能只凭 Provider 默认中心点直接通过。多入口景区、开放街区和演出地点必须保留入口语义；Geometry 代表地点本体，AccessPoint 代表游客接驳端点，两者可以不同。

### 4.4 核验开放时间、闭馆和固定场次（O05）

检查周规则、最晚入园、跨午夜窗口、固定场次、固定闭馆日和日期例外。`show` 类型地点必须核对场次开始/结束时间和演出地点，避免固定场次被错误当成普通开放时间。

1. 在开放时间页面新增、编辑或停用时间证据。
2. 使用“指定日期解析预览”输入至少一个工作日、一个周末和一个存在例外的日期（如有），确认开放窗口、最晚入园、固定场次和例外覆盖结果。
3. 重点确认跨午夜分钟值（大于等于 1440）和多个固定场次的歧义提示。
4. reviewer 对每条 active TimeRule、Closure、DateException 逐项通过或驳回。

解析预览是只读验证，不会代替审核，也不会改变证据状态。

新增时间证据时，`开始时间（分钟）`、`结束时间（分钟）`和`最晚入园时间（分钟）`是系统统一的时间表示：当天 `09:30` 为 `570`，跨午夜次日 `00:30` 为 `1470`。审核人应先从官方公告、售票页或现场信息确认当地时间，再换算为分钟；临时关闭类型不填写开放窗口。周规则用于重复发生的开放/场次，固定闭馆日用于每周固定关闭，日期例外用于具体日期覆盖周规则。

### 4.5 处理来源与字段冲突（O06）

打开“来源与字段冲突”，按同一 `source_id` 查看来源 URL、观察时间、内容指纹、许可登记和字段值。对冲突值选择采用方案并填写裁决说明；被否决来源保留，不删除、不静默采用最新值。

未裁决冲突会使 `conflicts_resolved=false`，并阻断 Revision 级通过和发布。裁决后仍需重新送审，因为裁决改变了当前 Revision 的事实闭包。

### 4.6 处理地点关系与重叠（O07）

打开“地点关系与互斥裁决”，核对 `contains`、`part_of`、`overlaps`、`same_experience` 及其证据。对于飞来峰/灵隐寺等包含或重叠对象，明确目录共存、选择互斥或求解投影去重语义。

- `resolved` 必须填写裁决说明；`not_required` 也要有足以解释为何无需裁决的记录。
- 未裁决的重叠或同一体验关系不能进入可发布投影。
- 关系编辑会递增 Revision 版本、清除审核资格，并要求重新送审。

关系记录通常由地点归一、去重或关系线索采集流程生成，审核页面不是让 reviewer 凭空创建关系的地方。若发现“飞来峰/灵隐寺”等实际存在关系但列表没有记录，应先由数据编辑流程补录关系及其来源，再回到 O07 选择“已裁决”或“无需裁决”并填写说明。没有关系记录不代表两者一定独立，只表示当前 Revision 尚无可审核的关系证据。

### 4.7 送审（编辑者）

编辑者确认基础事实、O04、O05、O06、O07 均已处理后，在 Revision 详情点击“送审”。接口创建或重用一个开放审核任务，状态为 `ready_for_review`，并记录操作意图和审计事件。

送审只是把工作交给 reviewer，不是“自动通过”。当前实现中，完整门禁的权威判断在 reviewer 的 Revision 级 `approve`；因此即使送审按钮可用，也可能在最终通过时因证据、冲突或来源依赖不完整而被拒绝。

### 4.8 reviewer 接单和逐项审核

1. reviewer 打开“审核队列”，筛选 `ready_for_review`、`in_review` 或 `changes_requested`。
2. 打开任务，记录任务版本，查看 Revision 与基线的差异、来源依赖、发布阻断摘要。
3. 进入 Revision 详情，按以下顺序逐项处理：基础事实与来源 → Geometry → AccessPoint → TimeRule → Closure → DateException → Relation。
4. 对每条 active 证据选择“通过”或“驳回”，而不是只审一条代表记录。逐项操作需要开放审核任务；服务端写入 `review_status`、`reviewed_at` 和审计事件。
5. 证据通过的判断依据是来源可信、归属正确、语义可解释、数值范围合理且与其他证据不冲突。

页面上的“通过”是证据级通过；不要把它与审核任务底部的 Revision 级“通过”混用。

### 4.9 Revision 级通过或退回

当所有 active 证据均已人工核验，且来源冲突、关系裁决和依赖闭包满足要求时，reviewer 回到审核任务，执行 Revision 级“通过”。服务端在同一事务中：

- 写入 `ReviewDecision(approve)`；
- 更新审核任务为 `approved` 并关闭任务；
- 将 candidate Revision 更新为 `human_verified`；
- 写入 `reviewed_at` 和管理审计事件。

任意 active Geometry、AccessPoint、TimeRule、Closure、DateException 或 Relation 未核验，或仍有未裁决冲突，服务端返回 `review_revision_not_approvable`，Revision 保持 candidate，不得由前端假定成功。

若选择“退回修改”：

1. 必须选择稳定理由码，可附非敏感说明；
2. 任务进入 `changes_requested`；
3. 编辑者修改或停用被指出的证据；
4. 保存产生新 Revision 版本并清除相关审核状态；
5. 编辑者重新点击“送审”；
6. reviewer 从当前版本重新逐项审核，不能沿用旧版本的通过结论。

### 4.10 准备求解投影（发布者）

只有 `human_verified` Revision 才能进入“准备求解投影”。`data_publisher` 在 Revision 详情点击该操作，系统按当前人工核验的访问点、时间和事实生成 `candidate` Solver Projection，计算 projection hash，并运行 publication gate。

该动作不会把 Revision 变为 published，也不会跳过发布检查。缺少人工核验访问点、Projection 已存在、来源依赖不完整等情况会返回稳定阻断码，例如 `MISSING_VERIFIED_ACCESS_POINT`、`PROJECTION_ALREADY_EXISTS` 或 `PROJECTION_DEPENDENCY_MISSING`。

### 4.11 发布检查、批次预览与发布

1. 在发布中心运行 publication check，确认依赖闭包、投影状态、冲突/关系门禁和数据快照版本。
2. 勾选通过检查的 Revision，创建发布批次预览；预览逐项显示可发布或阻断原因。
3. `data_publisher` 确认批次理由并执行批次。部分失败必须逐项报告，失败项不改变状态。
4. 成功项调用 `publish_projection`，在事务内发布 Revision/Projection，生成不可变 ResearchSnapshot 并写入审计。
5. 在快照历史核对快照编号、内容 hash、覆盖范围和质量摘要。

单个“发布新快照”快捷入口也必须先运行 publication check；不能通过通用编辑接口设置 `published`。

## 5. 快速判断表

| 当前看到的状态 | 下一步 | 不应做的事 |
|---|---|---|
| candidate，无开放任务 | 编辑/补证据后送审 | 直接准备 Projection |
| ready_for_review / in_review | reviewer 逐项审核 | 只点 Revision 级通过而不审证据 |
| changes_requested | 编辑被驳回项并重新送审 | 复用旧版本通过结论 |
| approved 任务但 Revision 仍 candidate | 刷新并检查服务端错误/版本冲突 | 手工改库为 human_verified |
| human_verified，无 Projection | 发布者准备 Projection | 直接发布不存在的 Projection |
| candidate Projection 有阻断 | 修复依赖或回到新 Revision | 忽略 reason code 强制发布 |
| publication check 通过 | 批次预览并执行 | 把预览当成已发布 |
| published | 只读；需要变更时新建 Revision | 原地修改历史版本 |

## 6. 审计和重试要求

创建 Revision、编辑事实、编辑/停用证据、来源裁决、关系裁决、送审、逐项审核、Revision 级决定、Projection 准备、批次预览和发布均必须产生追加式 AdminAuditEvent。审计至少关联操作者、角色、请求 ID、操作意图、目标对象、目标 Revision、前后摘要和结果。

网络重试必须复用同一个 `operation_intent_id` 和相同载荷；服务端会返回原结果。相同意图改用不同载荷返回冲突。遇到 `expected_revision_version` 或审核任务版本冲突时，重新读取页面，不要覆盖他人的新版本。

## 7. 完成定义

一条 candidate 只有同时满足以下条件，才算“人工核验闭环完成”：

- 当前 Revision 是目标版本，且所有事实和 active evidence 已核对；
- 所有来源冲突已裁决，所有需要裁决的地点关系已处理；
- reviewer 已逐项通过全部 active Geometry、AccessPoint、TimeRule、Closure、DateException、Relation；
- reviewer 已执行 Revision 级 approve，Revision 为 `human_verified`；
- candidate Projection 已准备，publication check 通过；
- 发布批次执行成功，ResearchSnapshot 可在快照历史中回放；
- 以上每一步均有可查询审计记录。

其中任一条件未满足，只能称为“审核进行中”或“发布准备中”，不能称为已发布研究数据。
- O07 无关系闭环：若系统没有发现任何地点关系，数据编辑员在 O07 点击“确认无关系”。该操作不是手工勾选求解资格，而是登记本次修订已完成关系检查；修订版本会递增并清除既有审核/求解状态，随后按正常流程重新送审。reviewer 只读查看该结论。
