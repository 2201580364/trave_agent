# O09 研究快照批次发布设计

状态：实现首版已完成，候选目录导入幂等/dry-run、Projection 准备管理 API、自动化与既有 Chrome 首版验收通过；真实 candidate 审核数据下的管理端勾选路径待回归。

## 目标

将多个已通过 Projection publication check 的地点版本固化为可审计、不可变的研究数据快照。

## 边界

- 单个 Projection 发布是地点级发布，不等同于研究快照；
- PublicationBatch 保存批次意图、操作者、目标地点集合、逐项结果和质量报告；
- ResearchSnapshot 保存不可变版本、内容 hash、来源数据版本和批次引用；
- 批次部分失败必须逐项记录，不能静默跳过；
- 已发布快照不允许原地修改，更新必须创建新版本。

## 实现顺序

1. Alembic 追加批次、批次项和研究快照表；
2. SQLAlchemy 仓储与幂等约束；
3. 批次预览 API，返回逐项门禁结果；
4. 批次执行 API，生成不可变内容 hash；
5. 快照列表/详情查询；
6. admin-web 发布中心接入批次预览、执行和历史查询；
7. `prepare_candidate_projections.py` 生成 candidate Projection，并把 publication gate 原因逐项落盘；
8. 全量自动化测试与 Google Chrome 验收。

Projection 节点号由仓储按 `data_snapshot_version` 分配，管理端不再依据 Revision 编号推导；通过 publication gate 的候选 Projection 会重算哈希并固化 `data_verified=true`。该规则保证跨地点批量准备时节点 ID 唯一且可重放。

## 当前退出条件

- 候选目录导入只能创建 `candidate` Revision，首次导入、重复导入和 dry-run 均可复现且不越过审核门禁；
- `projection-preparations` 只能由 `data_publisher` 对 `human_verified` Revision 发起，生成 candidate Projection 并保留逐项 publication-gate reason code；
- 只有通过正式 reviewer 逐项审核并生成完整 candidate Projection 的 Revision 才能进入发布中心可勾选集合；
- Chrome 必须补齐真实待发布数据下的“Revision 详情准备 Projection → 发布中心勾选 → 预览 → 执行 → ResearchSnapshot 历史”操作链路，不能用 SQL 直接制造状态；
- 在上述 UI 回归完成前，O09 仅标记为阶段性完成，不作为大模块提交点。
