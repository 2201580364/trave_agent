## 一、产品定位与愿景

### 1.1 一句话定位

> 一个**模拟人类真实做攻略过程**的AI旅行决策与陪伴系统——不是给你一份花哨的攻略，而是陪你完成从"想去"到"回来了"的每一步思考。

### 1.2 用户感知定位

```
M1-2：像一个"去过当地、做过功课、讲道理的"旅行顾问。
M3-4：升级为"去过当地、了解你、会说实话、不怕麻烦的"旅行朋友。
```

**设计原则**：人格化程度与产品成熟度匹配。早期追求"专业可靠"而非"亲密有温度"，避免在数据不足时做出无法兑现的情感承诺。

### 1.3 产品愿景

打造一个**有判断力、有记忆、值得信赖**的旅行伴侣。它是一个理解用户旅行需求的决策伙伴——帮用户省去繁琐的查询与对比，从根本杜绝低级错误，接住旅途中的意外，沉淀每一次旅行，并在下一次旅行时还记得用户是谁。

### 1.4 与竞品的核心差异

| 维度 | 现有产品 | 本产品 |
|---|---|---|
| 角色 | 信息聚合器 / 搜索引擎 / 票务预订平台 | 决策伙伴 / 全程陪伴 |
| 输出 | 散落信息、静态攻略文档 | 结构化对比、取舍辅助、动态行程 |
| 行程逻辑 | 按热度推荐、人工编排 | 硬约束求解 + 体验优化 + 个性适配 |
| 大交通 | 独立票务搜索（订票工具），与行程规划割裂 | 大交通是行程的"时间锚点"，与Day 1/Day N安排深度耦合 |
| 对用户认知 | 匿名、无记忆 | 越用越懂用户、跨越每次旅行 |
| 语言风格 | 信息罗列、机械时间表 | 会解释理由、会劝退、理性且有人情味 |

## 二、市场痛点与产品价值

### 2.1 解决的六大实际问题

| 痛点 | 现状 | 产品解法 |
|---|---|---|
| **信息碎片化** | 用户需在小红书、携程、大众点评、地图、天气App之间反复横跳 | 一站式聚合，结构化呈现，自动对比与排程 |
| **攻略与真实脱节** | 静态攻略不区分季节、天气、出行人群 | 多源评论AI提炼，行程随天气/季节/人群动态调整 |
| **选择焦虑** | 信息过载导致决策瘫痪，"看了一下午反而更纠结" | 对比表、舍弃建议、沙盘推演、多人协同决策 |
| **低级错误频发** | 周一排了闭馆博物馆、雨天排了全程户外、同天跨区来回跑 | 硬约束引擎从根本杜绝 |
| **行中变数焦虑** | 突遇天气/排队/关门，攻略失效，临时搜索浪费时间 | 行中动态剧本，实时感知 + 自动推送Plan B |
| **记忆流失** | 照片散落、心情遗忘、再没动力整理游记 | 自动生成图文游记，把行程 + 天气 + 照片 + 轨迹编织成故事 |

### 2.2 对用户的核心价值

- **省时**：做一份完整行程的时间从天/小时级压缩到分钟级
- **省心**：不用纠结，系统帮用户理清头绪、做取舍
- **避坑**：杜绝低级错误，守护体验底线
- **安心**：行中有Plan B，不怕计划赶不上变化
- **沉淀**：每次旅行都有痕迹，越用越懂用户

### 2.3 用户研究状态

> **注意**：以上痛点基于行业观察和逻辑推演得出，尚未经过正式用户研究验证。详细的研究计划见【第十一节】。在 M1 启动前，需完成 5-8 次目标用户深度访谈，对痛点优先级和表述进行校准。

### 3.3 大交通出行方式定义

大交通指从出发地到目的地的城际/省际/国际交通方式，是行程规划的第一层硬约束——到达时间决定了 Day 1 的实际可用时间，离开时间决定了最后一天的结束边界。

| 出行方式 | 典型场景 | 对行程的核心影响 | 特殊约束 |
|---|---|---|---|
| **飞机** | 跨省/国际旅行，距离 > 800km | 到达时间 + 机场到市区耗时（通常 1-2h）→ Day 1 有效起始时间 | 航班延误风险、行李提取耗时、值机提前量 |
| **高铁/动车** | 中短途城际，距离 200-800km | 到达时间 + 高铁站到市区/酒店耗时（通常 0.5-1h） | 准点率高、改签灵活 |
| **普通火车** | 预算有限、夜间卧铺 | 到达时间（通常清晨）→ 需考虑洗漱/寄存行李 | 舒适度低、可能影响当日体力 |
| **自驾** | 周边游、多目的地串联、家庭出行 | 到达时间灵活 + 目的地内部交通自由度高 | 车辆停放、景点可达性、充电桩/加油站、疲劳驾驶限制 |
| **长途大巴** | 短途周边、目的地公共交通不便 | 班次少、耗时长、灵活性低 | 舒适度最低 |

> **设计原则**：大交通方式的选择决定了行程的"时间锚点"。M1 用户手动输入到达/离开时间与方式；M2 起系统帮助搜索和比价；M3 实现票务预订聚合。自驾场景在 M3 独立规划，因为其复杂度（路线途经点、充电/加油、限行）不亚于目的地内部行程规划。

### 3.4 景点深度信息卡与社区功能（M2-M3）

**M2 落地深度信息卡**，解决用户"不知道景点值不值得去"的核心焦虑；**M3 落地评分与讨论区**。

#### 3.4.1 景点深度信息卡

每个景点展示一张结构化信息卡片，包含：

| 信息维度 | 内容 | 数据来源 |
|---|---|---|
| 基础标签 | 类型、体力消耗、建议游览时长、开放时间、室内/室外 | 人工标注 |
| 一句话亮点 | AI 从多源评论中提炼的最具代表性描述 | 大模型抽取 |
| 适合人群 | 情侣/亲子/老人/独行/团建等标签 | 人工标注 + 评论提炼 |
| 最佳时段 | 季节 + 一天中的最佳游览时段及理由 | 规则 + 评论提炼 |
| 用户评分 | 综合评分 + 分维度评分（风景/性价比/拥挤度/趣味性） | 用户UGC |
| 评论摘要 | 正面关键词云 + 负面高频吐槽 + 近期趋势（如"最近排队严重"） | 大模型提炼 |
| 实拍照片 | 用户上传的精选照片轮播 | 用户UGC |

#### 3.4.2 景点评分系统

- 用户完成行程后，可对已游览景点进行打分（1-5星）和维度评价
- 评分需关联实际出行日期和人群类型，形成"带上下文的评分"（如"带娃出行者平均评分 4.2"vs"独行者平均评分 3.8"）
- 评分入口：行后评价弹窗 + 景点信息卡中的快捷评分

#### 3.4.3 景点讨论区

- 每个景点下方挂载轻量讨论区（类似小程序的留言板）
- 内容：实用Tips（"后门进不用排队"）、时效信息（"最近在修缮"）、避坑分享
- 按"最新"和"最有用"排序
- 支持对讨论内容点赞，高赞内容自动置顶
- 反垃圾：初期人工审核，后期接入自动化审核

> **设计原则**：讨论区不追求"社区活跃度"，而是追求"信息密度"。冷启动时，讨论区可为空——用户看到"还没有人分享"比看到虚假灌水内容更诚实。

### 3.5 旅行小记（M2）

用户在行程进行中或结束后，可以按行程日期记录旅途中的碎片化记忆。

| 特性 | 说明 |
|---|---|
| 记录粒度 | 按行程日期组织，每条小记绑定到具体日期 |
| 内容形式 | 文字（短文本）+ 图片（最多9张），支持简单的图文混排 |
| 私密性 | 默认仅自己可见，可选择分享到景点讨论区 |
| 入口 | 行程详情页 → 对应日期 → "记录这一刻" |
| 与游记的关系 | 小记是碎片化的原始素材；M4 自动游记生成时，系统会从小记中选取素材编织叙事 |

> **设计意图**：旅行小记的定位不是"写日记"，而是"随手记"。用户拍了一张有趣的照片，写两句话，10 秒完成。这些碎片化记录在 M4 会成为自动游记生成的核心素材来源，同时为评分和讨论区贡献 UGC 内容。

### 3.6 行程分享卡片与反馈（M1 MVP）

#### 3.6.1 行程分享卡片

行程生成完成后，用户可一键生成精美行程卡片图片：

- 包含：目的地、日期、每日行程概览、景点缩略图、天气标注
- 底部嵌入小程序码，扫码可直接查看/复制行程
- 支持多种视觉风格模板（简约/文艺/活泼）
- 可直接分享到微信聊天、朋友圈、保存到相册

#### 3.6.2 行程反馈（👍👎）

- 每项行程安排（景点、时段建议）后附带 👍👎 按钮
- 用户点击后可选填原因（"时间太赶""路程太远""这个安排很好"）
- 反馈数据直接驱动求解器参数调优
- 反馈数据关联出行人群、行程模式，形成"带标签的满意度数据"

### 3.7 住宿区域建议（M2）

**这是"酒店推荐"的前置简化版**——不推荐具体酒店，而是推荐最优住宿区域。与 M2 酒店推荐在同一阶段落地，形成"区域→具体酒店"的递进体验。

#### 3.7.1 问题场景

用户选定景点 A、B、C 后，三个景点分布在城市的不同方向。如果住宿位置选在 A 附近，去 B 和 C 需要每天长途通勤；如果选在三个景点的几何中心，每天往返距离最小。

#### 3.7.2 求解逻辑

- 输入：用户选定的景点集合 + 各景点游览日期分配
- 计算：以最小化总通勤距离（或时间）为目标，基于景点空间分布和城市交通网络，推荐 1-3 个最优住宿区域
- 输出：推荐区域名称（如"西湖商圈"、"武林广场周边"）+ 选择理由（"到你的 5 个景点平均通勤时间仅 15 分钟"）+ 该区域大致的酒店价格区间
- 用户可自行在推荐区域内搜索和预订酒店

#### 3.7.3 与酒店推荐的差异

| 维度 | 住宿区域建议 | 酒店推荐 |
|---|---|---|
| 输出粒度 | 区域（商圈/地铁站周边） | 具体酒店（1-3家） |
| 数据需求 | 城市交通网络 + 区域价格区间 | 酒店详情 + 评论 + 实时价格 |
| 建设成本 | 低（基于地图API可达性计算） | 高（需酒店知识图谱） |
| 用户行为 | 看到区域建议 → 自行搜索预订 | 看到酒店推荐 → 系统内比价/预订 |
| 落地阶段 | M2（与酒店推荐同期） | M2 |

> **引擎影响**：住宿区域建议与景点日程安排是耦合的——住宿位置影响每日通勤，每日通勤反过来影响"住在哪里最合理"。M2 求解器在 M1 的"聚类分天→天内排序"基础上，增加住宿位置作为优化变量。

### 3.8 行程模式定义

| 模式 | 日体力预算 | 行程密度 | 景点类型倾向 | 餐饮倾向 |
|---|---|---|---|---|
| 特种兵模式 | 8星 | 高密度，紧凑衔接 | 打卡最大化 | 快捷便利优先 |
| 正常模式 | 5星 | 经典动线，节奏适中 | 大众好评经典 | 好评与实惠兼顾 |
| 休闲模式 | 3星 | 低密度，留白充足 | 过滤高体力景点 | 环境优先 |

> **假设标记**：体力预算体系（1-5星体力消耗 × 3/5/8星日预算）为待验证假设，M1 需通过用户测试确认合理性。

### 3.9 输出内容标准

**M1 输出**：
- 上午景点（含建议时段与理由）
- 下午景点（含建议时段与理由）
- 晚间活动/景点
- 天气风险提示（"Day 2 有雨，以下景点为户外景点，建议准备备选方案"）
- 室内替代方案建议（如遇雨天可替换的室内景点）
- 用户自行标记的餐饮/酒店位置（系统不做推荐，仅验证与行程的空间合理性）
- 行程分享卡片（精美图片，含小程序码）
- 每项安排的 👍👎 反馈入口

## 四、产品阶段路线图（★ V2.2 重新分解）

### 4.1 阶段总览

| 阶段 | 名称 | 核心目标 | 时间参考 | 团队 | 一句话描述 |
|---|---|---|---|---|---|
| M1 | MVP：行程骨架验证 | 验证核心假设——"AI排的行程比人排更合理" | 4个月 | 2-3工程师 + 1设计师 + 1PM | 只做行程骨架的正确性 + 分享闭环 + 反馈数据 |

**设计原则**：
1. 每个 Phase 只验证一个核心假设，不堆砌多个独立假设
2. 每个 Phase 的功能之间有明确的依赖关系——后续 Phase 的功能依赖前序 Phase 的数据或基础设施
3. MVP 只包含"缺了它就无法验证核心假设"的功能，而不是"有了会更好"的功能

### 4.2 M1：MVP——行程骨架验证（4个月）

**核心假设**：AI 求解器生成的行程，用户认为"比我自己排更合理"。

**一句话边界**：做行程骨架的正确性 + 分享闭环 + 反馈数据。不做推荐，不做信息聚合，不做社区。

| # | 功能 | 说明 | 复杂度 |

| 1 | 目的地选择 | 聚焦 1 个城市（如杭州） | 低 |
| 2 | 出发地 + 大交通方式 + 到达/离开时间 | 飞机/高铁/火车/自驾/大巴，手动输入 | 低 |
| 3 | 出行日期 + 行程模式 + 出行人群 | 特种兵/正常/休闲；独行/情侣/亲子/带老人 | 低 |

| 7 | 行程分享卡片 | 一键生成精美行程卡片图片，含小程序码回流，多种视觉模板 | 低 |

- ✗ 自驾路线规划（→ M3）
- ✗ 预订聚合和比价（→ M3）
- ✗ 行前提醒和打包清单（→ M3）
- ✗ 行中动态重排（→ M3）

- ✗ 自动游记生成（→ M4）

**引擎因素**：地理聚类、时间窗适配、开放时间硬约束、体力消耗控制、天气风险适配、到达/离开时间锚点约束

**技术要点**：地图API、天气API、核心求解器（约束满足 + 路径优化）、小程序分享卡片生成

**验证指标**：

**MVP 范围决策逻辑**：

```

├── 出行人群标签（老人/儿童/宠物的特殊约束——影响大交通方式选择，如带老人倾向高铁而非红眼航班）
```

## 六、推荐算法设计原则

### 6.1 核心原则

推荐算法在本产品中的目标**不是"留住用户"**，而是**"帮用户更快找到适合自己的选择"**。

**四项不做**：
- 不为了商业化扭曲推荐排序
- 不过度个性化制造信息茧房
- 不隐藏差评
- 不代替用户做最终决策

### 6.2 推荐算法的三个角色

| 角色 | 场景 | 方法 | 启动阶段 |
|---|---|---|---|
| 初筛排序 | 展示热门景点列表 | 多因子加权排序（季节、天气、人群、模式），透明可解释 | M1 |
| 偏好学习 | 基于用户行为调整推荐 | 短期：当前行程的选择/拒绝行为；长期：历史轨迹、反馈 | M2 起 |
| 评分校准 | 餐厅/酒店真实度评估 | 评论者可信度分析 + 差评信息量加权 + 近期趋势检测 | M2 起 |

### 6.3 分阶段技术方案

| 阶段 | 推荐复杂度 | 方案 |

| M4 | 深度学习 | 基于用户长期行为序列的Embedding，规则层兜底确保可解释 |

### 7.2 核心求解器复杂度评估（新增）

**问题定义**：给定 N 个景点、D 天行程、到达/离开时间锚点（Day 1 有效起始时间、Day N 有效结束时间）、每个景点有开放时间窗、体力消耗值、建议游览时长，景点间有实际交通耗时，在满足（到达/离开时间锚点、地理聚类、每日体力上限、开放时间、天气适配）多约束下，求每日景点序列的最优或近似最优解。

**复杂度定性**：本问题属于**带时间窗和多约束的团队定向问题（TOP-TW 变种）**，属 NP-hard。当 N=15、D=3 时，搜索空间已远超穷举可行范围。

**M1 求解策略**：
1. **地理聚类**：基于经纬度的 K-Means 或 DBSCAN 将景点按天分组（降维）
2. **天内排序**：对每天景点用带约束的旅行商问题（TSP-TW）启发式求解
3. **时间填充**：在每个景点间插入缓冲时间、用餐时段
4. **约束校验**：硬约束全部满足后才输出；不满足则回溯重排

**性能目标与可行性**：
- 目标：N ≤ 20, D ≤ 7 时，求解时间 < 2 分钟
- 方法：OR-Tools 路由求解器 或 模拟退火 + 贪心初始解
- 实测期望：对于中等规模问题（N=12, D=3），应在 1 分钟内收敛到合理解
- 风险：当用户选择景点过多（N > 25）或约束过于严格时，求解时间可能超限
- 缓解：对超大问题提供"推荐每日上限景点数"的前置提示

> **投资人/技术评审注意**：核心求解器是本产品最硬的技术壁垒。它不是一个"调 GPT 就能做"的问题。需要具备运筹优化（OR）或约束规划（CP）经验的工程师。这个能力在消费级产品中罕见，也是大厂最难用"堆人"方式快速追赶的环节。

### 7.3 五大技术难点

| 难点 | 描述 | 复杂度评级 | 解决思路 |
|---|---|---|---|
| **多约束耦合优化** | 地理、时间、体力、天气、住宿位置、到达/离开锚点等多目标冲突，NP-hard | ★★★★★ | 分层降维求解（聚类分天→天内路径→住宿位置优化→时间填充）；大模型仅做交互层 |
| **住宿位置优化** | 住宿位置与景点日程安排耦合——住宿影响通勤，通勤反过来影响住宿最优解 | ★★★★☆ | 先聚类分天确定景点分组 → 对各组计算最优住宿区域 → 迭代优化至收敛 |
| **知识图谱构建与保鲜** | 景点/餐饮/酒店标签体系从零构建，持续更新 | ★★★★☆ | 初期聚焦1城市人工标注+大模型辅助抽取；建立爬虫→校验→更新的数据管道 |
| **UGC内容质量与反垃圾** | 景点讨论区、评分、小记的灌水/广告/虚假信息治理 | ★★★☆☆ | 初期人工审核（用户量小可承受）；建立敏感词过滤 + 异常行为检测；后期接入自动化审核 |
| **多源交通票务数据聚合** | 机票/高铁/火车票多平台API接入、价格实时性、舱位余量同步 | ★★★★☆ | 初期接入1-2家OTA联盟API；建立价格缓存层（分钟级刷新）；非核心路径不阻塞主流程 |
| **多源评论真实性提炼** | 水军、情绪偏差、跨平台语义统一 | ★★★★☆ | NLP+大模型混合，结合可信度评分；显性化不确定性给用户 |
| **行中动态重排实时性** | 突发变数需秒级局部重算，避免打扰用户 | ★★★★☆ | 预计算多套替代方案+后台静默监控+阈值触发推送 |
| **自驾路线规划** | 途经点推荐、充电桩/加油站实时状态、限行规则、多日路线优化 | ★★★★☆ | 基于地图API路线引擎 + 充电桩/加油站POI数据；限行规则结构化维护 |
| **用户画像冷启动** | 新用户无历史数据，个性化无从谈起 | ★★★☆☆ | 快速提问（2-3题）+目的地大众数据先验+用户调整行为反向学习 |

### 7.4 大模型使用边界

| 使用场景 | 不使用场景 |
|---|---|
| 自然语言交互与行程解释 | 核心约束求解（自研引擎负责） |
| 评论摘要提炼与情感分析 | 实体存在性校验（基于结构化数据库） |
| 人文彩蛋内容生成 | 开放时间/价格等硬事实数据提供 |

| H6 | 用户愿意在行程规划工具中主动输入出发地和到达/离开时间，而非跳过此步直接选景点 | M1 | 用户测试：观察首次使用时的行为漏斗，统计跳过率 | 跳过率 > 50% 说明该步骤不应作为必填项 |
| H7 | 到达/离开时间锚点约束能显著提升行程合理性（Day 1 不排过多、Day N 预留赶路时间） | M1 | A/B测试：有无锚点约束的行程，用户满意度对比 | 满意度无显著差异 → 锚点约束可简化为可选 |
| H8 | 景点深度信息卡（含评论摘要）能显著减少用户跳转到其他App的行为 | M1 | 用户测试：观察使用深度信息卡前后的App切换行为 | 切换行为无明显减少 → 信息卡深度不足，需增强 |
| H9 | 住宿区域建议（非具体酒店推荐）对用户有价值，且用户能接受"推荐区域→自行搜索预订"的流程 | M1 | 用户测试：住宿区域建议的采纳率和满意度 | 采纳率 < 30% → 说明用户期望的是具体酒店推荐而非区域建议 |
| H10 | 用户愿意在行程中随手记录旅行小记（文字+图片），且默认私密的设计不会抑制使用 | M1 | 使用率数据 + 用户访谈 | 使用率 < 10% 且用户反馈"不想在旅行中打开App" → 小记功能需重新设计或后置 |
| H11 | 行程分享卡片能成为有效的获客钩子（分享 → 扫码 → 新用户注册） | M1 | 分享率 + 扫码转化率 + 新用户注册率 | 扫码转化率 < 5% → 卡片设计或小程序码引流策略需调整 |
| H12 | 景点讨论区在冷启动期（无内容或少量内容）不影响用户对产品的信任 | M1 | 用户访谈：空的讨论区是否让你觉得产品"还没人用/不靠谱" | 负面感知 > 30% → 讨论区需隐藏或改为邀请制内测 |

## 十一、用户研究假设与验证计划（新增）

### 11.1 研究目标

在 M1 启动前，验证或推翻第二章所述的六大痛点的优先级和表述，校准目标用户画像和核心使用场景。

### 11.2 研究方法

**深度访谈**（M1 启动前，预计 2-3 周）：

| 项目 | 说明 |
|---|---|
| 样本量 | 8-10 人 |
| 招募标准 | 过去12个月内有过2次及以上自助旅行经历；曾自行做攻略；混合年龄（22-45）、混合出行类型（独行/情侣/亲子） |
| 访谈时长 | 45-60 分钟/人 |
| 方法 | 半结构化访谈 + 关键事件法（回忆最近一次做攻略的具体过程、卡点、情绪） |
| 输出 | 用户旅程地图、痛点优先级排序、JTBD（Jobs-to-be-Done）陈述、核心用户画像 2-3 个 |

**竞品体验日志**（与研究并行）：
- 团队每人用竞品（小红书、携程、马蜂窝、Google Trips）完整做一份真人行程
- 记录每一步的摩擦点、情绪、耗时
- 输出：竞品摩擦点地图

### 11.3 关键研究问题

1. 用户做旅行攻略的真实流程是什么？从"想去"到"出发"，每个阶段花多少时间？在哪一步最痛苦？
2. "选择焦虑"和"信息碎片化"，哪个是更大的痛点？还是两者是同一个问题的不同表述？
3. 用户在什么情况下会放弃自己排行程，转用现成攻略/跟团？触发条件是什么？
4. 用户对"AI帮你排行程"的信任门槛在哪里？什么情况下会接受，什么情况下会拒绝？
5. 三个行程模式（特种兵/正常/休闲）是否覆盖了用户自述的旅行风格？有遗漏吗？
6. 用户是否愿意为行程规划付费？如果愿意，心理价位和付费模式（一次买断/订阅/单次）是什么？
7. 用户在大交通（机票/高铁/自驾）选择上的决策流程是什么？先订票再做攻略，还是先做攻略再订票？大交通决策中最大的摩擦点是什么？

### 11.4 验证结果如何影响产品

| 如果发现…… | 那么…… |
|---|---|
| "选择焦虑"比"排程逻辑"更大 | M2 的对比/舍弃功能前置，M1 增加简单的同质化标记 |
| 用户对"AI排行程"信任度低 | M1 更强的"可解释性"设计，每步安排附详细理由 |
| 休闲模式用户占比远超预期 | M1 优先打磨休闲模式的体验 |
| 用户认为体力预算概念不直观 | 替换为"行程节奏：紧凑/适中/悠闲"的语言表述 |
| 付费意愿远低于预期 | 重新评估变现路径，探索B端（旅行社/定制游）可能性 |
| 用户"先订票再做攻略"是主流 | M1 大交通输入前置为必填步骤，且需在景点选择前完成 |
| 用户"先做攻略再订票"是主流 | 大交通输入可后置为可选步骤，或与行程规划并行 |
| 自驾用户占比 > 30% | M3 自驾路线规划优先级提升，M2 即需考虑自驾场景的景点可达性信息 |

## 十二、Go-to-Market 策略（新增）

### 12.1 目标用户画像（假设，待研究验证）

| 画像 | 特征 | 旅行频次 | 核心需求 | 获客优先级 |
|---|---|---|---|---|
| **攻略倦怠者** | 25-35岁，一线城市白领，有旅行预算但没时间做攻略 | 2-3次/年 | 省时、避坑 | ★★★ 首批 |
| **打卡规划者** | 20-28岁，学生/初入职场，预算有限但想最大化体验 | 1-2次/年 | 高效打卡、不踩雷 | ★★★ 首批 |
| **家庭出行者** | 30-45岁，带娃/带老人出行，约束条件复杂 | 1-2次/年 | 老人孩子友好、节奏可控 | ★★☆ M2 |
| **深度旅行者** | 30-50岁，重视体验质量，厌恶商业化和网红化 | 2-4次/年 | 避开人潮、独特体验 | ★★☆ M2 |

### 12.2 获客路径（M1-2）

```
M1 冷启动（0 → 1000 用户）：
├── 路线1：选择一个垂直旅行社区（如豆瓣旅行小组/即刻旅行圈），
│          以"产品共创"名义招募种子用户，提供深度体验资格
├── 路线2：微信搜一搜/问一问中回答行程相关问题，引导体验
├── 路线3：小红书上发布"AI排行程 vs 手工排行程"对比内容，
│          以内容引流小程序
└── 路线4：在1-2个目标城市（杭州）的本地生活社群中定向推广

M2 增长（1000 → 50000 用户）：
├── 核心钩子：行程分享——用户生成行程后可一键生成精美行程卡片，
│          分享到朋友圈/微信群，卡片自带小程序码回流
├── 场景触发：节假日/小长假前2周加大内容投放
└── SEO：微信搜一搜优化目的地+攻略类关键词
```

### 12.3 变现路径（分阶段）

| 阶段 | 变现方式 | 预估收入 | 说明 |
|---|---|---|---|
| M1-2 | 不变现 | 0 | 专注体验打磨和用户增长 |
| M3 | 预订CPS佣金（酒店/门票/机票） | 单用户ARPU ~5-15元/次旅行 | 通过API接入携程/美团/飞猪联盟 |
| M4 | CPS + 付费深度规划（如复杂行程/小众目的地/多人协调） | 目标年ARPU ~30-50元 | 基础规划免费，高级功能付费 |

**盈亏平衡参考**：假设 M3 末期月活 10 万，年旅行 2 次/人，佣金 10 元/次，年收入 ~200 万。团队控制在 8-10 人规模时可接近打平。

### 12.4 竞品防御

| 威胁 | 防御策略 |
|---|---|
| 携程/美团在其App内集成类似AI规划功能 | 不做平台，做独立的"决策伙伴"品牌认知；用户不会在预订工具里做深度规划 |
| 小红书推出AI行程功能 | 小红书的优势是种草和灵感，不是决策和排程；强调"从种草到行程"的完整闭环 |
| ChatGPT/通用AI直接输出行程 | 通用AI输出无硬约束保障，易于出现闭馆日、跨区绕路等低级错误；这是核心求解器的护城河 |
