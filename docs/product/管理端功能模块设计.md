# 旅行助手管理端功能架构与里程碑

- 文档版本：V1.2
- 日期：2026-08-31
- 产品面：内部数据运营、审核、发布与内容治理
- 当前管理侧里程碑：OM1 — 研究数据治理与受控发布
- 当前状态：产品设计已接受；管理身份、独立管理 API、服务端 RBAC、管理员创建/角色管理、追加式审计后端底座、O00/O15/O16 安全操作面以及 O01–O09 地点审核/发布首版已实现，正在用真实 candidate 数据收口逐项审核到研究快照的闭环
- 当前项目节点：G7-R0.2-07 O09 真实 candidate 审核与研究快照闭环
- 上游：功能模块设计 V3.5、ADR-0005、ADR-0018、ADR-0019

## 1. 文档目标

本文补齐用户端之外的内部操作面，回答：

1. 哪些管理能力必须在 M1 Gate 7 前可用；
2. 管理侧如何按里程碑演进；
3. 数据编辑、审核和发布如何分权；
4. 哪些页面、状态、权限和审计构成最小闭环；
5. 如何避免管理端复制或绕过现有领域门禁。

管理端不以“后台菜单数量”为完成标准。每个功能必须能映射到角色、业务对象、状态转换、管理 API、审计事件和验收结果。人工核验的一线操作顺序、前置条件和退回重提规则统一见[《人工核验操作路径》](人工核验操作路径.md)，本文件负责能力域与里程碑边界。

## 2. 命名与范围规则

| 维度 | 取值 | 含义 |
|---|---|---|
| 用户侧产品里程碑 | M1–M4 | 旅行者可感知的产品能力路线 |
| 管理侧里程碑 | OM1–OM4 | 为对应用户能力提供数据、审核、发布、安全和运营支撑 |
| 实现优先级 | P0–P2 | 当前里程碑内的实现顺序，不表示产品阶段 |
| 管理功能 ID | `ADM-x.y.z` | 一级域、二级模块、三级原子功能 |
| 管理页面 ID | `O00–O16` | 内部 Web 页面；不进入用户端页面编号 Pxx |
| 研究问题严重度 | blocker/major/minor/observation | 不使用 P0/P1/P2 表示研究问题严重度 |

OM 里程碑不是独立商业路线，而是与 M 里程碑形成前置关系：公开能力所需治理未就绪时，对应用户能力不得开放。

## 3. 管理侧里程碑

### 3.1 OM1：研究数据治理与受控发布

目标：让杭州候选地点从 staging 到 human_verified、published research snapshot 的全过程可操作、可复核、可回放。

P0 范围：

- 管理员身份和服务端 RBAC；
- 候选地点与覆盖矩阵；
- 地点事实、几何、访问点和时间规则编辑；
- 来源与字段级 provenance；
- 重复、包含、重叠和互斥裁决；
- Revision 审核、驳回和 human_verified；
- 发布门禁、研究快照和退役；
- 结构化管理审计。

P1 范围：批量任务、数据质量看板、双人复核、过期提醒、Provider/OD 任务查询和快照对比。

退出条件：R0.2-05 的 50–75 个研究 Place 不依赖 SQL 手工改状态即可完成审核；R0.2-07 发布全过程可审计且不能绕过 `publish_projection`。

### 3.2 OM2：多目录运营、媒体与授权治理

目标：支撑 M2 深度地点信息、住宿/餐饮服务目录、多城市扩展、旅行小记和旅程回顾。

主要能力：

- 多城市地点和服务目录运营；
- 酒店/餐厅候选、营业时间、访问点和数据时效；
- 照片授权、媒体安全扫描和删除影响分析；
- 小记/回顾的公开授权查询与撤回处置；
- 内容来源许可、派生摘要版本和数据过期提醒；
- 城市发布批次、质量指标和运营任务分配。

OM2 治理能力必须先于相应 M2 公开内容或推荐上线。

### 3.3 OM3：社区与实时服务治理

目标：支撑 M3 景点评分、讨论区、举报、申诉、反垃圾、通知和动态服务。

主要能力：

- 内容审核队列；
- 举报和申诉；
- 用户违规记录和处置；
- 反垃圾规则和审核策略；
- 评分异常和刷量检测；
- 实时 Provider、提醒和 Plan B 运营状态；
- 预订/商业内容时效与披露检查。

没有 OM3 P0 治理闭环，不开放 M3 公开 UGC。

### 3.4 OM4：共创、AI 内容和生态治理

目标：支撑用户共创地点、自动游记、长期偏好和商业生态。

主要能力：

- 用户地点/路线贡献审核；
- 版权、来源、声誉和反作弊；
- AI 生成内容标识、素材授权和版本追踪；
- 长期偏好推断的查看、纠正和关闭；
- 商业合作、推荐关系和利益披露；
- 数据导出、删除和跨产品授权管理。

## 4. 角色与最小权限

| 角色 | 核心权限 | 明确禁止 |
|---|---|---|
| `data_editor` | 创建候选、编辑 candidate/staging、补充来源和审核材料 | 标记 human_verified、发布、修改审计 |
| `data_reviewer` | 审核 Revision、驳回、裁决冲突、标记 human_verified | 绕过缺失来源/入口/时间门禁发布 |
| `data_publisher` | 执行发布门、创建快照、退役/切换已发布版本 | 原地修改 published Revision |
| `research_viewer` | 查看覆盖、快照和 Gate 7 就绪报告 | 修改地点和审核结论 |
| `content_moderator` | OM3 内容审核、举报和处置 | 地点数据发布、系统权限管理 |
| `admin_security` | 管理管理员身份、角色和安全审计 | 通过权限配置绕过业务发布门禁 |

一个管理员可以拥有多个角色，但每次操作必须记录当时生效角色。管理员身份不与匿名会话、微信用户或普通账号自动互通。

### 6.8 ADM-8 Revision 审核工作流

| ID | 功能点 | 优先级 | 核心规则与验收 |
|---|---|---|---|
| ADM-8.1.1 | 待审核队列 | P0 | 按状态、区域、问题类型、负责人和更新时间筛选 |
| ADM-8.1.2 | 完整性检查 | P0 | 自动列出来源、几何、入口、时间、关系和投影缺口 |
| ADM-8.1.3 | 版本差异 | P0 | 字段、来源、端点、时间和 projection hash 差异可见 |
| ADM-8.2.1 | 审核通过 | P0 | 仅完整 Revision 可进入 human_verified，并写 ReviewDecision |
| ADM-8.2.2 | 驳回修改 | P0 | 必须选择 reason code，可附非敏感说明，返回 editor 队列 |
| ADM-8.2.3 | 审核历史 | P0 | 只追加，不覆盖；可按 Revision 回放 |

审核工作流必须按“候选准备 → 送审 → reviewer 逐项核验 → Revision 级通过/退回 →（通过后）Projection 准备 → 发布检查”的顺序执行。送审只创建或重用开放审核任务，不代表完整性门禁已通过；`human_verified` 只能由 reviewer 的 Revision 级 `approve` 事务产生。证据编辑、来源裁决和关系裁决都会递增 Revision 版本并要求重新送审。

## 8. 低操作负担与防误操作

管理端追求的是“减少重复录入”，不是隐藏审核依据：

- 候选创建允许最小信息，审核通过必须满足完整性；
- 已有来源和字段证据自动带入，不要求重复粘贴；
- 编辑页按“基础事实—地图—时间—来源—关系—投影”分区保存；
- 常规保存自动生成 candidate Revision，不反复弹确认；
- 发布、退役、角色变更等高风险操作才使用二次确认；
- 驳回 reason code 使用可搜索列表，说明可选但不能包含凭证/私人信息；
- 批量操作先预览影响，部分失败逐项报告，不制造全成功假象；
- 所有状态显示业务名称和机器状态，不只用颜色区分。

## 9. 用户端与管理端数据边界

| 数据/能力 | 用户端 | 管理端 |
|---|---:|---:|
| published 地点摘要 | 读取 | 读取和发布 |
| candidate/staging | 不可见 | 按权限读写 |
| 来源 URL/许可摘要 | 只展示必要来源类型 | 查看完整登记元数据，不展示凭证 |
| 管理审核说明 | 不可见 | 按权限查看 |
| projection hash/拒绝码 | 不直接展示 | 发布页查看 |
| 管理员身份和角色 | 不可见 | O16 管理 |
| 运行日志 | 不可见 | 受限运维访问，不在普通页面全文浏览 |
| 业务审计 | 不可见 | O15 只读查询 |
| Gate 7 原始研究材料 | 不可见 | 不进入普通管理端；独立受控存储 |

OM1 管理端应纳入 R0.3 Docker Compose，但不要求与用户 H5 使用同一前端构建物或公开入口。

阶段门禁必须分开理解：R0.2-05-03 批量进入 `human_verified` 前，O00/O01–O08/O16、服务端 RBAC 和追加式审计写入必须可用；O09 与 O15 的完整发布、快照和审计查询能力可在已审核数据基础上于 R0.2-07 完成，但必须早于任何正式研究快照发布。

## 11. OM1 不做

- 不建设微信小程序管理端；
- 不让管理端直接连接 MySQL；
- 不复制 Place/Revision/发布业务逻辑到前端；
- 不在管理端保存高德、和风、MySQL、Redis 密钥；
- 不把运行日志当作唯一业务审计；
- 不在 OM1 实现 M3 社区审核全功能；
- 不因管理端存在就允许 conditional 来源直接 published；
- 不提前拆管理微服务、多租户或重型工作流引擎。
