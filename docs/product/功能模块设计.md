## 1. 文档目标

本文不按代码包或技术组件罗列功能，而是从产品工程视角建立可追踪的功能架构：

```text
一级功能域 L1
└── 二级功能模块 L2
    └── 三级原子功能点 L3
```

- 一级功能域回答“产品为用户或运营方解决哪一类问题”；
- 二级功能模块回答“完成该问题需要哪些相对独立的能力集合”；
- 三级功能点必须能够单独描述前置条件、业务规则、状态、权限和验收结果，后续可直接映射到用户故事、页面、API、数据实体与研发任务；
- 技术组件只作为支撑能力出现，不与用户功能混为同一级别。

### 2.4 低操作负担设计原则

M1 采用“默认简单、逐步展开、结果可调”的交互模型。功能完整性不等于让所有参数同时出现在用户面前。

```text
系统无法可靠推断的关键事实 → 主流程询问
系统可以给出安全建议的参数 → 自动填入并允许修改
低频但有价值的控制点       → 高级设置按需展开
纯算法和契约参数             → 不向普通用户暴露
```

每个用户输入按以下四类管理：

| 输入类别 | 定义 | 默认交互 | 是否保留控制权 |
|---|---|---|---|
| 核心必填 R | 系统无法可靠推断，且缺失会使行程边界不成立 | 主流程直接展示 | 是，用户直接输入 |
| 推荐选择 S | 有助于改善体验，但存在合理默认值 | 默认选中，可一键更改或跳过 | 是 |
| 高级调整 A | 低频、专业或只在特殊场景需要 | 默认折叠，在摘要与结果页提供入口 | 是 |
| 系统推导 D | 可根据结构化数据、Provider 或规则可靠计算 | 不要求填写，展示推导结果与来源 | 在安全允许时可覆盖 |

默认值必须满足：可解释、可查看、可覆盖、可追溯。系统不能以减少操作为由静默使用 `0`、吞掉数据缺失或绕过硬约束。

### 2.5 M1 输入负担模型

| 输入/参数 | 分类 | 主流程表现 | 默认/推导策略 | 修改入口 |
|---|---|---|---|---|
| 目的地 | R | M1 直接显示“杭州”，无需重复选择 | 当前唯一开放城市 | 多城市开放后在创建入口修改 |
| 开始/结束日期 | R | 日期范围选择器 | 无 | 创建页 |
| 首日到达时间 | R | 时间选择器 | 无 | 创建页或结果页“调整条件” |
| 末日离开时间 | R | 时间选择器 | 无 | 创建页或结果页“调整条件” |
| 到达交通类型 | R | 快捷选项，必须选择或确认 | 可预选最近值或高频值，但不能静默确认 | 创建页；通常 1 次操作 |
| 离开交通类型 | R | 显式展示“与到达方式相同” | 默认继承已确认的到达方式 | 仅在“返程方式不同”时展开；通常 0 次操作 |
| 旅行节奏 | S | 三个语义化选项 | 默认“适中” | 创建页或结果页 |
| 同行人群 | S | 快捷项，可跳过 | 默认“普通成人同行/未指定” | 创建页 |
| 到达后接驳时间 | A/D | 主流程只显示系统预留摘要 | 交通节点/方式对应默认或 OD | “时间预留”高级设置 |
| 提前到站时间 | A/D | 主流程只显示系统预留摘要 | 按交通方式安全默认 | “时间预留”高级设置 |
| 末景返程时间 | A/D | 系统推导，不单独要求填写 | 目的地 OD；无数据时要求确认建议值 | “时间预留”高级设置 |
| 单日活动时间 | A | 不在主流程展示 | 冻结默认 09:00–21:00 | “每日时间”高级设置，进入实现前需评审契约影响 |
| 景点游览时段偏好 | A | 不在批量创建流程逐项询问 | 用户覆盖 > 策展 > 公开攻略综合 | 景点卡片或结果页就地调整 |
| 天气依据 | D | 不要求输入 | 自动选择预报或气候参考 | 只查看来源，不允许伪造 |
| 景点开放时间 | D | 不要求输入 | 已验证结构化数据 | 用户只可报告错误 |
| 有向 OD | D | 不要求输入 | 地图 Provider 或版本化快照 | 用户只查看真实/近似标识 |
| 晚餐留白 | D | 不在创建时询问 | 求解器 90→60→未安排 | 结果页解释；自定义属于后续评审项 |

### 2.6 三步主流程

M1 首次生成最多采用三个主步骤，不为内部原子功能点创建同等数量的页面或操作：

```text
步骤 1：什么时候去
杭州 + 日期 + 到达/离开时间 + 确认到达交通方式
返程方式默认显式继承，只有返程不同时再选择
系统在底部显示“已预留接驳与返程时间 [查看或调整]”

步骤 2：想去哪里
搜索/筛选 + 选择景点 + 已选清单

步骤 3：确认并生成
行程摘要 + 默认节奏/同行人群 + 系统将自动考虑的约束
[生成行程] [调整偏好] [高级设置]
```

用户在默认设置下必须能够直接完成生成；高级设置不是必经步骤。

交通类型属于必须明确的业务事实，但 `R` 不等于必须展示空白表单。到达方式可以预选，但必须由用户选择或确认；离开方式可以从已确认的到达方式继承，并在摘要中显式展示。系统不得在用户无感知时假定其乘坐高铁。

### 2.7 必填事实的确认状态

为兼顾业务可靠性与低操作负担，R 类字段记录“值”和“确认状态”，不能只记录最终枚举：

| 状态 | 含义 | 是否允许生成 |
|---|---|---:|
| `unresolved` | 没有可靠值 | 否 |
| `suggested` | 系统预选，但用户尚未确认 | 否 |
| `confirmed` | 用户直接选择或确认 | 是 |
| `confirmed_by_inheritance` | 从用户已经确认的关联字段继承，且界面明确展示 | 是 |
| `overridden` | 用户修改了建议值或继承值 | 是 |

M1 典型状态：

```text
arrival_transport_type = high_speed_rail
arrival_confirmation   = confirmed

departure_transport_type = high_speed_rail
departure_confirmation   = confirmed_by_inheritance
```

如果用户选择“返程方式不同”，离开方式转为 `unresolved`，直到用户选择后成为 `overridden/confirmed`。

## 3. 用户角色与服务对象

| 角色 | 说明 | M1 权限边界 |
|---|---|---|
| 匿名规划用户 | 未登录，通过浏览器临时身份创建行程 | 创建、选择、生成、查看、保存到当前设备、反馈 |
| 已登录用户 | 通过微信等身份登录 | 在匿名能力上增加跨设备保存、历史行程和分享归属 |
| 景点数据运营 | 维护景点硬事实、来源、冲突和版本 | 导入、校验、发布，不可修改求解器规则 |
| 产品/验证人员 | 查看漏斗、反馈与假设验证证据 | 只读分析，不可直接篡改业务审计记录 |
| 系统管理员 | 配置 Provider、权限和运行参数 | 不能绕过数据门禁发布未校验硬事实 |

## 6. 三级功能点清单

### 6.1 一级功能域 1：旅行需求建档

#### 1.1 行程草稿

| ID | 三级功能点 | 里程碑 | 优先级 | 核心规则与输出 | 验收口径 |
|---|---|---|---|---|---|
| 1.1.1 | 新建行程草稿 | M1 | P0 | 创建唯一 `draft_id`，初始状态为 `editing`；不要求先登录 | 用户可从空白状态进入建档，刷新后仍能识别同一草稿 |
| 1.1.2 | 自动保存草稿 | M1 | P0 | 字段变更后本地防抖保存；可选同步服务端；保存失败不阻塞继续填写但必须提示 | 已填写字段在刷新、后退再进入后不丢失 |
| 1.1.3 | 恢复未完成草稿 | M1 | P0 | 检测同设备最近未完成草稿，允许继续或放弃 | 用户选择继续后恢复最后成功保存版本，不混合两个草稿 |
| 1.1.4 | 放弃草稿 | M1 | P1 | 二次确认后标记 `abandoned`；已生成行程不随草稿删除 | 放弃后不再自动弹出；操作可审计 |

#### 1.2 目的地与日期

| ID | 三级功能点 | 里程碑 | 优先级 | 核心规则与输出 | 验收口径 |
|---|---|---|---|---|---|
| 1.2.1 | 确认目的地城市 | M1 | P0 | M1 直接展示杭州，不要求用户重复选择；其他城市显示“尚未开放”，不得伪造数据 | 用户无需额外操作即可确认杭州；只有已发布数据版本的城市可进入下一步 |

| 1.3.3 | 推导并调整到达后接驳时间 | M1 | P0 | 系统按交通节点/方式给出建议并默认应用；主流程只显示预留摘要，用户在高级设置中覆盖；保留来源 | 默认路径无需填写；C4 使用已确认或系统建议值；无法可靠推导时必须请求用户确认，不能按 0 处理 |

## 7. M1 首个纵向切片

### 7.1 纳入范围

首个用户可操作版本只纳入形成端到端闭环所需的 P0，并遵守“三步主流程、默认设置可直接生成”：

```text
匿名新建草稿
→ 步骤 1：确认杭州、选择日期、填写到达/离开时间
→ 选择或确认到达交通方式；返程方式默认显式继承
→ 系统推导接驳、提前到站和末景返程，并显示可调整摘要
→ 步骤 2：搜索/筛选并选择景点
→ 步骤 3：确认摘要，以默认“适中”节奏直接生成或按需展开高级设置
→ 数据门禁 + 阶段性完成的核心求解器（按稳定且版本化的契约调用）+ 质量门 + 审计
→ 展示每日时间线、交通、天气、晚餐和节奏提示
→ 展示未排入、硬失败和软降级
→ 保存并恢复结果
```

### 7.2 暂不纳入

- 微信登录与跨设备同步；
- 分享卡片；
- 行程编辑和修订历史 UI；
- 用户自定义游览时段偏好；
- 真实在线地图与天气 Provider；
- 异步任务、Celery、WebSocket；
- LLM 行程解释；
- 多城市和受控多样性；
- 可视化运营后台。

这些能力已经在功能树中预留，不阻塞首个切片。首个切片使用版本化杭州数据、天气与 OD 快照，但必须如实显示来源和精度。

### 7.3 用户操作复杂度门禁

| 指标 | M1 目标 | 说明 |
|---|---:|---|
| 首次生成主流程步骤 | 3 步 | 什么时候去、想去哪里、确认并生成 |
| 默认路径直接输入组 | 不超过 7 组 | 不把推导参数逐项变成表单 |
| 纯键盘输入字段 | 不超过 2 个 | 日期、时间、枚举优先使用选择器 |
| 默认设置可直接生成比例 | ≥ 80% | 除推导失败或输入矛盾外不要求高级设置 |
| 从进入创建到首次点击生成 | 中位数 ≤ 3 分钟 | 通过可用性测试和埋点验证 |
| 单项偏好调整跳转 | 最多 1 次 | 结果页就地入口，保留其他输入 |
| 字段错误定位率 | 100% | 不只给页面级“参数错误” |
| 失败后明确下一步比例 | 100% | 修改、换景点、重试等建议可执行 |
| 普通用户可见算法参数 | 0 | 不暴露 seed、成本权重、缓冲比例等 |

交通方式的业务完整性不以点击数衡量：到达方式必须有用户确认，离开方式可以通过显式继承达到确认。大多数往返同方式用户的交通类型操作目标仍为 1 次。

高级设置展开率、默认值覆盖率和生成后返回修改率作为观察指标，不预设“越低越好”；它们用于发现默认值和信息架构是否合理。

### 7.4 不向用户暴露的控制面

以下属于系统契约和安全底线，不是用户偏好：

- 硬约束 C1/C2/C4/C5/C6 的开关；
- 建议时长硬比例、交通缓冲比例；
- OR-Tools 搜索时限、drop penalty、成本权重；
- random seed 和内部聚类参数；
- 数据门禁与质量门是否启用。

用户调整使用业务语言，例如“悠闲一点”“希望晚上去”“多留一点返程时间”“不去这个景点”，由应用层转换成受控结构化输入。
