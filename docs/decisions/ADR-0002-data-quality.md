# ADR-0002：硬事实字段数据建模与质量门禁结论（Data Quality Spike）

- **状态**：已接受
- **日期**：2026-08-21
- **决策者**：工程（AI 协作 Spike 产出）
- **关联假设**：H3（数据准确是 H3「硬约束 100% 正确」成立的前提）
- **关联代码**：[spike/data_quality_spike/](../../spike/data_quality_spike/)

## 背景与问题

求解器的正确性 100% 依赖景点「开放时间/闭馆日」的准确。技术选型文档把「景点列表 + 基础标签」标为低复杂度，但这是**被低估的隐藏关键路径**。本 Spike 用 9 个真实杭州景点公开数据，量化硬事实字段的复杂度与失败模式。

## 结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | 单一 `open_time`/`close_time` 字段**不足以表达**现实 | 夏令/冬令、工作日/周末/节假日、暑期延长、闭园随演出顺延，均需**按日期区间的多套时间窗** |
| 2 | 闭馆日字段有「例外」和「时效」两大风险 | 省博物馆「周一闭馆，遇法定节假日顺延」；伞博物馆 2023 从周一改周二闭馆 |
| 3 | **数据保鲜 > LLM 抽取精度** | 即使抽准也会抽到过期数据（伞博物馆「周一闭馆」）或错误口径 |
| 4 | 时间语义需锁定「有效入园截止」 | 一个景点有停止售票/停止入园/清场/闭园多口径，不同源混用 |

## 决策

1. **数据模型升级**：`open_time`/`close_time` 改为「日期区间 → 时间窗」规则表（含 `last_entry` 有效入园截止），按出行日期解析当天时间窗。M1 字段：
   `time_rules JSON = [{date_range, open_min, close_min, last_entry_min}]`
2. **闭馆日支持例外**：`close_day` + `close_day_exception`（如「法定节假日开放」）。M1 维护一张节假日例外表。
3. **质量门禁**：所有景点字段带 `data_source` + `fetched_at`（抓取时间戳）+ `data_verified`；**「开放时间 + 闭馆日」M1 100% 人工校准**后才进求解器（失败后果严重、样本小、可承受）。
4. **多源冲突检测**：同字段多源不一致时（雷峰塔价格 40 vs 95、宋城场次）标记 `conflict=1`，人工裁决，不以任意单源为准。

## 备选方案与权衡

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 单一 open/close + 人工抽查 | 实现最简单 | 无法表达季节性/例外，错误率高 | ❌ 不采纳 |
| B. 日期区间时间窗 + 100% 人工校准 | 正确性最高，M1 规模可承受 | 人力成本，M2 不可扩展 | ✅ M1 采纳 |
| C. 全自动爬虫 + LLM + 抽样 | 可扩展 | 闭馆日过期/多源冲突难自动裁决 | ❌ M2+ 再评估 |

## 后果

- **正面**：杜绝「周一排闭馆博物馆」「季节时间错误」这两类最低级错误，守住 H3。
- **代价**：M1 需投入人工校准 80–120 个景点（约 2–3 人天）；`fetched_at` + 冲突检测增加数据管道复杂度。

## 何时推翻重议（触发条件）

1. **M2 扩展到 2–3 城市、景点数破千时**：「100% 人工校准」不可扩展，需重议自动化比例 + 爬虫→校验→冲突检测管道（技术选型文档 7.5 已预留）。
2. **若发现某类字段（如体力/类型）LLM 抽取准确率 > 95% 且稳定**：可将该类字段降级为「LLM + 抽样抽检」，释放人工校准人力。
3. **若引入官方数据源**（景区官方 API/OTA 联盟）：`data_source` 可信度分级，官方源可降级抽检比例。
