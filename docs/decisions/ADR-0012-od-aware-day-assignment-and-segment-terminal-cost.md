# ADR-0012：OD 感知分天与分段终端成本

- 状态：Accepted
- 日期：2026-08-26
- 产品里程碑：M1
- 实现优先级：P0
- 关联：ADR-0003、ADR-0004、ADR-0009、ADR-0010、ADR-0011、H3、C1、C2、C4、C5、C6

## 背景

高德真实有向 OD 快照首次进入 `ProductionSolverGateway` 后，硬约束、景点守恒和结果结构均通过，但路线体验暴露出两个软目标缺陷：

1. 用户未指定日期时，Gateway 只按建议时长、体力、数量和日容量派生默认日期，不感知真实 OD，导致灵隐寺与飞来峰等近邻景点被拆到不同天，并形成跨区往返；
2. Step 3 把日间和晚间节点分别求解后再合并，日间 OR-Tools 只计算日间内部边，没有计算日间末节点前往晚间首节点的成本。因此在“浙江省博物馆、西湖湖滨、湖滨晚间表演”场景中，日间内部仅相差 1 分钟的顺序可能让晚间衔接额外增加约 15 分钟。

这两项不是 C1/C2/C4/C5/C6 硬约束缺失，也不改变公开结果结构，但会改变稳定主方案的软优化语义，必须升级约束版本并留下可回放决策。

## 决策

### D1 默认日期偏好使用已发布 OD 聚类

当用户没有显式日期偏好时，Gateway 使用本次求解已经加载的、版本化的 `TravelTimeProvider` 生成中性日期偏好：

- A→B 与 B→A 取对称接近成本，保留真实有向边的差异，不假设二者相等；
- 使用确定性的 average-linkage 层次聚类；
- 最大簇大小为 `ceil(N / days)`，避免一个簇吞并全部景点；
- 只缺一个方向时施加稳定惩罚；两个方向都缺失时使用确定性大成本；缺边绝不按 0 分钟处理；
- 聚类完成后再按日期容量、建议时长、体力和数量稳定分配；
- 相同输入快照、数据快照、版本和 seed 必须得到相同结果。

OD 聚类只生成默认日期偏好，不直接决定最终日期。Step 1 的 `assign_days()` 仍负责闭馆日、开放窗口、首末日锚点、极端天气、容量和跨天重分配；因此该启发式不得绕过 C1、C2、C4 或 C5。

### D2 Step 2 继续负责天内硬可行排序

分天聚类不代替 OR-Tools。每一天仍使用已发布 OD 和时间窗完成硬可行排序，C6 缺边仍按不可衔接处理。聚类结果不能把不可用景点强行留在某天，也不能让景点静默丢失。

### D3 日间路线包含前往晚间首节点的终端成本

存在晚间段时，Step 3 按以下顺序执行：

1. 先求解晚间段并确定其首节点；
2. 求解日间段时，把“候选日间末节点 → 晚间首节点”的真实 OD 加到 OR-Tools 路线成本；
3. 日间与晚间合并时，再按真实 OD 计算到达时间、缓冲和 C6 可行性。

终端 OD 只用于选择更合理的日间顺序，不加入 OR-Tools 时间维度，避免把同一段交通重复计时。最终结果中的交通耗时、距离、模式和 basis 仍由合并阶段保存。

### D4 版本组合

本次不改变请求结构、公开结果字段或默认数值参数，版本组合为：

```text
solver contract    = solver-p1-v2
result schema      = trip-result-v2
constraint version = constraints-p1-v3
parameter version  = parameters-p1-2026-08-25
```

保留历史 `solver-p1-v1`、`constraints-p1-v1/v2`、`parameters-p1-*` 和 `DEFAULT_SOLVER_P1_CONTRACT` 标识。历史 TripRevision 不迁移、不覆盖、不原地重算；新生成 Revision 使用 V3 软目标语义。

## 验证证据

同一份 42/42 高德有向边、0 approximate、0 missing 的杭州快照离线回放：

```text
修复前：约 23,195m / 109min
修复后：    7,594m /  50min
```

修复后稳定分天与顺序：

```text
Day 1：飞来峰 → 灵隐寺
Day 2：浙江省博物馆 → 西湖湖滨 → 湖滨晚间表演
Day 3：河坊街 → 雷峰塔
```

道路距离约减少 67%，接驳时间约减少 54%；7/7 景点守恒、0 未排入、4/4 实际连接均为 `basis=gaode`，硬质量门禁通过。该证据证明本样本的路线质量缺陷被修复，不等同于 H3 已通过真实专家或用户验证。

## 影响与代价

- 默认分天需要访问已经发布到内存的完整 OD 快照，但求解过程中不调用高德 HTTP；
- 缺边惩罚会降低相应组合进入同一簇的概率，但最终 C6 仍以真实边可用性为准；
- 软目标变化会使新 Revision 与 V2 旧 Revision 的稳定主方案不同，这是版本升级后的预期行为；
- 当前仍需校准真实游客入口坐标，并完成正式 PublishedDataProvider、配额监控和旧快照继续服务策略。

## 验收

- 灵隐寺/飞来峰、西湖湖滨/晚间表演等近邻组合在固定 OD fixture 中稳定同日；
- 非对称 OD 场景稳定选择“浙江省博物馆 → 西湖湖滨 → 晚间表演”；
- 所有景点守恒，硬约束违反数为 0；
- 同一回放键的结果哈希一致；
- 真实快照离线回放保持 7,594m/50min、4/4 高德连接；
- Golden、降级、接近度、数据校验、性能与全量测试门禁通过。

## 何时重新评审

- M2 引入酒店、餐厅或用户锁定节点，需要联合分天与跨段全局优化；
- 正式城市规模或 OD 缺边率使层次聚类性能、稳定性或质量不可接受；
- 专家/用户证据显示 average-linkage 和当前容量策略持续产生不合理分天；
- 目标函数改为距离、费用、换乘次数、多目标 Pareto 或受控多样性候选池；
- 高德以外 Provider 的模式语义或缺边规则无法映射到当前对称成本。
