# ADR-0019：管理端、管理 API 与治理审计边界

- **状态**：已接受
- **日期**：2026-08-29
- **决策者**：产品 + 工程
- **关联里程碑**：M1、OM1
- **关联 Gate**：G7-R0.2～R0.4
- **关联决策**：ADR-0005、ADR-0018

## 背景与问题

项目已经具备来源 registry、字段字典、Place/Revision、几何、访问点、时间规则、地点关系、选择互斥组、求解投影和 published 发布门禁，但这些能力当前只能通过代码、CLI 或数据库仓储调用。要求数据审核人员直接编辑 JSON、调用 Python 或操作 SQL，无法形成稳定、低差错、可审计的人工作业闭环。

现有产品文档中的 `O10–O14` 只面向 M3 景点讨论和举报治理，不能承载 M1 Gate 7 前的地点候选、事实审核、重叠裁决和研究快照发布。与此同时，若为管理端复制一套独立后端和发布逻辑，又会产生双写、门禁漂移和绕过审计的风险。

## 决策

### D1 管理端是独立产品面，不是用户端隐藏页面

建立桌面优先的内部管理 Web 应用。管理端拥有独立入口、路由、身份、权限和导航，不进入普通用户 H5/微信小程序导航，不复用匿名旅行用户身份。

管理侧里程碑使用 `OM1–OM4`，管理原子功能使用 `ADM-*`，管理页面使用 `O00–O16`。`P0/P1/P2` 仍只表示当前里程碑实现优先级。

### D2 两套前端共享一套领域与应用能力

M1/OM1 采用：

```text
用户端 Taro/React ──用户 API──┐
                              ├── FastAPI application/domain ── MySQL/Redis/Provider
管理端 React Web ──管理 API───┘
```

- 用户 API 和管理 API 路由、认证上下文和 DTO 分离；
- Place、Revision、审核、发布和审计业务规则只在领域/应用层实现一次；
- 管理端禁止直连 MySQL；
- 当前不拆独立管理后端微服务；达到独立扩缩容、合规隔离或团队边界触发条件后再评审。

### D3 管理 API 使用独立前缀和服务端 RBAC

管理 API 前缀固定为：

```text
/api/v1/admin
```

管理侧角色目录：

```text
data_editor
data_reviewer
data_publisher
research_viewer
content_moderator
admin_security
```

OM1 启用 `data_editor`、`data_reviewer`、`data_publisher`、`research_viewer` 和 `admin_security`；`content_moderator` 在 OM3 内容治理启用。角色可以组合授予，但审核、发布和权限管理仍分别校验，不能因拥有其中一个角色自动获得其他权限。

前端隐藏按钮不构成权限控制。每个管理写请求必须在服务端校验管理员会话、角色、资源状态、乐观锁/幂等键和业务门禁。普通匿名/登录旅行主体不能兑换或继承管理员权限。

### D4 published 仍只能通过既有领域门禁

管理端只是操作面，不新增绕过路径：

- candidate/staging 可以编辑并产生新 Revision；
- human_verified 必须有审核决定；
- published 只能调用 `publish_projection` 或后续同语义应用用例；
- 已发布 Revision 不原地修改；变更创建新 Revision；
- 回滚通过切换已发布快照或发布新版本实现，不覆盖历史 TripRevision 和研究 environment。

### D5 运行日志与业务审计分离

ADR-0005 的每日 debug/info/error 文件和月度 ZIP 继续用于运行诊断。管理行为另存结构化、可查询、追加式业务审计，至少记录：

```text
audit_event_id, actor_id, actor_role, action,
target_type, target_id, target_revision,
before_digest, after_digest, reason_code, reason_text,
request_id, result, occurred_at
```

运行日志清理不能删除业务审计。审计记录不保存密码、token、API Key、完整自由文本、第三方页面全文或未授权媒体。

### D6 OM1 在批量人工审核前落地

R0.2-04 候选发现仍可使用版本化 JSON/CSV/CLI，不等待完整管理端。R0.2-05 拆为：

```text
R0.2-05-01 管理身份、管理 API 和审计底座
R0.2-05-02 地点审核工作台 P0
R0.2-05-03 采集、归一、去重和人工审核
```

在 50–75 个研究地点批量进入 `human_verified` 前，管理员登录/RBAC、追加式审计底座和 O01–O08 的 P0 审核闭环必须可用；不得以 SQL 手工改状态替代。O09 发布中心和 O15 完整审计查询必须在 R0.2-07 正式发布研究快照前可用。

## 管理侧里程碑

| 里程碑 | 目标 | 与用户侧关系 |
|---|---|---|
| OM1 | 研究数据治理、地点审核、发布、权限和审计 | 支撑 M1 Gate 7；M1 数据发布前置 |
| OM2 | 多城市/服务目录运营、媒体与授权治理、质量效率 | 支撑 M2 深度信息、餐饮住宿、执行和小记 |
| OM3 | 评论/讨论/举报/申诉、反垃圾和实时服务运营 | 必须先于 M3 公开社区和动态服务 |
| OM4 | 用户共创、AI 生成内容治理、长期偏好纠错和商业透明 | 支撑 M4 记忆与生态 |

## 安全与部署边界

- 管理端使用桌面 Web，不建设微信小程序管理端；
- 管理端构建产物和用户 H5 分开，可由同一 Compose 项目管理不同容器；
- 生产/受控环境必须 HTTPS；初期可叠加邀请访问或 IP allowlist；
- API Key、MySQL/Redis 凭证只由服务端 Secret 注入，不进入管理端 bundle；
- 高风险发布/退役操作需要理由、确认和审计；双人复核作为 OM1 P1，根据团队规模启用；
- 管理端不能浏览 Gate 7 原始录音、联系方式或未授权私人旅行材料，研究证据继续使用独立受控存储。

## 备选方案与权衡

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 继续只用 JSON/CLI/SQL | 开发量最小 | 审核门槛高、差错和越权风险大、地图/版本对比不可用 | 否决 |
| B. 在用户端隐藏管理员页面 | 复用前端工程 | 身份、导航和泄露边界混乱，移动端不适合地图审核 | 否决 |
| C. 独立管理前端 + 共享后端领域能力 | 操作面清晰，规则单一，M1 成本可控 | 需要新增 RBAC、管理 API、审计和桌面 UI | 采纳 |
| D. 独立管理微服务和独立数据库 | 隔离强 | M1 过重，容易双写和发布门禁漂移 | 暂不采纳 |

## 后果

- R0.2-05 前新增 OM1 P0 实现切片；
- 功能、UI、交互、架构、API、数据模型和 Gate 7 计划均需登记管理侧；
- `O10–O14` 保留为 OM3 内容治理页面，不再代表全部管理端；
- 当前 `0006_place_catalog` 不因本 ADR 被改写；管理身份、审核任务和审计表通过后续新迁移追加；
- 管理端设计完成不等于 OM1 已实现，也不改变当前 G7-R0.2-04 节点。

## 何时重议

1. 管理 API 需要独立部署、独立网络域或独立合规责任主体；
2. 多城市/多团队并行导致单体应用权限和发布吞吐成为瓶颈；
3. 审计需要外部 WORM、SIEM 或法规规定的双人复核；
4. 管理端需要对第三方运营机构开放并形成租户隔离；
5. 单机 Compose 不再满足可用性或安全要求。
