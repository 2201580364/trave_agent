# ADR-0010：真实路网、用餐节点与日内时间展开演进

- **状态**：已接受（分阶段实现）
- **日期**：2026-08-25
- **决策者**：产品 + 工程
- **关联假设**：H3、H7
- **前置**：ADR-0004、ADR-0005、ADR-0008、ADR-0009

## 背景

首个浏览器纵向切片暴露了三个不能仅靠“景点全部排入”解释的体验问题：

1. 当前本地 OD、接驳时长和交通方式是坐标距离近似，误差可能显著，不能作为生产路线承诺；
2. 午餐由结果空档派生，晚餐是求解软块，尚不支持用户选择具体餐厅后重新求解；
3. 交通最短且硬可行的路线可能把普通景点全部压在上午，在固定晚间活动前留下无解释的长下午空档。

因此，行程质量不能再只定义为“硬约束零违反 + 景点守恒”，还要确保上午、下午、晚上的安排可理解，空档有合理用途，展示语义不制造虚假的分钟级承诺。

## 决策

### D1 近似 OD 的使用边界

坐标直线距离、统一速度和绕行系数只允许用于：

- 本地开发 fixture；
- 外部地图 Provider 不可用时的透明降级；
- 自动化测试中的确定性输入。

近似 OD 不得被描述为真实道路距离、真实交通方式或生产级接驳时长。页面必须展示 `approximate` 依据和实时导航确认提示。

### D2 M1 接入高德真实有向路网

高德 Provider 属于 `M1 / P0`，至少返回：

```text
origin entrance coordinate
destination entrance coordinate
directed distance
travel mode
travel duration
basis / provider version / fetched_at
```

要求 A→B 与 B→A 独立；优先使用景点实际入口而不是几何中心；步行、公交/地铁、驾车等模式分别请求和保存。Provider 必须具备超时、限流、缓存、缺边和降级策略，任何缺失不得填 0。

### D3 午晚餐分阶段进入求解

M1 阶段先保留午餐、晚餐软留白：

- 午餐优选窗口 `11:30–14:00`，完整留白 60 分钟；
- 晚餐沿用版本化的 90/60 分钟软块；
- 用餐留白不得挤掉固定表演、突破开放时间或制造 C6 假衔接；
- 无法安排时输出结构化降级，不把景点静默移除。

当前午餐仍由稳定结果空档派生，属于过渡实现；进入餐厅节点能力前，应将午餐软块完整纳入求解和审计。

### D4 餐厅是可选真实行程节点

`M2 / P1` 支持用户在生成结果后添加或替换午餐地点、晚餐地点。餐厅节点至少包含坐标、营业规则、最晚到店、建议用餐时长、预约/排队依据和数据版本。

餐厅推荐与求解职责分离：推荐系统负责候选、口味、评分和排队信息；求解器负责餐厅节点的时间窗、真实 OD、用餐时长和全行程可行性。

### D5 添加餐厅必须完整重排并生成新 Revision

添加餐厅不是前端插卡片。系统必须：

```text
旧 TripRevision
→ 新草稿/输入快照
→ 餐厅作为真实节点
→ 重新加载开放时间和真实 OD
→ 完整检查 C1/C2/C4/C5/C6
→ 生成新的不可变 TripRevision
```

旧 Revision 不原地覆盖；固定场次和用户锁定项不得被餐厅破坏。失败时保留旧 Revision，并返回具体冲突和可操作建议。

### D6 新增 DAY_SPREAD 日内时间展开软目标

当一天有两个及以上普通日间节点且存在真实空余容量时：

- 优先把计划停留时长从 C2 最低可玩时长扩展到发布的建议时长；
- 优先保留完整午餐空档；
- 以约 16:00 作为多节点宽松日程的稳定展开目标，单次额外延后最多 60 分钟；
- 固定晚间节点存在时，仍需为其前置接驳和完整晚餐留白保留容量；
- 不改变 OR-Tools 已选顺序，不为填满下午显著增加交通；
- 不突破建议时长、开放时间、最晚入园、日期锚点或交通衔接；
- 无法安全展开时回退到原硬可行方案。

该目标解决“所有普通景点都在上午完成、下午无解释留白”的问题，但不要求把全天机械填满。用户显式要求自由活动、休息或留白时，系统应保留并解释该空档。

### D7 区分四类空档

结果和后续质量指标必须区分：

1. 午餐/晚餐留白；
2. 景点之间必要的接驳和合理休息；
3. 用户主动要求的自由活动；
4. 没有解释的超长空档。

只有第 4 类进入无意义空档惩罚。当前 M1 先通过稳定展开规则避免明显问题，后续基于 Gate 7 数据校准阈值。

### D8 版本与门禁

输入输出结构未变，因此：

```text
contract_version = solver-p1-v1
```

软目标语义和默认参数已经改变，因此升级：

```text
constraint_version = constraints-p1-v2
parameter_version  = parameters-p1-2026-08-25
```

保留 `DEFAULT_SOLVER_P1_CONTRACT` 和历史 `solver-p1-v1` 机器标识。历史 Revision 继续保存并返回原版本，不进行原地重算。新版本必须重新通过 Gate 6 全量、Golden、降级、接近度和稳定回放门禁。

### D9 失败与降级

- 高德超时、限流或缺边：优先使用未过期缓存；仍不可用时允许透明近似降级，并标记原因；
- 餐厅关闭或无可行 OD：不破坏旧 Revision，提示更换餐厅、时间或取消餐厅节点；
- DAY_SPREAD 无安全空间：保留原硬可行时序；
- 午晚餐留白不足：结构化标记 reduced/unscheduled；
- 任何降级都不得伪装成真实路网或分钟级确定承诺。

## 验收场景

核心新增 Golden Case：

```text
Given 2 个普通日间景点 + 1 个 18:30 固定表演
And 当天有足够开放时间和真实交通容量
When 生成行程
Then 普通景点不会在午前全部结束
And 第二个日间景点覆盖下午时段
And 午餐存在完整软留白
And 18:30 表演和晚餐留白继续保留
And C1/C2/C4/C5/C6 违反数为 0
And 重复求解结果稳定一致
```

同时验证紧时间窗回退、真实 OD 缺失、Provider 限流、餐厅关闭、餐厅加入后新 Revision、旧 Revision 不变和结果回放。

## 后果

M1 的下一实施顺序调整为：先完成日内展开回归和 Gate 6 复验，再接高德真实路网；真实 MySQL 与部署仍需要完成，但不应掩盖当前路线质量缺陷。具体餐厅节点和餐厅加入后的重排进入 M2，午晚餐软块则继续在 M1 求解器内完善。
