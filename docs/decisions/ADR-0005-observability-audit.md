# ADR-0005：P1 日志、求解决策审计与数据变更审计

- **状态**：已接受
- **日期**：2026-08-22
- **决策者**：产品 + 工程
- **关联假设**：H3（失败归因与结果可解释）、H7（时间锚点效果验证）

## 背景与问题

P1 需要回答“为什么生成这份行程”以及错误来自数据、算法、外部服务还是交互。仅保存最终 itinerary 或把所有信息打印到 stdout，无法支持 H3 复盘、历史结果复现、硬事实变更追踪和生产故障定位。

同时，FastAPI 与 Celery 是多进程组件；多个进程直接争写同一日志文件存在交错和轮转风险。P1 不需要 ELK/Kafka 等重型平台，但需要明确的文件生命周期、级别分类、隐私边界和审计模型。

## 决策

### D1 文件日志按日、模块和级别分类

生产日志以 UTF-8 JSON Lines 文件为主，不依赖 stdout 作为唯一落点：

```text
logs/<component>/<level>/YYYY-MM-DD.log
```

- `component`：`api`、`worker`、`scheduler` 等；不再按进程实例/PID拆分；
- `level`：`debug`、`info`、`error`；
- `DEBUG` 进入 debug 文件；`INFO/WARNING` 进入 info 文件；`ERROR/CRITICAL` 进入 error 文件；
- 本地开发可选同时输出控制台，生产不依赖控制台归档。

同一模块的多个进程通过跨进程文件锁完整追加单行 JSON。写入采用“加锁 → 打开追加 → 写入并刷新 → 关闭 → 解锁”，避免日志碎片化，也避免月归档时仍持有旧月份文件句柄。

### D2 每月 ZIP 归档已结束月份

- 每天自动切换到新的 `YYYY-MM-DD.log`；
- 每月首次写日志或进程启动时，扫描并归档所有早于当前月份的日文件；
- 归档路径：`logs/archive/YYYY-MM/<component>-<level>.zip`；
- 写入和归档使用同一个模块/级别锁，避免压缩、删除与并发追加竞争；
- 先写临时压缩包并校验条目，再原子替换正式压缩包；
- 只有压缩成功并确认文件已进入压缩包后，才删除原始日文件；
- 当前月份文件不归档。

### D3 运行日志只保存允许字段

结构化日志公共字段：

```text
timestamp, level, logger, event, message,
request_id, task_id, trip_id, solve_run_id,
duration_ms, error_code, exception
```

禁止记录 API key、token、Cookie、数据库连接串、微信 openid 原值、手机号、精确家庭地址和未经筛选的自由文本。用户标识使用内部 ID 或不可逆标识。

### D4 求解决策审计与运行日志分离

运行日志用于故障定位，可按保留期清理；求解决策审计是业务记录，后续持久化到 `solver_runs`，至少包含：

```text
solve_run_id, solver_version, constraint_version, parameter_version,
input_snapshot_hash, data_snapshot_version, od_basis, weather_basis,
random_seed, duration_ratio, assignments, unplaced reason codes,
input_count, scheduled_count, unplaced_count, data_rejected_count,
hard_constraint_violations, elapsed_ms, status, created_at
```

审计决策事件记录安排日期、跨天重排的原日期/目标日期、未排入或数据拒绝原因，以及最终硬约束违反。
纯求解函数不直接写文件或数据库；调用层通过纯转换层收集确定性结果并写审计，保持算法可测试。

### D5 硬事实变更使用 revision 审计

P1 后续新增 `attraction_revisions`，记录字段旧值/新值、来源、抓取时间、修改者、校准者和冲突裁决。不得只覆盖当前值而丢失历史依据。

### D6 保留期限

- 未压缩日文件：当前月；
- 压缩运行日志：默认 180 天，可配置；
- 求解决策审计：至少覆盖 P1 验证周期，默认 180 天；
- 景点硬事实 revision：P1 长期保留；
- 用户删除请求触发关联标识匿名化，不破坏统计和约束证据。

## 备选方案与权衡

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 只输出 stdout | 容器友好、最简单 | 不满足明确的本地周期归档要求，依赖外部采集 | ❌ 不采纳为唯一落点 |
| B. 标准库分级日文件 + 跨进程锁 + 月度 ZIP + DB 审计 | 日志集中、零运行时依赖、P1 足够 | 每条写入有打开/加锁开销 | ✅ 采纳 |
| C. ELK/Loki/Kafka + 专业审计平台 | 查询和扩展能力强 | P1 过重、运维成本高 | ❌ P2+ 再评估 |
| D. 无锁多进程共享同一轮转文件 | 文件少 | 多进程轮转和写入不安全 | ❌ 不采纳 |

## 后果

- **正面**：日志生命周期明确；错误可按级别检索；求解结果可复现和归因；数据变更可追踪。
- **代价**：需要磁盘容量监控、归档调度和清理任务；跨进程锁与逐条打开文件会增加少量 I/O。
- **技术债务**：P1 文件日志不支持跨实例集中查询；P2 多实例部署时需要接入集中日志平台。

## 何时推翻重议（触发条件）

1. 单模块日志吞吐导致锁等待明显，或需要跨机器实时检索时，评估 QueueListener、Loki 或云日志服务，文件仍可作为短期缓冲。
2. 日志写入或月归档明显影响请求/求解性能时，改为独立日志进程或平台采集。
3. 单月压缩日志超过 5GB 或磁盘占用超过实例容量 60% 时，缩短保留期并迁移对象存储。
4. 审计字段需要复杂查询、单个 `decision_trace` JSON 过大时，将求解决策拆成事件表。
5. 合规要求变化时，重新评估保留期、匿名化和访问控制。

## 实现要求

- 日志归档必须有安全测试：压缩失败时不删除源文件；
- 日志配置不得在 import 时隐式创建文件；由应用入口显式初始化；
- 求解器纯函数不得直接依赖 logger 或数据库；
- 日志和审计测试关联 ADR-0005/H3。
