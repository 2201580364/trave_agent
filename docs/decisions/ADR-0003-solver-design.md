# ADR-0003：M1 求解器详细设计决策（目标函数、分天算法、天气分层）

- **状态**：已接受
- **日期**：2026-08-21
- **决策者**：工程（G4 详细设计）
- **关联假设**：H3、H7
- **前置**：ADR-0001（Solver Spike）、ADR-0002（Data Quality Spike）

## 背景与问题

G3 两个 Spike 得出：收敛非瓶颈（毫秒级）、但单车辆 TSP-TW 需 AddDisjunction、K-Means 分天失衡需修正、数据需多套时间窗。G4 需明确三件此前模糊的事：**目标函数是什么、分天怎么做、天气如何分层**。

## 决策

### D1 目标函数（字典序）

```
min   Σ travel(aᵢ, aᵢ₊₁)          # 层次1：天内交通耗时
s.t.  C1-C6 全部满足（违反数=0）     # 层次0：硬约束，优先于任何优化
```
- 分天层面不设显式目标项，空间聚集由 K-Means 保证。
- **M1 只优化「交通耗时」一个量**。「同质化/季节/拥挤度」留 M2，避免 M1 目标函数膨胀导致不可解释。

### D2 分天算法（K-Means + 确定性容量修复）

- K-Means（K=D）按经纬度空间聚类 → **确定性**容量修复（超载天把「离质心最远」景点移到最空天）。
- 不采用 capacity-aware 聚类库 / DBSCAN：M1 单城市规模小，K-Means + 修复足够且可解释；M2 上多车辆建模时一次性解决（ADR-0001「何时重议」）。

### D3 天内排序（OR-Tools + AddDisjunction）

- 单车辆 TSP-TW，`AddDisjunction(penalty)` 允许丢弃放不下的景点，丢弃成本远大于交通成本 → 尽量排入、仅不可行时丢弃。
- `slack_max=240`（等开门上限，ADR-0001 教训：设 1440 会撑爆搜索空间）。

### D4 天气分层

| 时间跨度 | 数据源 | 处理 |
|---|---|---|
| 出行日期 ≤ 3 天 | 和风实时预报 | 可信，极端天气触发硬约束排除室外 |
| 出行日期 > 3 天 | **气候基线**（该月历史概率） | 只给「该月多雨」提示，**不判极端**，UI 标注「气候参考」 |

> 原因：和风免费版仅 3 天预报；旅行规划常为数周后，远期无法精确到某天台风。混用会夸大天气风险提示准确性（评审问题 #7）。

## 备选方案与权衡

| 议题 | 方案 | 结论 |
|---|---|---|
| 目标函数 | A 只优化交通 / B 多目标加权（交通+体力+体验） | ✅ A（M1 简单可解释，多目标留 M2） |
| 分天 | A K-Means+修复 / B capacity-aware 聚类 / C 直接多车辆 | ✅ A（M2 重议 → C） |
| 天气 | A 统一用预报 / B 分层预报+气候基线 | ✅ B |

## 何时推翻重议（触发条件）

1. **M2 引入住宿位置优化**：重评估 D2 → 多车辆建模（方案 A），一次性解「景点分配+住宿+排序」（ADR-0001 已记录）。
2. **若「交通耗时最小化」产出的行程用户不满意**（G7 归因到目标函数而非数据/交互）：在 D1 引入体验项（同质化/季节），写新 ADR。
3. **若和风 3 天预报对「周末短途游」覆盖不足**：评估接入付费中长期预报或改用 15 天气候趋势。

## 后果

- **正面**：目标函数、分天、天气三个模糊点全部明确，可直接进入 G5 约束 TDD。
- **代价**：分天「K-Means+修复」是已知过渡方案，M2 会重写为多车辆建模（一次性成本，可接受）。
