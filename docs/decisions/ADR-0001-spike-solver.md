# ADR-0001：M1 求解器分层路线可行性结论（Solver Spike）

- **状态**：已接受
- **日期**：2026-08-21
- **决策者**：工程（AI 协作 Spike 产出）
- **关联假设**：H3（硬约束正确 + 行程合理 → 认可「比手动排更合理」）
- **关联代码**：[spike/solver_spike/](../../spike/solver_spike/)

## 背景与问题

求解器是本产品最硬的技术壁垒（技术选型文档自评 ★★★★★）。团队无 OR 背景，因此在投入正式实现前，用可丢弃原型验证「K-Means 聚类分天 → 天内 TSP-TW → 约束校验 → 回溯」这条分层路线是否可行、收敛是否达标。

## 结论（Spike 证据）

| 结论 | 证据 |
|---|---|
| ✅ 分层路线逻辑可行 | 7/7 硬约束单测全绿（闭馆日 / 时间窗 / 锚点 / 天气 / 体力检测） |
| ✅ 收敛毫秒级，非瓶颈 | OR-Tools 单日 TSP-TW：N=12/D=3 max **1.6ms**；N=20/D=7 max **1.4ms**（<30s 达标） |
| ⚠️ 单车辆 TSP-TW 必须访问所有节点 | K-Means 把 5 个景点塞进一天（总时长超 9:00–21:00 预算）→ 无可行解（返回 None）。需 `AddDisjunction` 允许丢弃 |
| ⚠️ OR-Tools 优于贪心 | 同一天 OR-Tools 排入的景点数多于贪心「最近可行」（packing 更强） |
| 🔴 真正风险仍是 K-Means 分天均衡 | 纯经纬度 K-Means 不感知每日景点数/体力，会聚出失衡分组，靠 `rebalance` 事后打补丁不优雅 |

## 决策

M1 采用 **OR-Tools Routing Solver + AddDisjunction（可丢弃放不下的景点）** 做天内排序；**不接受**纯贪心启发式。K-Means 分天需替换为 **capacity-aware 聚类或 DBSCAN**（待定，见「何时重议」）。

## 备选方案与权衡

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 纯贪心最近可行 | 零依赖、简单 | 先到先得、局部最优、漏排景点 | ❌ 不采纳 |
| B. OR-Tools 单车辆 TSP-TW（硬访问） | 全局最优、快 | 不可丢弃，集群超载时不可行 | ❌ 需加 disjunction |
| C. OR-Tools + AddDisjunction | 全局最优、快、可降级丢弃 | 需正确设 penalty | ✅ 采纳 |

## 后果

- **正面**：收敛时间不再是约束，团队可专注「聚类均衡 + 数据质量」两个真风险点。
- **代价**：需维护 disjunction 的 penalty 参数；丢弃逻辑要配合「推荐每日上限景点数」的前置提示。
- **技术债务**：`rebalance` 是 K-Means 失衡的打补丁，需在详细设计阶段替换为 capacity-aware 聚类。

## 何时推翻重议（触发条件）

1. **M2 引入住宿位置优化时**：重评估**方案 A（多车辆建模）**——一次性求解「景点分配 + 住宿位置 + 天内排序」全局最优（技术选型文档 4.4 已记录）。
2. **若 K-Means 均衡问题在真实杭州数据上无法靠 capacity-aware 聚类解决**：提前上多车辆建模，而非继续打补丁。
3. **若某天景点数 > 10**（如用户选 15 个景点只排 2 天）：单车辆 + disjunction 可能丢弃过多，需评估「跨天交换」局部搜索（LNS）。

## 下一步

1. G4 详细设计：capacity-aware 聚类（每类限制景点数/能量）+ OR-Tools + disjunction 的具体设计。
2. 用 20 个真实杭州景点跑 **Data Quality Spike**（待高德 API key），量化 LLM 抽取开放时间/闭馆日准确率。
3. 把「每日上限」前置提示纳入 M1 交互设计（关联 H6/H7）。
