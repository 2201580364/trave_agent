# ADR-0008：游览时段软偏好与硬时间窗分离

- **状态**：已接受（S-F1 领域模型完成，S-F2 求解集成待实现）
- **日期**：2026-08-23
- **决策者**：产品 + 工程
- **关联假设**：H3（行程合理性与用户认可）
- **前置**：ADR-0004（约束分级）、ADR-0007（评审行程接近度）

## 背景

Gate 6 杭州接近度案例显示，河坊街在上午游览不违反开放时间，但与“晚间优选、下午可接受”的公开攻略综合节奏不一致。若直接缩窄 C2 开放窗口，会把“体验上不理想”错误表达为“物理上不能游览”；若完全忽略时段偏好，交通耗时的微小改善又可能长期压倒明显的旅游体验差异。

因此需要在求解器输入中显式建模游览时段软偏好，并与开放时间、最晚入园和固定场次彻底分离。

## 决策

### D1 三类时间语义不可混用

```text
开放时间/最晚入园/固定场次 → C2 硬时间窗
用户锁定时段               → 后续锁定能力，不属于本 ADR 的软偏好
优选/可接受游览时段         → 软偏好，只影响硬可行方案之间的选择
```

软偏好不得：

- 修改 `TimeRule`；
- 缩窄 `EffectiveTimeWindow`；
- 产生 C2 违反；
- 让原本硬可行的景点变成未排入；
- 覆盖固定表演或预约场次；
- 绕过最终 C1/C2/C4/C5/C6 复核。

### D2 使用稳定的三个时段桶

```text
morning   00:00–11:59
afternoon 12:00–16:59
evening   17:00–23:59
```

跨午夜时间使用当地时钟分钟取模后判断，例如 `25:00` 对应次日 `01:00`，归入 `morning`。时段边界属于版本化求解契约；未来如需按城市或旅行模式调整，必须升级参数版本。

### D3 偏好包含优选、可接受、来源和来源引用

```text
preferred_buckets
acceptable_buckets
source
source_ref
```

优选集合不能为空；P1 每个景点只允许一个优选时段，可接受集合可以包含其余时段；优选和可接受集合不得重叠；所有偏好必须保留来源引用，禁止无来源推断进入求解器。单一优选时段使 OR-Tools 的线性软上下界具有唯一、可解释的零成本区间；多峰偏好留待后续候选模型支持。

来源分为：

```text
USER
CURATED
PUBLIC_GUIDE_SYNTHESIS
```

优先级为：

```text
USER > CURATED > PUBLIC_GUIDE_SYNTHESIS
```

同一优先级出现互相冲突的结构化偏好时必须拒绝并要求上游裁决，不得按加载顺序静默选择。

### D4 评价结果分为三级

```text
PREFERRED  实际到达时段命中优选集合
ACCEPTABLE 实际到达时段命中可接受集合
FALLBACK   景点仍然硬可行，但未命中以上集合
```

`FALLBACK` 是体验降级，不是拒绝码。S-F2/S-F3 将为其增加版本化成本、输出提示和审计原因。

### D5 偏好属于行程请求上下文，不属于开放时间硬事实

基础景点实体继续只保存开放时间、闭馆、时长、室内外等事实。经过来源优先级解析后的有效时段偏好附着于 `AttractionPreference`，并随 `DayAllocation` 传播到日内路由。这样用户偏好可以覆盖策展或攻略偏好，而不会污染全局景点硬事实。

数据库可保存策展/攻略候选偏好，但 API 在每次行程请求中负责合并用户偏好并生成单一有效偏好。求解器不直接访问数据库，也不自行抓取或推断最佳时段。

## 分阶段实现

### S-F1（本次）

- 建立时段、来源、偏好和评价模型；
- 建立来源优先级与同级冲突检测；
- 将偏好从 `AttractionPreference` 传播到 `DayAllocation`；
- 复用同一时段桶函数进行接近度评估；
- 不改变当前路由目标和求解结果。

### S-F2（已实现首版）

- 在硬可行方案内使用 OR-Tools 时间维度软上下界引入时段偏差成本；
- 原始交通每分钟按 `30` 成本计，偏离优选时段每分钟按 `1` 成本计，使时段偏好只在交通质量接近时产生明显作用，避免为了偏好接受大幅绕路；
- 保持景点守恒、固定场次和最终硬约束门禁。

`30:1` 是 `parameter_version` 管理的 P1 初始实验参数，不是业务真理。丢弃罚分继续远高于交通和时段成本；偏好区间即使落在 C2 窗口外，也只推动到达时间靠近偏好，不会扩大硬窗口。

### S-F3

- 生成逐景点 `preferred/acceptable/fallback` 提示；
- 写入偏好来源、实际时段、偏差和降级原因审计；
- 同步 API 输出模型。

### S-F4

- 完整回归、性能、确定性和 Golden Case 验证；
- 冻结 P1 求解器输入输出契约；
- 转入功能模块和页面设计。

## 验收

1. `12:00` 明确属于下午，`17:00` 明确属于晚间；
2. 跨午夜 `25:00` 按次日 `01:00` 归入上午；
3. 用户来源覆盖策展和公开攻略来源；
4. 同级冲突不会静默覆盖；
5. 偏好从分天输入无损传播至日内分配；
6. 添加偏好本身不改变 C2 时间窗；
7. 没有偏好的现有输入和输出保持不变。

## 后果与重议条件

- **正面**：能够表达夜游、晨游等体验差异，不污染硬事实；偏好有来源、可覆盖、可解释。
- **代价**：S-F2 需要多目标权衡和更多回归；应用层需要保存来源与覆盖关系。
- **重议**：若用户测试显示三个时段桶过粗、时段偏好与满意度低相关，或交通近优容差造成明显绕行，则调整桶、来源策略或成本参数，并升级版本。
