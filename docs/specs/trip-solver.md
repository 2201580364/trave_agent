# 需求规格：一键生成分日行程（trip-solver）

- **关联假设**：H3（硬约束正确 + 行程合理）、H7（时间锚点）
- **关联指标**：行程生成 < 2min、硬约束通过率 100%、认可率 ≥ 70%
- **优先级**：P0（核心，承载 H3）
- **设计依据**：ADR-0001（Solver Spike）、ADR-0002（Data Quality Spike）、ADR-0003（目标函数/分天/天气）、ADR-0004（约束分级修订）

## 一、需求规格（Given/When/Then）

### S1 闭馆日（关联 C1）
```
Given 某景点 close_days=[1]（周一闭馆），出行首日为周一
When 求解器生成 Day 1 行程
Then 该景点不出现在 Day 1；若它周二可用，则分配到周二（而非丢弃）
```

### S2 建议时长软阈值（关联 C2、S1）
```
Given 某景点 17:00 闭馆、建议游览 2h、无入园截止
When 求解器当天 15:30 到达该景点（可玩 1.5h = 75% ≥ 60%）
Then 排入，并标注「实际可玩 1.5h（建议 2h）」

Given 同上景点，求解器当天 16:15 才能到达（可玩 45min = 38% < 60%）
Then 不排入（进入「放不下」池并带原因）
```

### S3 体力软约束（关联 S2）
```
Given 休闲模式，用户选了 2 个 4 星景点
When 求解器生成分日行程
Then 两个 4 星景点倾向分到不同天；若同天，输出「本日节奏偏紧」提示（不硬拦）
```

### S4 时间锚点（关联 C4、H7）
```
Given 到达 14:00 + 机场到市区 1.5h，离开 16:00 + 提前到站 1.5h + 末景返程 0.5h
When 求解器生成 Day 1 与 Day N
Then Day 1 首景开始 ≥ 15:30；Day N 末景结束 + 返程 ≤ 14:30
```

### S5 极端天气（关联 C5）
```
Given Day 2 天气为暴雨（extreme），某室外景点被选中
When 求解器生成 Day 2
Then 该室外景点被排除；若 Day 3 天气正常且可用，则移到 Day 3，否则替换为室内景点并标注原因
```

### S6 降级（N 过多）
```
Given 用户选了 30 个景点、2 天
When 求解器生成行程
Then 前置提示「每日建议不超过 X 个」；排不下的景点标注「未排入及原因」，不静默丢弃
```

## 二、硬/软约束清单（ADR-0004 定稿）

### 硬约束（物理上不能，违反数 = 0 才输出）

| 编号 | 约束 | 求解器位置 |
|---|---|---|
| C1 | 闭馆日：`weekday ∈ close_days → 不可排`（含节假日例外） | Step 1 可用性 |
| C2 | 入园时间窗：`arrival ∈ [open, min(last_entry, close − 0.6×duration)]` | Step 2 时间窗 |
| C4 | 时间锚点：Day1 首景 ≥ 到达+场站耗时；DayN 末景+返程 ≤ 离开−提前量 | Step 2 锚点 |
| C5 | 天气：extreme 排除室外 | Step 1 可用性 |
| C6 | 时间衔接：真实路网 OD | Step 2 transit |

### 软约束（体验，不硬拦）

| 编号 | 约束 | 求解器位置 |
|---|---|---|
| S1 | 建议时长比例 ≥ 60%（已编码进 C2 硬窗口），<100% 时输出「实际可玩 X min」 | 输出 |
| S2 | 体力均衡偏好（高体力景点分散）+「节奏偏紧/偏松」提示 | Step 1 均衡 + 输出 |

## 三、求解器算法设计（V3）

```
Step 1 分天（可用性感知 + 时间容量均衡）
  1a K-Means 按经纬度聚成 D 组（空间聚集）
  1b 可用性重分配：闭馆日/极端天气不可用的天，把景点移到「最近可用天」；
     无可用天才丢弃 + 原因（修 P0-3：不静默丢弃）
  1c 时间容量均衡：某天时长超窗时，把景点移到较空的天（只算时长+交通）
  1d 体力均衡偏好（软）：高体力景点倾向分散，不硬拦
  ↓
Step 2 天内排序（单车辆 TSP-TW，硬窗口，缓冲已折算）
  transit(i,j) = travel(i,j) × 1.2 + duration(j)   ← 缓冲折进 transit（修 P0-2）
  时间窗 CumulVar ∈ [open, min(last_entry, close − 0.6×duration)]
  锚点 Start/End；AddDisjunction 允许丢弃放不下的景点
  ↓
Step 3 时段拆分与填充
  日间景点与晚间-only 景点分离求解，合并顺序固定为「日间 → 晚间」；晚餐不作为固定硬分界
  晚间-only 景点（open ≥ 17:00）排在日间景点之后（不插入日间段，避免破坏时间窗）
  晚间-only 仅表示分段顺序，不代表 arrival 必须 ≥ 19:00；18:30 固定场次仍按其 C2 窗口排入
  晚餐是可移动软时间块：从剩余空档中优先预留 90min，可放在晚间活动前或后
  90min 放不下时降级为 60min；仍放不下则保留硬约束可行的景点并提示「晚餐时间紧张」
  晚餐本身不得产生硬约束拒绝或触发跨天迁移；只有 C2/C4/C6 失败才进入重排
  ↓
Step 4 约束校验
  硬约束全量校验（C1/C2/C4/C5/C6 违反数 = 0 才输出）
  行程级景点守恒：输入景点 = 已排入 + 未排入 + 数据门禁拒绝；检测缺失、重复和意外 ID
  生成分约束违反计数与质量门禁报告，供 Gate 6 验证和调用层审计使用
  体力软约束：计算每日体力，输出「节奏偏紧/偏松」提示
```

### 目标函数（字典序）

1. **层次 0（硬约束）**：C1/C2/C4/C5/C6 违反数 = 0，否则回退重排。
2. **层次 1（优化）**：最小化总交通耗时 `min Σ travel(aᵢ, aᵢ₊₁)`（真实路网 OD）。
3. 体力均衡在 Step 1 启发式体现，不进目标函数（ADR-0004）。

### 稳定主方案与后续受控多样性

P1 默认使用 `seed=0` 生成可审计重放的稳定主方案。系统重试必须沿用原 seed，不得造成结果漂移。

### 评审行程接近度

ADR-0007 将“行程合理”拆为固定项、分天、时段、同日组合与相邻顺序的可解释比较。评估必须在景点守恒及 C1/C2/C4/C5/C6 零违反之后执行；硬门禁失败不可由软接近度补偿。基线必须声明来源和版本，公开攻略综合不得称为专家金标。当前初始权重与 `0.75` 阈值仅作为 Gate 6 的版本化实验参数，后续由真实专家评审和用户研究校准。
“换一个方案”属于 ADR-0006 定义的 P2 显式能力：只能从通过相同硬约束、景点守恒、锁定项和
版本化近优阈值的候选池中选择。Gate 6 不直接引入随机行为。

## 四、输出标准

- 上午/下午/晚间景点（含建议时段与理由 + 实际可玩时长标注）
- 天气风险提示（区分近期预报 vs 气候基线）
- 室内替代建议（雨天）
- 未排入景点清单 + 原因（不静默丢弃）
- 体力节奏提示（偏紧/适中/偏松）
- 求解质量报告（景点守恒、C1/C2/C4/C5/C6 分项违反数）
- 每项安排的 👍👎 反馈入口

## 五、性能与降级

| 场景 | 目标 | 措施 |
|---|---|---|
| N ≤ 20, D ≤ 7 | < 2min | 天内独立求解并行 |
| N ≤ 12, D ≤ 3 | < 30s | 实测 OR-Tools 毫秒级 |
| N > 25 | 降级 | 前置提示 + AddDisjunction 丢弃 + 未排入标注 |
| 求解超时 | 兜底 | OR-Tools 超时返回 best-so-far（PATH_CHEAPEST_ARC 首解已内建） |

降级说明由纯转换层统一生成，不改变求解结果：景点数 `>25` 时提示选择过多；存在未排入时
必须给出数量和逐项原因；晚餐无法预留时输出“晚餐时间紧张”。OR-Tools 搜索状态必须区分
有解但未完成的 `best_so_far` 与超时无解的 `time_limit_no_solution`；每次 initial、reassignment、
final 搜索均保留尝试历史，跨天恢复不得覆盖超时证据。best-so-far 仍须通过最终硬约束复核。
