# 开放时间数据规范

> 属「硬事实」规范。求解器时间窗、LLM 辅助抽取和数据校验均以本规范与 [M1 数据模型](../specs/data-model.md) 为准。

## M1 字段定义

| 字段 | 类型 | 说明 |
|---|---|---|
| `time_rules` | JSON | 多套日期区间时间窗：`[{date_range, open, close, last_entry}]` |
| `is_always_open` | TINYINT | `1` 表示全天开放，可不提供 `time_rules` |
| `close_days` | JSON | 闭馆星期数组，如 `[1,2]`；空数组表示无固定闭馆日 |
| `close_day_exception` | VARCHAR/结构化规则 | 法定节假日开放、顺延闭馆等例外语义 |
| `is_indoor` | TINYINT | `0` 室外、`1` 室内，供 C5 使用 |
| `suggested_duration` | INT | 建议游览分钟数，供 C2 的最低比例窗口与 S1 提示使用 |
| `data_source` | VARCHAR | 硬事实来源，如 `gaode`、`official`、`manual` |
| `fetched_at` | DATETIME | 数据抓取或确认时间 |
| `data_verified` | TINYINT | `1` 表示已人工校准 |
| `conflict` | TINYINT | `1` 表示多源冲突待裁决 |

单套 `open_time`/`close_time` 和单值 `close_day` 仅属于历史 Spike 简化，不作为 M1 生产模型。

## 九条校验规则

1. 每条 `time_rule` 必须包含合法日期区间、`open` 和 `close`；`last_entry` 可空。
2. 普通规则满足 `close > open`；跨午夜规则内部将结束时间表示为次日分钟 `+1440`，并显式标记。
3. `last_entry ≤ close`；不同日期区间不得无意重叠或产生无法裁决的冲突。
4. `close_days` 必须是无重复整数数组，元素范围为 `{1..7}`。
5. `is_always_open=1` 时 `time_rules` 可为空；否则目标日期必须匹配至少一条规则。
6. `suggested_duration > 0`；`energy_level ∈ {1..5}`；`category` 属于九类枚举。
7. `lat`/`lng` 必须位于合理经纬度范围，并通过目标城市范围检查。
8. 硬事实必须有 `data_source` 与 `fetched_at`；多源不一致时设置 `conflict=1` 并人工裁决。
9. 仅 `data_verified=1 && conflict=0` 的记录可进入求解器输入集。

## 当天时间窗解析

1. 按出行日期匹配 `time_rules.date_range`，解析 `[open_min, close_min, last_entry_min]`。
2. 无匹配规则时返回 `NO_MATCHING_TIME_RULE`，不得猜测或使用 LLM 补值。
3. `is_always_open=1` 时跳过固定开放时间窗，但仍受时间锚点、交通和天气约束。
4. 当天星期属于 `close_days` 时默认不可用；结构化节假日例外可覆盖常规闭馆规则。
5. C2 最晚到达时间为：

   ```text
   latest_arrival = min(last_entry, close - duration_ratio × suggested_duration)
   ```

   `last_entry` 为空时只使用时长比例上界；M1 默认 `duration_ratio=0.6`。
6. `arrival < open_min` 时允许等开门；`arrival > latest_arrival` 时当天不可排。
7. 实际可玩时长低于建议时长但达到阈值时允许安排，并输出 S1「实际可玩 X 分钟」提示。

## 闭馆日与例外

- `weekday ∈ close_days` 是 C1 硬约束。
- `close_day_exception` 必须保留原始来源与适用日期；M1 结合结构化节假日表解析。
- 闭馆规则不可用时先尝试把景点移到其他可用日；所有日期均不可用才进入未排入清单。

## 数据保鲜与冲突

- 开放时间与闭馆日会随季节、政策和场次变化，`fetched_at` 不得省略。
- M1 杭州 80–120 个景点的开放时间与闭馆规则执行 100% 人工校准。
- 多源冲突不得由 LLM 自动裁决；保留候选值、来源和人工结论。
- M2 扩展的是自动刷新、可信度分级和规模化冲突管道，不是才开始引入多套时间窗。

## LLM 边界

- LLM 可从来源材料中辅助抽取候选 `time_rules` 和闭馆规则。
- 候选值必须经过九条校验和人工校准后才能入库。
- LLM 不得在运行时生成开放时间、价格、闭馆日、例外或 `data_verified` 状态。
