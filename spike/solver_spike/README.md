# G3 Solver Spike（分层求解可行性验证）

> 工作流 G3 阶段的风险前置验证。**代码可丢弃，只求结论。**

## 验证的问题

1. 「K-Means 聚类分天 → 天内 TSP-TW → 约束校验 → 回溯」这条分层路线，在真实规模数据上**逻辑能否跑通**？
2. 硬约束（闭馆日、开放时间、体力预算、时间锚点、天气）能否被**确定性机制**保证，而非依赖 LLM？
3. 纯经纬度 K-Means 分天是否会产生**严重不均衡**（某天景点过多/体力爆表）？

## 运行

```bash
cd spike/solver_spike
python solver.py        # 跑一次完整分层求解，打印行程
python test_solver.py   # 跑硬约束单测（零 pytest 依赖，也可用 pytest）
```

仅依赖 numpy（本机已装）。

## 成功判据（Gate 3 退出准则）

- [x] 分层求解逻辑跑通，输出可读行程
- [x] 硬约束单测全绿（闭馆日 / 时间窗 / 锚点 / 天气 / 体力检测）
- [ ] 典型规模（N=12, D=3）< 30s 收敛 —— **本 Spike 用贪心，天然 < 1s；真正 <30s 需 OR-Tools 版验证**
- [ ] K-Means 分组均衡性可接受，或已决定替代方案（见下方「已知弱点」）

## 已知弱点（Spike 结论，决定下一步）

1. **纯经纬度 K-Means 不感知每日均衡**：会聚出「某天景点多/体力爆表」的分组，靠 `rebalance` 事后打补丁，不优雅。**结论**：生产建议换 capacity-aware 聚类（如限制每类景点数/能量）或 DBSCAN，或直接上方案 A（多车辆建模，P2 时重评估）。
2. **贪心最近可行是局部最优**：不是全局最优路径，且「先到先得」可能漏掉本可排入的景点。**结论**：生产用 OR-Tools Routing Solver 替换 `solve_day_tsp_tw`（映射见技术选型文档 4.5）。
3. **OD 矩阵是直线距离 × 绕行系数**，非真实路网耗时。**结论**：生产接高德路径规划 API 预计算（见技术选型文档 6.2）。
